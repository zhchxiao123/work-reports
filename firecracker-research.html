定位：轻量 microVM 的 VMM

Firecracker 通过 Linux KVM 运行 microVM；它是执行底层，不是完整的 Agent 编排或沙箱服务平台。

运行职责

配置 vCPU、内存、磁盘、网络和 vsock，加载 guest kernel / rootfs 并启动虚拟机。采用最小设备集合降低开销与攻击面。

Host API

单个 VMM 进程暴露宿主侧 API，通常通过 Unix socket 控制；它不是面向终端用户的多租户业务 API。

上层仍需实现

镜像与模板、实例调度、身份、网络路由、快照存储、配额和用户会话。直接接 Firecracker 需要这些配套能力。

运行链路与隔离

Agent 可以运行在 guest 内，或由外部 Harness 通过工具接口调用 guest。拓扑由上层决定。

平台控制器 → 宿主 API → Firecracker VMM → KVM → Guest Linux → 工具 / Agent
客户端问答、DSH binding 与任务恢复不是这一条虚拟化链路自动提供的功能。

Guest

自己的内核和用户空间；文件、命令与工具依赖由 guest 镜像及上层配置提供。

Jailer 与宿主

生产配置使用 jailer 的 cgroup / namespace 隔离与降权，配合 seccomp。安全取决于宿主配置，而不只是一层 VM。

部署约束

运行需要合适的 Linux / KVM 环境。普通云主机是否开放虚拟化必须核对，不能套用 Cube PVM 的部署条件。

快照：内存与 VM 状态，不自动打包全部资源

暂停后创建快照，再在另一个 Firecracker 进程加载并恢复 guest。磁盘文件与宿主资源由集成方管理。

创建与恢复

Pause → CreateSnapshot → 保存 memory / VM state → 新进程 LoadSnapshot → Resume。加载内存可按需分页与写时复制。

磁盘与网络

disk backing files、TAP 与 vsock 资源需准备好。连接不保证保持，现存 vsock 连接会关闭，工具适配器要重新连接。

版本与身份

恢复需要兼容软硬件；克隆快照可能重复身份、缓存随机数与 Token。VMGenID 的熵更新不自动解决所有应用层重复状态。

快照恢复 ≠ 外部副作用回滚或 exactly-once。快照文件的权限、完整性保护、存储生命周期与配额由上层负责；默认 CRC 不等于认证加密。

与 CubeSandbox、Substrate、DSH 的关系

更适合比较的是 Firecracker 与其他 VMM；CubeSandbox 与 Substrate 则位于更高的平台层。

项目主要层次与当前研究关系
FirecrackermicroVM VMM自建执行底座的候选组件
CubeSandbox沙箱服务与生命周期当前 DSH A / 工具 B 的执行平台
SubstrateActor / worker 执行控制面另一种工具底座候选，文档列出 gVisor 与 Kata + Cloud Hypervisor
DSHAgent Harness模型循环、会话、工具路由与上下文
不能把 CubeSandbox 或 Substrate 称为 Firecracker 的封装；前两者有自己的运行后端与控制体系。详细关系见 三者分层对照。

第一轮研究实验

不修改现有 220 环境；另找满足 KVM 条件的测试宿主，按故障场景验收。

基本执行

启动 guest，验证文件写入、命令执行、API 访问边界与资源限制。

暂停恢复

在 guest 留内存计数和磁盘标记，创建快照后终止 VMM；恢复时核对文件、内存、时间和网络重连。

安全与容量

验证快照克隆身份、权限、配额和资源开销；启动延迟与持久化延迟分别测量，不引用供应商数字作为我们的结果。
