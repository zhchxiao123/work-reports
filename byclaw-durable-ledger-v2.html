账本怎么贯穿系统

账本回答一个问题：这一轮做到哪了，还欠用户什么。它不是一个要新建的大存储。DSH 已经记下了大部分内容，我们只补缺的那一层，并规定谁能写、谁能读。

结论：账本不是一个新存储：DSH 日志存内容，进度记录随日志写，Redis 待确认列表当待办，轮次索引放数据库给 BE 看。日志和进度只由宿主写，索引由 BE 根据结局事件维护；请求都通过命令发给宿主。每次执行是一次可替换的“尝试”。

01账本由什么组成

部分存什么放哪何时有为什么这样放
DSH 日志用户消息、回答、每次尝试、工具调用和结果、这一轮的开始和结束共享存储上的会话文件已有模型上下文本来就来自这里，再复制一份就有两份真相
进度记录这一轮对应哪条命令、哪个 trace id、用哪个沙箱、第几次尝试、配置版本写进同一份 DSH 日志（插件事件）阶段 2和内容同序、同一次落盘，崩溃后看到的是一致的前缀
未完成的命令还没处理完的用户请求Redis 待确认列表已有阶段 2 用它当续跑器的待办清单，不加新存储
轮次索引每轮一行：状态、结局、归属宿主BE 数据库阶段 3BE 读不了会话文件，也要跨会话查询；阶段 4 的租约也放这里
实时文字不在账本里：它只走 Redis，半截丢了就重新生成。

03一轮对话走一遍

下面是阶段 3 之后的完整形态。

  1. 收下输入命令 → 日志 + 索引

    宿主用稳定消息 ID 把消息交给 DSH，并写绑定记录。Redis 命令不确认，留作待办，直到结局落盘。

  2. 模型回答实时走 Redis

    文字直接推送，不写账本。回答完整后 DSH 写入日志。

  3. 执行工具DSH 保证顺序

    工具调用落盘后才经 SSH 到沙箱执行，结果在下一次模型请求前落盘。

  4. 等待提问 · 委派

    提问状态在 Redis，日志里有未结束的工具调用，BE 据事件在索引标“等用户”。委派的父子关系目前只在进程内，由续跑器按日志判断。

  5. 结局落盘后才算数

    先等日志落盘，再把最终答案和结局事件发到 Redis，记下已发送，然后确认命令。BE 消费事件后写索引、入库并收尾。后台任务还在跑时，这一轮保持打开，带时限。

04宿主重启后怎么接

续跑器启动时扫描自己名下未确认的命令，逐条打开会话对照日志。DSH 打开会话时会自动补上被中断的结尾和工具错误结果。

日志里看到动作
这一轮已完成，有答复补发最终答案和结束事件，确认命令；BE 已有标记能吸收重复
这一轮被中断（DSH 补了结尾）新起一次尝试并附恢复说明：先检查目录、git 和外部状态，再决定是否重复外部动作；前端替换这一步。尝试次数到上限直接失败
有未回答的提问继续等待，沿用现有的冷恢复
没有这条命令的绑定记录先按稳定消息 ID 查“已落盘日志 + 队列”：已有就接上，没有才按新命令处理，避免出现两份消息
为什么用恢复说明：工具如果已经跑了一半，DSH 会告诉模型“结果未知”。恢复说明进一步要求先核实外部状态；但发邮件、部署这类外部副作用仍可能重复，所以尝试次数要有上限。

05最难的三处

日志和索引不在一个事务

写入顺序固定

先写日志并等落盘，再发结局事件，BE 据此写索引。崩溃后对不上时，以日志为准，补发事件修正索引。

日志序号不能当全局编号

崩溃后可能复用（推断）

序号就是内存里的长度，丢失的序号之后会分配给别的事件。对外的引用要用 trace id、命令 ID 这类稳定编号。

两个可能丢输入的窗口

读代码推断，待实测

优雅停机可能清空排队；消息被取出后、写入日志前崩溃，它既不在队列也不在历史。靠对账补投兜住：命令留到结局才确认，按稳定 ID 查日志和队列，缺了就重投。改 DSH core 降为可选。
