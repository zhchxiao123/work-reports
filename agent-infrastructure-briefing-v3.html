ByClaw 工具沙箱与 Harness 分离

ByClaw 把 Harness 和工具沙箱分开了。这份汇报讲清楚为什么分、分成什么样，重点是工具沙箱怎么启动、怎么释放。

背景阅读 · 阿里云云原生 · 刘军

Agent as a Service：驱动 Personal Agent 与企业智能体的服务架构

阅读原文 ↗

文章把 Agent 的部署分成两种：Harness 和代码执行放在同一个沙箱（Agent IN Sandbox），或者 Harness 留在沙箱外、通过工具接口调用沙箱（Sandbox as Tool）。ByClaw 选的是后者，这份汇报的部分架构图也参考该文绘制。

01为什么要拆：ByClaw 原来的架构

每个用户登录后，平台为用户启动一个完整的容器：对话、模型调用、插件、命令执行、浏览器都在这一个容器里。

这样做的问题

用户越多越明显
  • 闲着也占资源：用户不说话时容器照样常驻，每个容器各加载一份插件和配置。
  • 大脑和手绑在一起：对话和执行在同一个环境，执行环境出问题，对话也跟着受影响。
  • 换环境代价大：想给某些人一个专门的工具环境（比如游戏开发），只能换整个镜像，对话层跟着变。
  • 凭证和生成的代码在一起：模型生成的代码和平台凭证在同一个容器，一旦被提示注入，边界就没了。

02关键选择：Harness 在沙箱里面，还是外面

要解决上面的问题，关键是把“大脑”和“手”拆开：Harness 负责调模型、判断下一步，工具沙箱负责真正动手。

03同一方向的实践

这条路也是业界的共同选择。Anthropic、OpenAI 和 DeepSeek 都明确把 Harness 和执行环境分开，理由也一致：安全和持久。

大脑：Agent 运行循环与编排手：执行工具的环境持久状态与平台服务
Anthropic · 2026-04 · Beta

Claude Managed Agents

把 Agent 拆成会话记录、Harness（驱动模型干活的循环）、沙箱三块，各自可以独立失败、独立替换。Harness 由平台托管、本身不存状态，挂了就新起一个，读会话记录从断点接着干。每个会话一个隔离容器，建会话时后台准备，推理不等它；空闲时给容器做检查点，状态最多保留 30 天。令牌放在沙箱外的保管库，从沙箱里根本碰不到。执行端可以放在企业自己的机器上，但推理、会话记录和工具结果仍在 Anthropic 一侧。

要点：大脑和手分开，凭证和状态都放在沙箱之外

OpenAI · 2026-04-15

OpenAI Agents SDK

开发框架的新版本内置 Harness，并接入多家沙箱服务。官方的小标题就是“为安全、持久和扩展而分离 Harness 与计算”：设计时要假定存在提示注入和数据外泄，分离有助于让凭证远离模型生成代码的运行环境。状态外置后，丢了沙箱不等于丢了任务，可以在新容器里从上一个检查点继续。

要点：假定会被注入，所以凭证不和生成的代码放在一起

OpenAI · 2026-09-29

ChatGPT Dots

ChatGPT 里的常驻个人 Agent：对话结束后继续干活，可以自己决定何时暂停、何时醒来，也支持定时和事件触发；空闲时做只读的“主动调研”。每个 dot 有自己的一台云电脑（Linux + Chrome，状态在两次使用之间保留），用户可以打开查看或接管；编排和安全系统在 OpenAI 侧，与执行环境分开。目前每人一个主 dot，并行的活派给后台子 Agent、ChatGPT Work 和 Codex；多个 dot 组队是官方愿景。

要点：编排与执行分开，每个 dot 一台有状态的云电脑

DeepSeek Harness 团队 · 2026-10 · 研究原型

Super-agent

分两步解耦：先把推进 Agent 循环的计算和会话状态分开，再让循环和执行环境分开。上层 Router 只负责交互和分派，Worker 隔离执行，外部 Watchdog 监督有没有实质进展。它也把“Agent 不接触凭据也能使用凭据”列为开放问题。

要点：计算、状态、环境三者分离，再加独立的控制回路

04我们的选择：Sandbox as Tool

方向和上面一致，具体做法按 ByClaw 的情况取舍：企业内部署、用户多、大部分时间只是对话、已经有自己的数字员工和技能体系。

选择我们的做法为什么
Harness：共享宿主一个常驻宿主承载所有用户的对话，每人一个独立的上下文大部分时间用户只在对话，不需要为每人常驻一整套环境；公共部分只加载一份
工具：每人一个沙箱对话时启动，闲置 10 分钟释放，释放前先查有没有任务在跑容器级隔离，生成的代码只能碰到自己的环境；闲时不占资源
状态：放在沙箱外用户文件、对话记录、个人配置都在持久存储上沙箱随时可以释放重建，用户无感
平台：自己管沙箱由 ByClaw 平台统一创建和回收数据和工具留在企业内；沿用现有的员工、技能和权限体系

为什么不把 Harness 留在沙箱里

也就是 ByClaw 原来的做法

依赖复杂本地工具链的场景，这样更容易起步。但生成的代码和凭证在同一边界内，推理和环境绑在一起，也无法分别调度。对我们这种多用户的企业平台，分开更合适。

为什么不直接用托管平台

比如 Claude Managed Agents

编排在厂商平台上，工具的输入输出要经过外部服务，也接不进我们的数字员工、技能和权限体系。我们借鉴它的拆分思路，编排和执行都留在自己平台上。

05现在分成了什么样

分离已经完成。原来每个用户独占一整个容器，现在对话在共享宿主里，动手在每个人自己的工具沙箱里。

06工具沙箱怎么启动

登录不起工具沙箱，平时是对话的一轮把它拉起来，只聊天也算。闲置释放后的下一轮会再起一个，这一轮要多等沙箱启动的时间。另一个入口是用户在页面上做账号登录：要打开远程桌面，前端会直接拉起沙箱。
  1. 登录：只准备 Harness

    用户登录后，BE 异步准备用户存储，并启动开了“登录自启动”的规格：Harness 的规格开着，工具沙箱的规格关着，所以只在共享宿主上为用户建好上下文。这是规格配置决定的，配错了登录也会起沙箱。建上下文时要写到沙箱里的东西（目录、Skill 副本等）先排队。之后每次提问前，BE 还会再确认一次上下文，并带上新令牌。

  2. 发消息：触发启动

    模型运行之前，这一轮要先读用户目录里的指令文件、Skill 和规则，而用户目录只有沙箱能访问，所以这时候起沙箱。只聊天不用工具的一轮也会起。

  3. 向 BE 要沙箱

    Harness 以用户身份调用 BE，按“用户 + 沙箱类型”获取或创建：已有就复用，没有就新建。Harness 不持有沙箱平台的凭据，规格也由 BE 管。

  4. 连上去

    BE 返回沙箱地址，Harness 等端口可达后用 SSH 连接（阿里云环境经 WebSocket 桥接）。沙箱只接受这个 Harness 的密钥，不接受密码和 root 登录。

  5. 排队的工作先落地，然后开始干活

    排队的写入先执行，某一项失败只记日志，不挡后面的；然后才读指令文件、调模型、跑工具。之后的操作都复用这条连接。

启动不顺利时

情况处理
向 BE 要沙箱失败（如正在创建或释放）每 3 秒重试，最多 60 秒，都在这次操作内完成，用户这一轮不会因一次失败而中断
60 秒后仍然不行放弃本次并报出原因；之后按 1 秒起、翻倍到 30 秒的间隔再试，不会每次操作都去打 BE
返回的地址连不上释放这条记录，重新要一个，只做一次
用户令牌过期从登录状态取最新令牌重试一次；BE 下发新令牌后退避立即解除
规格配错（没有 SSH 端口）配置错误，立即失败，不重试

07工具沙箱怎么释放

Harness 这一侧：10 分钟没有任何操作，并且确认没有活在跑，就释放。每次操作都会把 10 分钟重新计时；有命令在执行时，计时根本不开始。平台另有一条 30 分钟的回收规则，见下表。

还有哪些情况会释放

情况发生什么
平台空闲回收作为兜底，平台每分钟扫描一次，超过 30 分钟（默认值）没有访问的工具沙箱会被释放。账号登录时前端拉起的沙箱，Harness 连上之前就靠这条规则回收
用户手动释放通过页面状态入口或管理端释放；下一次操作再起新的
用户上下文被销毁、共享宿主正常停止关闭连接时一并释放沙箱，最多等 5 秒；没等到结果也不阻塞退出
用户换了沙箱类型起新沙箱之前先释放旧的，因为两者共用用户家目录
共享宿主崩溃，来不及释放沙箱会留下来。下次同类型直接复用，换了类型就先释放旧的；用户不再回来时，由平台自己回收
沙箱被平台移除当时那个操作失败一次，下一个操作自动起新沙箱

释放后什么还在

还在

用户文件（工作区）
用户家目录：CLI 登录状态、配置、用户级安装的工具
Harness 上的会话和上下文

不在了

临时目录 /tmp
还在跑的进程（超过 6 小时被放掉的那些）
装到系统目录的软件

08效果：用起来和原来一样

验收标准是“拆分前后功能完全一样”。同一套环境里，一个用户走旧架构、一个走新架构，跑同一组检查，结果逐项相同。

  • 执行命令、读写文件、终端：在用户自己的工具沙箱里，和别人隔离
  • 浏览器与远程桌面：同一个浏览器，网站登录状态保留，可在页面里看到
  • 账号登录、操作录制：照常可用
  • 技能与指令文件：每轮对话都能读到，技能里的脚本能执行
  • 个人配置和登录信息：工具沙箱释放再重建后仍在
  • 知识库等平台命令行工具：照常可用
  • 群聊、团队任务、代码图谱：照常可用
  • 长时间在线：连续几天不掉线，Harness 不会在任务进行中释放沙箱

新能力：按人换工具环境

拆开之后，给某些人配一个专门的工具环境，只需换这个人的工具沙箱，对话、数字员工、技能都不用动。我们用游戏开发环境（Unity）做了验证。

09安全：把生成的代码隔离出去

这是我们做分离的另一个原因：模型生成的代码只在工具沙箱里运行，碰不到共享宿主和别的用户。

为什么分离和安全有关
模型生成的代码不可信。提示注入只要说服模型读取自己的环境，就能拿到同一容器里的凭证。结构上的解法，是让凭证根本碰不到生成代码运行的地方。

Anthropic 的做法是“令牌永远无法从沙箱触达”；OpenAI 的说法是“设计时要假定存在提示注入和数据外泄”；DeepSeek 把“不接触凭据也能使用凭据”列为还要解决的问题。分离之后，权限也可以集中在工具边界检查。

还要注意的一点

  • 共享宿主是一个进程：用户之间靠上下文隔离，不是容器隔离。所以宿主里不能运行不可信代码，插件要守“不共享进程级状态”的规则，这也是工具必须全部放进沙箱的原因。

10账号密码保管：第一版方案

Agent 用浏览器干活时，经常要登录网站。现在没有地方保存账号密码，让 Agent 自己填，密码还会经过模型。第一版由 ByClaw 自己加密保存在数据库里。

为什么要做

来自我们自己的业务需要
  • 自推广要运营新媒体矩阵：我们要在小红书、CSDN 等平台持续发内容，账号多、平台多，发帖、回复、看数据都要先登录。
  • 这些工作正交给 Agent 去做：Agent 在工具沙箱里用浏览器操作这些平台，登录这一步绕不开账号密码。
  • 现在没有统一保管的地方：账号密码散落在个人手里，要么口头告诉 Agent，要么写进对话或文件，密码就进了模型上下文、会话记录和第三方模型服务。
  • 目标：账号密码由系统统一保管，Agent 能用来登录，但模型始终看不到。
第一版目标：大模型看不到账号密码。模型只拿到账号引用（一个 id），取值和填写都由系统在模型看不见的地方完成。状态：原型已在测试环境跑通，还有几项要补齐后才能上线。

同类产品怎么做

个人 Agent 产品已经把“替用户保存账号密码、由 Agent 代为登录”做成了标准功能，入口都放在设置里，由用户自己录入。

MuseGrok BotByClaw 第一版
入口设置 → 安全存储设置 → 保险库账号管理（页面待做）
保存内容网址、账号、密码登录信息、支付、联系信息网站、账号、密码
网站绑定网址可绑定多个网站，含子域名一个网站，含子域名，且只在 HTTPS 页面填写
告诉 Agent 何时用—有“提示”字段只有名称
模型能否看到明文分析显示不能公开界面未说明不能，已在测试环境验证
我们可以借鉴的：给账号加一句“使用提示”，帮助 Agent 选对账号；允许一个账号绑定多个网站。支付信息风险高，第一版仍不保存。

我们的方案

一次登录怎么走

  1. 保存

    用户以自己的身份保存网站、账号名和密码，BE 加密后写入数据库。之后只能修改或删除，列表只返回名称和网站。

  2. 打开并选择账号

    模型用浏览器打开登录页，再列出可用账号，选一个 id。账号属于谁由 Harness 的上下文决定，模型不能指定。

  3. 要求填写

    模型只给出“哪个账号、填用户名还是密码、填进哪个输入框”。工具没有“值”这个参数，模型想传也传不了。

  4. 核对并取值

    Harness 查当前网址，通过签名的服务通道向 BE 取值。BE 核对三件事：账号属于这个用户、页面是 HTTPS、网站与保存时一致，任何一项不符就拒绝。

  5. 填写并遮挡

    值交给浏览器填入。Harness 记下这个值，此后这个 Agent 收到的所有浏览器结果里，只要出现它，就替换成“已隐藏”。模型收到的只有“已填写”。

实拍：在 ByClaw 里用保存的账号登录

测试环境实录。左侧是对话，也就是模型能看到的内容；右侧“远程桌面”是这个用户工具沙箱里的真实浏览器，用户能看到，模型看不到。演示用的是公开的练习登录站，页面上自带的测试账号提示已打码。

为什么大模型看不到

五道保证，缺一不可
  • 参数里没有值：模型只能传 id，值不会出现在模型输出、工具调用记录和发给模型服务商的请求里。
  • 身份不由模型决定：取谁的账号由上下文决定，拿别人的 id 也取不到。
  • 取值通道模型够不着：取值只认 Harness 的服务签名，密钥不在工具沙箱里；沙箱里的用户令牌调不通这条路。
  • 值不落日志：BE 和 Harness 都不记录值，审计表只记操作、字段和网站。
  • 结果统一遮挡：哪怕网站把填入的内容原样显示在页面上，模型拿到的也是“已隐藏”。

验证结果

检查结果
用保存的账号登录真实网站通过　登录成功，全程没有向用户要密码
网站回显填入的随机密码通过　模型拿到的是“已隐藏”
会话日志、各服务日志、数据库里搜索该密码通过　都没有
数据库里查看保存的账号通过　只有带版本号的密文，没有明文
不带服务签名调用取值接口通过　被拒绝
浏览器本地数据待修　浏览器自动填充会保存普通输入框（如用户名）里填过的内容

第一版已做到

密码不外流到这些地方
  • 模型的上下文和模型服务商
  • 会话日志、各服务日志和审计
  • 浏览器返回给模型的观察和页面文本

上线前要补齐

按优先级
  • 关闭浏览器自动填充和密码保存
  • 填写后禁止截图或对截图打码：截图是图片，文字遮挡管不到
  • 账号录入页面和首次使用确认卡片
  • 主密钥的生产保管：只挂载给 BE，云上可交给 KMS 托管，并纳入备份

第一版不承诺的

  • 工具沙箱被完全攻破时，填写那一刻密码仍会到达沙箱里的浏览器。根本办法是把登录用的浏览器单独放进一个不运行模型代码的沙箱，作为下一阶段。
  • 遮挡按原文匹配，网站如果把值改了形式（如编码后）再显示，遮不住。
  • 支付类账号不建议保存，由用户在远程桌面里亲自操作。

为什么存在自己的数据库，而不是单独部署密码管理器

在我们的场景里，两者的安全性差别不大，运维差别很大
  • 怎么存：账号和密码用国密 SM4-GCM 加密，每个用户一把派生密钥，密文与用户、条目、字段绑定，挪到别处无法解开。主密钥只放在 BE 能读的地方，不进数据库，所以数据库导出或备份泄露也拿不到明文。
  • 为什么够用：模型看不到密码，靠的是前面的五道保证，与存在哪里无关。BE 必须能读才能填写，单独的密码管理器在 BE 被攻破时同样挡不住。
  • 省掉什么：不用多部署、监控、备份一个服务，也不用处理重启后解封，客户内网交付更简单；也能直接使用国密算法。
  • 留了余地：存储只有一个可替换的入口。客户要求硬件密钥、外部 KMS 或已有的专业密码管理平台时，通过配置切换，上层不用改。
