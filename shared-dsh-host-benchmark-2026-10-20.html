共享 DSH 宿主性能测试报告

一个 Node 进程承载多个用户的 DSH 上下文，工具在每个用户自己的沙箱 B 里执行。本报告回答七个问题：宿主在 0、1、2、3 个用户时各占多少内存；首次需要工具调用、工具环境已启动两种情况下的首词响应时间；以及多个用户同时对话时首词是否变慢。全部数据来自 220 e2e 环境的真实登录与对话。

01结论

先给答案，细节在后面各节。

一句话
第一个用户让宿主从 82 MB 涨到 380 MB，之后每多一个用户只多 25 到 50 MB；工具环境冷启动让首词晚约 2.5 秒，三个用户同时对话首词不变慢；扩到 10 个用户宿主只用 650 MB，但 220 这台机器先撑不住了。

内存：插件和 profile 在第一个上下文时一次性载入，后续用户只付上下文本身的代价。跑完约 40 轮对话后进程稳定在 490 到 530 MB。

首词：不需要工具的对话 0.4 秒出第一个字；B 已在运行时 0.6 秒；B 空闲暂停后唤醒 1.9 秒；B 从零创建 3.1 秒。冷启动的代价发生在模型调用之前，因为会话目录和技能要先从 B 取。

并发：1、2、3 个用户同时发起带工具的对话，首词中位数分别为 611、361、479 毫秒，差异在模型自身的波动范围内。

10 个用户：宿主进程 649 MB，每用户约 28 MB；5 个用户同时对话首词 0.9 秒，10 个同时 1.5 秒。10 个 B 同时从零创建要 19 秒才出首词，瓶颈在 OpenSandbox 建容器。之后测试机内存耗尽进入抖动，后续 10 用户数据不可信，详见第 06、07 节。

02环境与口径

所有对话都从 BE 的 WebSocket 发起，与前端页面走同一条链路；时间戳打在客户端收到每一帧的时刻。

首词的三个时刻

从发出消息那一刻起计时，单位毫秒

首个模型输出：第一帧带内容的流，通常是思考过程的第一个字。这是用户第一次看到“在动”。

首个回答字：工具跑完后正式回答的第一个字。

整轮结束：收到 appStreamResponse。

四种工具环境状态

同一条提示词：用 bash 执行 hostname，只回复输出

无工具：提示词“只回复一个字：好”，作模型基线。

冷：B 被删除，本轮要创建容器、起 sshd、连上。

空闲暂停：B 由工具环境自己因空闲暂停，本轮唤醒。

热：B 正在运行。

口径定了。↓　第一个问题：宿主随用户数怎么长。

07发现的问题

两个问题：一个是工具环境被外部暂停时的边界情况，一个是 10 用户测试暴露的测试机瓶颈。

B 被外部暂停后 5 秒内对话，一半的轮次空回答

状态 边界情况　触发条件：通过 OpenSandbox API 暂停 B，而不是工具环境自己因空闲暂停
场景清洁轮次表现
外部暂停后 5 秒发消息3 / 6空回答，耗时 8 到 15 秒，worker 报 SSH operation cancelled
外部暂停后 20 秒发消息3 / 3正常，3.0 到 5.3 秒
工具环境自己空闲暂停后唤醒3 / 3正常，见第 04 节
原因：工具环境只在 SSH 连接断开时才察觉 B 不可用；外部刚暂停时 TCP 连接还在，第一个远程操作挂到超时才被取消。建议：远程操作卡住超过若干秒时，主动查一次沙箱状态，发现已暂停就直接走唤醒。生产路径里 B 都由工具环境自己暂停，所以当前不受影响。

220 测试机在 10 用户时内存耗尽，后续数据失真

状态 环境限制　15 GB 内存、无 swap、同时跑着整套 e2e 和 byclaw-direct 栈
观测数值
加 10 用户前后的可用内存2.3 GB → 1.3 GB（宿主 +0.8 GB，10 个 B 容器 +1.15 GB）
并发对话时的系统负载load 2.4 → 18 到 19，iowait 71% 到 85%，磁盘 vda 100% 忙、读 130 MB/s
读盘的来源宿主、BE、gaussdb、mysql、coredns 各 50 到 100 MB，分散在所有容器：是页缓存被挤掉后的整机抖动，不是某个进程在读
抖动期间 10 路纯模型对话（不碰工具）首词 7.5 s → 5.4 s → 3.2 s，随负载回落而下降；单用户基线 0.4 s
宿主进程自身813 到 892 MB，CPU 峰值约 1.2 核（机器 8 核）
结论：10 用户的瓶颈是这台测试机，不是共享宿主。要拿到可信的 10 用户以上并发数据，需要一台内存不被其他栈占满的机器，或者先停掉 220 上无关的栈。建议：生产上按“宿主 400 MB + 每用户 30 MB + 每个 B 约 40 MB”预留内存，并给 B 设更短的空闲暂停时间以释放容器内存。
所有数据都可以复跑。↓　脚本和原始数据都留在 220 上。

08复现方法

文件都在 220 的 [构建目录]/ 下，按阶段分开跑，每个阶段几分钟。

  1. 准备三个用户登录到同一个状态文件

    10 个用户的个人助理都指向模型 10000542（deepseek-flash）。用户C 和后加的 7 个用户是本次新开的，原模型备份在 restore/employee-<id>.orig.tsv。

  2. 内存bench.sh mem

    释放全部用户，重启宿主，等 45 秒读空载；再逐个登录，各等 25 秒读一次。

    bash bench.sh mem

  3. 首词bench.sh baseline / cold / paused / warm

    cold 先用 OpenSandbox API 删除三个 B；paused 先用 API 暂停。空闲暂停场景是等 180 秒后用 bench-idle.sh paused。

    for p in baseline cold paused warm; do bash bench.sh $p; done

  4. 并发bench.sh concurrent

    先给三个用户各跑一轮预热，再按 1、2、3 用户同时发消息，重复两轮。

    bash bench.sh concurrent && python3 summary.py

原始数据与工具

  • bench-chat.mjs：发一轮对话，记录每一帧相对发送时刻的毫秒数，按 tool.call / tool.result / answerDelta 标记首词时刻。
  • bench.sh：3 用户各阶段编排；bench10.sh：10 用户版本（mem / warm / concurrent / coldconc / conc10plain 等）；原始记录在 bench-results.jsonl 与 bench10-results.jsonl；summary.py / summary10.py 汇总。
  • 环境：220 e2e，8 核 15 GB，宿主镜像 byclaw/dsh:0.2.1-multi2，工具环境空闲 180 秒暂停，BE 已启用 byclaw.sandbox.shared-dsh-host.*。
