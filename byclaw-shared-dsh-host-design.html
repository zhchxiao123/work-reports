ByClaw · DSH 0.2.1 · OpenSandbox

一个 DSH 宿主承载多个用户，每个用户一个工具沙箱

ByClaw 之前为每个用户启动一个完整的 DSH 容器。本方案把它拆成两层：一个常驻的 DSH 宿主进程（A）承载所有用户的对话上下文；每个用户的文件、进程和终端在自己的工具沙箱（B）里执行。平台（BE）把“启动一个沙箱”变成“在宿主上添加一个用户上下文”。全部改动已在 220 e2e 环境跑通，并提交到 PR beyonai/ByClaw#312。

01问题与结论

先说为什么要拆，再说拆完是什么样。

结论
把 DSH 分成常驻的对话层和按需的执行层之后，每个用户的固定开销从一个容器降到 25 到 50 MB，工具沙箱空闲即暂停，而文件、进程、终端的隔离仍然是容器级的。

原来的问题：每个用户一个 DSH 容器，空闲时也常驻约 200 MB 以上；首次登录要拉起整个容器；插件、profile 每个容器各载一份。用户一多，内存先于一切成为瓶颈。

现在的形态：宿主 A 是一个 Node 进程，插件只载一次，每个用户一个 Cordis 上下文；B 是用户自己的 OpenSandbox 容器，第一次用工具时创建，空闲 3 分钟暂停，被删了下次自动重建。BE 通过宿主的管理 API 增删用户，Web 入口经宿主网关按用户路由。

默认行为不变：所有插件改动都是配置开关，不设置时和今天一样；BE 不配置共享宿主时仍是每用户一个沙箱。

03三层职责

划分原则只有一条：碰用户文件和进程的事情在 B，其余在 A，决定谁该存在的在 BE。

宿主 A

常驻 · 一个进程 · 每用户一个上下文

Web UI、会话持久化、模型调用、Agent 循环、插件逻辑。每个上下文有自己的 dsh-home、worker 名、环回监听端口、浏览器实例。

对外两个口：管理 API（BE 用）和 Web 网关（浏览器用）。

工具沙箱 B

按需 · 每用户一个容器 · 同一镜像

通过 DSH 0.2.1 的 SSH provider 接管 ctx.fs、ctx.subprocess、ctx.sandbox 和 PTC。bash、文件树、git、终端 PTY、技能文件、语音和媒体落盘、agent-teams 成员进程都在这里。

只挂载这个用户的 /by 和只读的 agent-templates。

平台 BE

控制面 · 不碰用户数据

决定员工授权、谁在线、何时回收。启动 = 向宿主 PUT 用户；释放 = DELETE；Web 入口 = 宿主网关地址加该用户的 token。

空闲回收仍按记录（即按用户）计时，30 分钟无访问即释放上下文。

职责清楚了。↓　把一个用户从登录到回收走一遍。

04用户生命周期

每一步都在 220 上用真实登录和对话验证过，时间是当时的实测值。

  1. 登录BE 向宿主 PUT 用户

    BE 的 SharedDshHostRuntimeProvider 把 byclaw-dsh 的启动请求变成 PUT /v1/users/{用户}，带上 sandboxId 和该用户的个人参数。宿主为这个用户组合 profile、加载插件、启动环回 Web 监听，写入 Redis 归属键。7 到 11 秒返回 ready 和该用户的 webToken。

    PUT 幂等；上下文已在运行时直接返回。BE 记录 sandboxId 为 byclaw-dsh-<用户>，endpoint 为网关地址。

  2. 打开页面浏览器经网关进入用户的上下文

    入口 /u/{用户}/chat?token=…。网关校验 token 后种下仅限该用户路径的 cookie，并把请求以环回身份转给该上下文的 DSH 监听。无 token 401，拿别人的 cookie 访问 401。WebSocket 同样经网关代理。

  3. 第一次工具调用创建或唤醒 B

    上下文的第一个远程操作触发租约：B 不存在就通过 OpenSandbox 创建并等 sshd 就绪；已暂停就恢复。会话目录在 B 上创建，技能从 B 读取，然后才调模型。冷启动首词 3.1 秒，暂停唤醒 1.9 秒，热态 0.6 秒。

  4. 空闲B 自己暂停，上下文保留

    3 分钟没有操作、也没有打开的流，B 被暂停；正在跑的命令和后台任务会占着流，不会被中途暂停。上下文留在宿主里，内存约 50 MB。

  5. 回收BE DELETE 用户

    30 分钟无访问，BE 的空闲清理任务按记录释放，经 provider 变成 DELETE /v1/users/{用户}。宿主销毁上下文、释放 Redis 归属键；B 保持暂停状态，用户文件都在共享卷上，不丢。

  6. 宿主重启reconcile 自动重建

    宿主重启后所有上下文消失，BE 的一致性检查发现远端不存在，按记录自身的类型重拉，用户在几秒内回到宿主。这里修了一个原有缺陷：重拉以前按员工类型解析，会把 byclaw-dsh 用户拉成 openclaw。

生命周期里最关键的部件是 B 的租约。↓　它怎么保证 B 来去自如而连接不断。

05工具环境 B 的机制

由插件 @byclaw/dsh-tool-env 实现，默认关闭，环境变量 BYCLAW_DSH_TOOL_ENV=opensandbox 时生效。

DSH 基础行替换为效果
fs-sandboxdsh-fs-ssh读写、列目录、搜索在 B 上执行
subprocessdsh-subprocess-sshbash、PTY、后台任务在 B 上，流保持打开时 B 不会被暂停
sandboxdsh-sandbox-ssh权限策略由 B 执行；拆分模式默认 danger-full-access，B 容器本身是边界
ptc-runtime经 SSH 启动PTC 的引导脚本摘要由 A 按自身安装计算，B 校验不匹配即拒绝
A 和 B 必须同一个镜像：helper 和 PTC 引导的摘要来自 A 自己的安装，镜像不一致时 B 会拒绝连接。
B 隔离的是文件和进程。↓　那同一个进程里的用户，靠什么互不可见。

06隔离模型

两种边界：宿主进程内按上下文的软隔离，B 的容器级硬隔离。凡是碰用户数据的动作都落在硬边界里。

对象原来（每用户一个 A）现在
员工可见性BE 按用户授权不变，每个上下文以自己的身份拉清单
员工模板与技能A 的 DSH_HOME 和 /by/.openclaw用户自己的 dsh-home 和自己 B 上的 /by/.openclaw
会话历史A 的 DSH_HOME/sessionsusers/<用户>/dsh-home/sessions
命令、终端、gitA 容器内B 容器内，容器级隔离
浏览器A 内一个固定 socketA 内每用户一个 browserd，socket 在各自运行目录
Web 入口每用户一个地址网关 /u/<用户>/ + 按用户的 token 与 cookie
环境变量A 的全部环境透传给命令只放行列表内的变量，宿主密钥不进 B
故障影响面一个用户的 A 崩只影响自己插件异常按用户隔离；Node 进程级崩溃影响全部用户
软隔离的前提是插件守规矩：这轮改造逐个清掉了进程级共享状态（agent-teams 的全局表、by-framework 的内存历史、浏览器的固定 socket、从 process.env 读用户身份）。以后新增插件要守同一条规则。
隔离靠插件守规矩。↓　每个插件具体改了什么。

08平台侧改造：宿主启动器与 BE

宿主启动器是一个脚本；BE 是一个 provider 加一段配置。两边之间只有一份契约。

宿主启动器

scripts/byclaw-multi-host.mjs · 19 个单测

管理 API（Bearer token）：PUT /v1/users/{u} 幂等确保上下文运行并返回 webToken；GET 查状态；DELETE 销毁；GET /v1/health 列出用户。

网关：/u/{u}/ 下的 HTTP 和 WebSocket 代理到该用户的环回监听，token 换 cookie，cookie 限定路径。

上下文组装：复用 managed profile 的 bundle 和 node_modules；按用户把配置叠加到各行（因为 patch 会整体替换 config）；替换 Web 监听行；按设计禁用的行标记原因；为每个上下文提供 webStartup。

失败隔离：一个用户启动失败、崩溃或未处理的拒绝只标记该用户 failed，下一次 PUT 重试。

BE

SharedDshHostRuntimeProvider · SandboxServiceTest 41 个全过

启用：byclaw.sandbox.shared-dsh-host.base-url、token、可选 web-base-url。未配置时一切如旧。

路由：只有 byclaw-dsh 类型走宿主，openclaw 等其它类型仍走原 provider。sandboxId 固定为 byclaw-dsh-<用户>，endpoint 指向网关。

回收：现有空闲清理任务按记录调用 remove，即 DELETE；心跳对共享上下文是空操作，它活到 DELETE 为止。

两个修复：reconcile 按记录类型重拉（原来按员工解析成 openclaw）；未托管宿主写的 Redis 归属键仍可让 BE 跳过独立沙箱。

契约项内容
每用户主目录<root>/users/<用户>/dsh-home，插件通过 dshHome 及派生路径拿到
PUT 请求体{ sandboxId, env? }；sandboxId 用于空闲上报，env 是该用户的个人参数（不能覆盖用户身份）
PUT 响应{ userCode, status: "ready", hostId, webPath: "/u/{用户}/", webToken }；失败 503 带 error
Redis 归属byclaw:dsh:shared-host:user:<用户> = hostId，EX 90，每 30 秒续期
Web 入口<web-base-url>/u/<用户>/chat?token=<webToken>
链路通了。↓　它到底省了多少、慢了多少。

10横向扩容

宿主无状态、归属在 Redis、消息按用户名路由，这三点已经具备；缺的是 BE 侧选宿主。真正按用户线性增长的是 B 的数量和模型并发。

  • 已具备：Redis 归属键记录用户在哪台宿主；消息路由与宿主无关；用户数据在共享存储上；Web 入口按宿主返回。
  • 待做：BE 的宿主池配置、放置规则、按 health 的用户数做最少负载选择。
  • 真正的边界：每活跃用户一个 B 容器，OpenSandbox 要先能横向扩；大量用浏览器的用户会先把 A 的内存吃掉，那时按“用浏览器的用户”单独分组放置。
方案可以扩。↓　但有几处要说清楚的缺口。

11已知缺口与下一步

按影响面排序，前两项需要你决定。

事项现状下一步
CodeGraph 不可用它的 MCP 连接会一直占着 B 的流，B 永远不会空闲暂停，所以在共享宿主里暂时禁用接受 B 常驻，或把它改成按需连接
bash 看不到个人环境变量只放行 TZ、LANG、BE 地址几个；插件仍能读到用户的个人参数，但技能脚本直接从 env 读密钥会读不到扩放行列表，或在创建 B 时注入
外部暂停 B 的边界B 被 OpenSandbox API 从外部暂停后 5 秒内对话，6 轮里 3 轮空回答；自身空闲暂停不受影响远程操作卡住时主动查沙箱状态
宿主进程级故障插件异常已按用户隔离；Node 进程崩溃（如 OOM）会同时断掉全部用户，reconcile 几秒内重建给宿主设内存上限并监控；多宿主后影响面自然缩小
浏览器仍在 A 上每用户一个 Chromium 是 A 上最大的内存消耗按浏览器用户分组放置，或把 browserd 移到 B
BE 容器 healthcheck探测 8080 而服务在 8086，显示 unhealthy；与本方案无关，预先存在改 healthcheck 端口
