Muse Agent 详细设计：会话、运行时、文件、资料库与记忆

第一篇报告回答了"基础设施、数据流、组网、互联"。本篇深入 agent 本身：它如何组织会话（主聊、线程、侧聊、目标线程），一轮对话内部发生什么（事件流、lane、工具路由、子代理、压缩），文件与资料库怎么落在 VM 文件系统上，记忆是什么形态，以及共享 agent 与 peers 的设计。证据主要来自内嵌 web 客户端中的 218 条网关路由、4152 条界面文案、事件与字段名。

01结论

一句话
Muse 的 agent 是一个"以文件系统为真相源"的运行时：对话转录、记忆、工件、Spaces、播客都是 VM 家目录下的文件，资料库只是这些文件的视图；对话本身则是一条带 lane 的事件流。

会话：一个不可删除的主聊（canonical main chat）+ 任意多个线程；线程可以挂在目标（goal）上；侧聊面板承载线程、共享 agent 的私有侧聊和 peer 侧聊；/thread/new 是草稿线程，首条消息才创建会话。

一轮对话：客户端发 chat.send，服务端用 delta.* 事件推回：message_start → text_append → tool_start/tool_done → placeholder/presentation → compaction_start/done → turn_done。消息带 lane（main / subagent / critical / normal），子代理推理单独成 lane。

工具路由：服务端工具（tool.exec / tool.imagine / tool.zeitgeist / tool.web_fetch）、本机节点工具（nodes.invoke_*）、VM 浏览器任务（owner 可为 user / main_agent / cron，可被用户接管）三类并存，统一经审批与名为 sentinel 的出网管控。

文件：两套文件系统并存，Mac 侧 files.*（经节点）与 VM 侧 fs.*；VM 布局为 /home/hatch/workspace/ 下 your_files、artifacts、podcasts、conversations，根记忆文件 /MEMORY.md。记忆是可搜索、可合并（consolidate）、可重建索引的 Markdown 文件集。

先看壳：用户能进入哪些面板。↓　这决定了后面每个子系统的入口。

03会话模型：主聊与侧聊

后端对象叫 session，界面上叫 thread / side chat。主聊是唯一特殊的 session；其余都是平等的线程，差别只在它们挂在什么东西上。

操作路由说明
列出会话GET /api/session/list、/api/session/list/{id}返回 pinned / archived / unread_count / space_slug；侧聊面板与本地缓存（isSideChatListCacheEntry）据此渲染。
创建POST /session/start草稿线程路由 /thread/new；草稿历史源键 hatch.chat.draft，首条消息发出时才真正创建。
管理/session/rename · pin · unpin · archive · unarchive · delete文案 "Thread rename is not available on this VM yet" 说明部分能力按 VM 版本灰度。
主聊chat.main，路由 /"The canonical main chat thread"；在共享 agent 作用域里可被整体共享为"有界最近消息副本"。
目标线程/thread/{id}?goal=…&goal_intent=…线程与 goal 绑定；activity.goal_actions 给出该目标下 agent 做过的动作。
读取历史GET /chat/history、/chat/history-window、/chat/message、/chat/searchhistory-window 带最大响应字节数限制；chat.delete_turn 可删一轮。
已读与催促POST /api/chat/{thread_id}/seen、/chat/unread-count、/chat/pokechat.poke 推断为"戳一下 agent 继续"的轻量触发。
小结：会话模型很扁平，复杂度被推到了作用域（goal、shared agent、peer、space）和本地缓存（转录按 sessionId 缓存并记录最近访问）上。

04消息与流式事件

消息对象的字段、事件流的类型和顺序，都能从 web 客户端的归一化与分组函数里直接读出来。

消息对象

从 isChatMessageEligible* / mergeToolCallData 还原
  • role：user / assistant / system。
  • 标志：isBackground（后台工作产出，不参与气泡分组）、isToolTranscript（工具转录）、presentationCarrier（仅承载展示）。
  • toolCall：{toolCallId, name, toolType, request, result, status}，status 为 running / completed / failed 等。
  • compaction：{phase, reason}，有压缩的消息不可加反应、不计时间戳。
  • 内容槽：text、images、files、widgets、presentations、placeholders、citations、attachments、reactions。
  • 排序：sortSeq；运行中的 toolCall 保持原位直到完成。
  • 审批：approvalId 关联审批卡；checkpoint 字段用于轮次分隔线。

widget 种类（部分）

kind === … 枚举中与内容相关的值

browser_task（浏览器任务卡，含截图与步骤）· artifact · space · saved_space · file · image · video · thread / chat_thread（引用其它线程）· goal · citation · local_map · hero_image · unit_media（feed 媒体）· person · cart / hotel_results / ads_entity（购物、酒店、广告实体）· shared_agent · invite · token_input。

widget 有自己的状态通道：widgets.state.set / patch，并有 chat.widget.normalize 做服务端归一化。购物、酒店、广告类 widget 表明对话里有商业化实体卡。

05运行时内部逻辑

把路由、事件和文案拼起来，能还原出一个"主代理 + 子代理 + 三类工具后端 + 定时触发"的运行时轮廓。以下按一轮对话的决策顺序排列。

  1. 入口触发源不止用户消息全自动

    浏览器任务的 owner_kind 枚举为 user | main_agent | cron，说明同一套任务既可由用户发起、由主代理自主发起，也可由定时任务发起。定时任务用 job_id 标识，tasks.run 可手动触发一次，tasks.runs 列出运行记录；文案里称 "Cron automation"，出网作用域里有 "Chat + Crons + Artifacts" 三类。渠道（WhatsApp / Messenger / Telegram companion）与 peer 投递（peers.inbox.deliver）也是入口。

  2. 模型与技能每轮前可切模型，技能可禁用全自动

    model.set {model} 返回 selected_model 与 generation，客户端丢弃过期 generation 的响应；界面是否显示模型身份由 modelIdentityVisibility 控制，另有开关 hatch_big_boy_models。模型名称在静态包里被抹掉，只剩选择机制。技能（skills.list）带 entryPoint、authType、OAuth 流程，可 set_disabled；自定义连接器 custom_connectors.register 另成一类。

  3. 推理主代理与子代理分 lane 输出全自动

    lane 枚举：main、subagent、critical、normal。子代理产出标 isBackground，界面上有 "Subagent reasoning" 折叠区。五个协作人设模板（Strategist / Researcher / Builder / Critic / Synthesizer）是现成的多角色分工脚本，推断用于共享 agent 或 "flock" 场景（路由里有 hatch.flock）。

  4. 工具按工具类型路由到三种后端全自动

    服务端：tool.exec（审批图标为地球，推断为带网络的执行环境）、tool.web_fetch、tool.imagine、tool.zeitgeist（文档搜索类）。VM 浏览器：browser.lease 租用，browser_task.* 管理生命周期（heartbeat、present、takeover、refresh_environment、clipboard）。节点：nodes.sync 同步能力，nodes.invoke_ack / invoke_result 回执；web 客户端注册 device_commands 与 hatch_app_commands 后同样可被调用。

    接管：control_owner 可在 agent 与 user 间切换，用户可随时 browser_task.takeover 接管 VM 浏览器，再交还。

  5. 审批需要授权时暂停，等人决定人 ①

    决策枚举：allow_once / allow_always / allow_session / deny / deny_always / ask / never / auto_allow。审批对象覆盖连接器动作、文件系统读写、电脑控制、单个工件、单个想法、Feed、单个定时任务的 web 访问。详见第 06 节。

  6. 压缩轮次之间做上下文压缩并通知界面全自动

    delta.compaction_start / compaction_done 携带 phase 与 reason；带 compaction 的消息在界面上作为分隔，不可反应。推断：压缩结果与记忆系统相关（"Summarize into memory" 是显式动作，自动压缩是否写记忆未知）。

  7. 收尾turn_done 后更新活动、目标与通知全自动

    activity.* 记录动作并可按目标过滤；goals.suggestions.decide 让用户接受或拒绝 agent 对目标的建议；notifications.foreground/background/border 区分提醒方式；chat.unread_count 更新角标。

运行时的每一步都可能被拦下来。↓　拦截点在哪里，规则怎么存？

06审批与出网管控

两套机制叠加：面向动作的 HITL 审批，和面向网络的 sentinel 服务。

HITL 审批

approvals.* · 决策与作用域
  • 决策：allow_once / allow_always / allow_session / deny / deny_always / ask / never / auto_allow；另有 accepted / dismissed 作为卡片状态。
  • 作用域（文案）：单个连接器动作、连接器写权限整体、文件系统读 / 写、电脑控制（对整台 Mac）、单个工件、单个想法、Feed、单个定时任务。
  • 持久性："Always allow has no time limit"；改变连接器写权限会清空已保存的动作审批。
  • 可编辑：egress.approval.editable_message / edit_message 允许用户修改 agent 将要发出的内容再批准。
  • 历史：approvals.history、approvals.snapshot；本机侧超时未答不重试。
  • 内部开关：EndoNodeAllowAllHITLGating、is_tool_mocking_enabled_for_hatch、redteam mocks，发布版是否可达未知。

sentinel 出网

service: sentinel · /permissions/*
  • 透明代理：permissions/tproxy、permissions/mitm、permissions/sni-rejection、permissions/network-rules，即 VM 出站流量被透明代理，可做 TLS 中间人与按 SNI 拒绝。
  • 作用域权限：/permissions/scopes/{scope_type}/{scope_id}，按连接器 /permissions/connectors/{connector} 单独设置并可重置。
  • HITL 节流：permissions/hitl 与 snooze 删除；"residential egress override" 让浏览器任务在未获住宅出口授权时失败。
  • 审批流：/approvals 列表 → decide；文案 "{assistant} wants to share information with {domain} for {scheduledTask}" 说明按域名 + 任务粒度审批。
  • revoke / reset：一键撤销或重置全部出网权限。
设计意图推断：把"agent 想访问哪个域名、为了哪个任务"做成和"agent 想删哪个文件"同级的审批对象，是这套系统把网络副作用纳入 HITL 的方式；MITM 能力意味着 sentinel 可以看到明文请求，这既是审计基础也是隐私边界。
动作和网络都管住了。↓　agent 产出的东西放在哪里，用户的文件又怎么进来？

07文件系统与文件管理

两套文件系统、一套版本化、一个导出通道。VM 家目录就是 agent 的"硬盘"。

能力接口说明
读文件fs.read / fs.reads（批量）· fs.raw/{*path}raw 走 media 通道、无响应大小上限，用于图片视频直出；thumbnail 单独接口。
写文件fs.write · files.create_file · files.savepeers 的 discretion.write 复用 /fs/write，说明 peer 相关状态也以文件存放。
实时性fs.subscribe → fs.updated、files.updated、library.fs_event资料库与文件查看器按事件增量刷新，不轮询。
版本化git.log · git.show_file工作区有 git 历史，可回看某文件某版本；是否自动提交未知。
导出fs.export {path, format:pdf} · document.pdf · dyi.export单文件导 PDF；dyi（Download Your Information）整体导出。
加密盘vault.luks_status（/luks/status）机密 VM 的数据盘用 LUKS 加密，PIN 对应解锁。
运维入口ssh.operator.enable/disable · /hatch/ssh-access/tokens可为"operator"开启 SSH；operator 是用户还是 Meta 支持人员，静态不可判。
小结：文件管理的设计重心不在"管理"而在"让所有产出都是文件"，这样搜索、分享、导出、版本回溯都能用同一套 fs 接口完成。
文件系统是底座。↓　资料库就是它的几种视图，加上工件和 Spaces 这两种"活"的文件。

08资料库与工件

资料库路由 /library/* 共八个分区；数据全部来自 fs.library {preset, limit, offset} 的分页查询，所以它是文件系统上的视图而非独立存储。

分区路由 / 数据源内容与能力
Recent/library/recent · library.sidebar.root最近项目；navigation.recents.touch 记录访问。
Artifacts/library/artifacts · fs.library preset=artifacts · artifacts.*agent 生成的可交互产物。list / pin / share / remove / fetch_url / snapshot / subscribe；"Web artifacts" 子类；删除会移除整个工件文件夹及其媒体；分享生成公开链接，部分 VM 不支持。
Documents/library/documents文档类工件；可导出 PDF（document.pdf）；原生包里带 markdown-editor.html 编辑器。
Files/library/files · fs.list 文件浏览器对应 workspace/your_files；支持 files.dialog.save 存回 Mac。
Media/library/media · fs.library preset=media照片与视频，走 raw/thumbnail 通道；library.media.previews。
Podcasts/library/podcasts · podcasts.*agent 生成的个人播客："Create a podcast"、发布到 RSS 订阅源（公开链接，可加到 Apple Podcasts）。
Slideshatch.library.slides · artifacts.slides.rebuild幻灯片工件，可重建为 pptx（180 秒超时）并在内置查看器播放。
Spaceshatch.library.spaces · /spaces/v2 · saved_space见下卡。
小结：Artifacts 是"静态产物"，Spaces 是"带服务端逻辑的产物"，Podcasts 是"定期生成的产物"，三者都落在同一棵文件树上。

Spaces 的实现形态

/spaces/v2/{slug} · /spaces/cvm/{slug}/…

一个 Space 由 slug 标识，可 save（存为 saved_space）、delete、export_html（导出单文件 HTML）。渲染走 spaces.cvm.render（GET 根路径）与 spaces.cvm.get / post {*subpath}，即 Space 的页面和后端请求都由 VM 内进程响应。

调试接口 debug/summary · invocations · invocations/{id} · log 表明每次请求是一次"invocation"，有日志可查。分享有独立审核流：share/review → share → settings / fix，并可 unshare；文案里有 Cloudflare 共享帧 URL（cloudflare-shared-space-frame-url），推断公开分享经 Cloudflare 托管。

原生侧 EndoSpaceWebView 以独立 scheme 加载，阻止无用户手势的外部打开；Space 可请求 Mac 文件（"A Space wants to use files from your Mac"）。

工件的生命周期

artifact.build_thread · artifact.use · hatch.artifact.*

路由追踪里有 hatch.artifact.load、artifact.runtime_signal、artifact.rewrite，说明工件有加载、运行时信号与改写三个阶段；artifacts.subscribe 推送变更。

在共享 agent 的能力授权里，artifact.use 对应 "Use shared apps"，artifact.build_thread 对应 "Build apps together"，即工件可以被另一个 agent 使用或与之协作构建。

web 包内置 LSP 客户端（workspace/* 方法、诊断、语义着色），推断用于在工件编辑器里提供代码智能。

09记忆系统

记忆不是向量库黑盒，而是用户可直接打开、编辑、搜索的 Markdown 文件，外加一组维护接口。

形态

/MEMORY.md + 记忆条目路径

Activity/Status 面板上有一张 "MEMORY · ACCESS WITH CARE" 文件卡，点击打开 /MEMORY.md；ui.navigate.memory.item {path} 打开某个记忆路径，说明除根文件外还有按路径组织的条目（"Memory entry"）。

读写

memory.* 四个接口 + 三个显式动作

memory.search、memory.get、memory.consolidate（合并）、memory.reindex（重建索引）。界面动作："Add memory"、"Import memory"、"Summarize into memory"（把当前对话总结进记忆）。

边界

共享与隔离

向共享 agent 共享记忆要逐条挑选（"Choose specific memories to share"），对应能力 memory.query（"Look up memories"）。重置 VM 会永久删除记忆；机密 VM 下记忆落在 LUKS 加密盘。

与压缩的关系（推断）：上下文压缩（compaction）和记忆写入是两条线：前者是服务端自动的、按轮次的；后者有显式的"总结进记忆"动作。reindex 的存在说明搜索基于某种索引（可能是向量或全文），但索引本身不是真相源，文件才是。
一个人的 agent 讲完了。↓　它如何被拆出一部分给别人，或和别人的 agent 对话？

10共享 Agent 与 Peers

两种"多人"设计：把自己 agent 的一个作用域版本给别人（Shared Agent），或让两个人的 agent 互相投递（Peers）。

Shared Agent

shared_agents.* · 定义页 · 私有侧聊
  • 定义："A Shared Agent is a scoped version of your assistant with its own private side chat"。创建时不带任何私有内容，之后在定义页逐项加入：对话上下文（主聊有界副本或指定线程）、知识（文件、工件、记忆）、目标、Spaces、连接器 / 技能 / 凭据描述符（"Raw secret values are never included"）。
  • 身份：名称、角色、头像、强调色、指令（identity.update 与 definition.update 分开）。
  • 能力授权：chat.send、chat.read_history、artifact.use、file.read、file.share、memory.query、artifact.build_thread、cron.create、cron.list、tool.execute，各有人话标签。
  • 分享：shares.create / list / revoke，每个分享有自己的对话（shares/{id}/conversation）；接收方通过 /hatch/shared-agents/claim 领取，再用 remote.open / remote.send 与之对话（connectionClass 为 shared_agent）。
  • 侧聊：创建即生成一个 owner-only 侧聊，"automatically includes its current-epoch recent messages"。

Peers（可信网络）

peers.* · SAS 验证 · 收件箱
  • 建立关系：invites.create / open / accept / revoke，落地页 /peer/accept；请求阶段有 requests.sas 与 sas.confirm，即短认证串（SAS）人工比对，典型的端到端密钥验证做法。
  • 关系版本：断开要带 relationship_generation_id / revision / started_at，说明关系有代际与修订号，防止旧状态回放。
  • 投递：inbox.deliver / list / decline，peer 的消息进入收件箱，由本人 agent 决定如何处理；reset_conversation 可清空与某 peer 的对话。
  • 可见性：peers.update、discretion.write（复用 fs.write）控制向对方披露什么；头像照片按 sha256 取。
  • 来源：/hatch/trusted-network/contacts 从联系人里找可邀请的人。

渠道与多角色

channels.* · 五个人设模板

channels.link / status / unlink 与 WhatsApp / Messenger / Telegram companion（whatsapp_companion.link、messenger_companion.unlock）把 IM 变成和自己 agent 对话的入口。五个人设模板（Strategist、Researcher、Builder、Critic、Synthesizer）各自一句定位，推断用于让多个 agent 实例围绕一个议题分工讨论（路由里的 hatch.flock 可能是其载体）。
