中文总结架构边界持久执行项目对照
中文核心概括

Agent 的规模化不只是增加沙箱。运行时、状态、交付、凭据和计算机应分别管理；模型越强，验证、存储与资源调度越可能成为瓶颈。

01 / 原文观点译述

先分开扩展边界

运行时与计算机

运行时负责推进任务，计算机作为按需资源。

状态与进程

持久记录保存工作事实，进程可替换。

执行与授权

先提交行动声明，再执行；凭据隔离与授权分别处理。

能力与系统容量

扩展对象还包括交付、验证、存储与外部影响。

以上为压缩后的中文译述，不是逐句全文翻译。组件划分与实现描述均来自作者自述。

03 / 我们的独立解读

最值得带走的，是故障边界

我的理解是，应把“什么东西坏了以后，哪部分工作还能继续”作为设计问题。进程、工具沙箱和浏览器是三种独立的故障来源；一种组件的恢复不能替代另外两种。

进程可以替换

替换前必须有可读的任务进度和归属记录。否则新进程虽已启动，却不知道旧进程做到哪里。

执行资源可以重建

需要区分已确认文件、运行中的命令与外部副作用。文件检查点完整，不代表一个付款或发布命令可以重新执行。

客户端可以断开

用户关闭页面，应只改变观看方式。任务是否继续、取消是否送达、结果是否仍可读取，要由系统明确管理。

承诺需要分层

“请求已接收”“工作已交付”“结果已提交”应是不同状态。界面不能把最早的一次成功响应当成最终完成。

一个用于理解的故障例子

假设工具已把发布文件上传成功，但执行进程在保存结果前退出。直接重新发布可能重复产生副作用，直接标记失败又可能误导用户。我们需要保存行动身份、查询外部结果并协调未知状态。这是本文阅读后提出的工程检查例子，不是 Tetral 已完成的验收案例。

05 / 我们建议的验证顺序

下一步优先验证可恢复任务

下面是本文阅读后提出的实验建议，没有在本次执行，也不要求立即引入另一套编排框架。

  1. 明确接收边界。任务有稳定 ID，接收后能查到内容、当前状态和责任方。
  2. 记录关键进度。在模型请求前后、工具执行前后保留可协调的事实，区分执行失败与结果未知。
  3. 做一次故障注入。在工具执行成功但结果尚未确认时停掉测试运行时，检查恢复时是否重复执行。
  4. 检查取消与交付。断开页面、取消任务、替换工作进程，核对队列、远端命令与可见状态是否一致。
  5. 最后测容量。同时观察任务等待、模型连接、沙箱启动、磁盘和构建验证开销，避免只统计 VM 数量。
选择架构之前，先用一个真实业务闭环说明：任务在哪里接收，进度在哪里保存，资源由谁分配，未知结果由谁核对。
06 / 阅读与证据

把观点、实现自述与验收分开

本文将原文压缩为中文摘要，后半部分是我们对当前项目的独立解读。我们没有部署 Tetral，也没有验证它的吞吐、恢复或授权机制。作者的产品方向不能直接当作我们或其系统已经通过的生产验收。

如果继续阅读原文，可以围绕三个问题做笔记：行动如何取得稳定身份；任务完成依据什么记录判断；运行资源失去时如何区分重试与协调。这些问题也适用于我们自己的实现。
