一个 harness 进程能扛多少同时在对话的用户

工具沙箱分离（A/B 分离）场景下，把共享宿主（harness A）单独放在 220，其余全部放在 118，用真实模型 MiniMax-M3.1-Flash、真实链路（主助手 → 委派数字员工 → 在用户自己的工具沙箱 B 上执行 bash）压测。先测出原始上限，剖析主线程，做了三处优化，再测一遍，并用 7 个代码和文件用例做了优化前后的功能对照。最后单独压测了 openGauss 会话库（写入容量、单用户大量会话、与 BE 混合负载），以及 harness 能承载的 WebSocket 长连接数。

结论
单个 harness 进程从约 10–12 人 同时活跃，提升到 50 人 全部可用，主线程还剩约 20% 余量

优化前：瓶颈是 harness 的单个主线程。10 人时主线程空闲只有 0.8%，15 人时首词 p50 变成 18 s，20 人时 43% 的轮次超时。根因是 DSH 里两段"一个进程一个用户"的写法：每查一个工具就重建整张工具表；委派工具放在全进程共享的集合里，每一步遍历所有用户的定义。

优化后（分支 perf/harness-single-thread，3 个提交，未推送）：10 人时主线程空闲 71%；50 人并发 97/100 轮成功，第 2 轮起 50/50 成功，稳态首词 p50 8.6 s；功能回归 7 个用例结果与优化前一致。

还没到真正上限：50 人以上没测，卡在支撑机 118 的内存（50 个工具沙箱后只剩 1.8 GB）。另外发现 BE 死锁、平台沙箱上限 30、Node 默认堆过小、分离模式下 grep/glob 不可用等问题，详见第 12 节。

长连接：现在每条到工具沙箱的连接是一个 ssh 进程加一个 ws-proxy 进程，实测每条约 14 MB，500 条时延迟和 CPU 都正常，上限由内存决定；同样的连接放在一个 Node 进程里只要约 40 KB/条，单进程实测 3.3 万条。还发现每断开一条连接留下一个僵尸进程，已在分支修复（详见第 11 节）。

会话库不是瓶颈：openGauss 单机（8 核测试机）在 4000 个会话同时写入时 p99 88 ms，拐点在 4000–5000 个会话，约合 6000–7000 个活跃用户；一个用户 2 万个会话时列表与恢复仍在百毫秒级。同一个库上，每个活跃用户在 BE 侧的开销约是会话写入的 14 倍，先压满数据库的会是 BE（详见第 10 节）。

02测试目标与范围

回答一个问题：harness 和工具沙箱分离后，一个 harness 进程最多能承载多少同时在对话、并且都要用工具沙箱的用户；瓶颈在哪里。

在范围内

本次测了
  • 单个共享宿主进程的并发承载：5–50 人同时活跃
  • 首词、整轮耗时、工具往返，以及 BE / harness / 模型各占多少
  • harness 的 CPU、内存，常驻用户数上限，冷启动
  • openGauss 会话库：写入容量、单用户大量会话的写入与读取、与 BE 的混合负载
  • WebSocket 长连接：现有形态下一个 harness 能持有的到工具沙箱的连接数，以及连接放进同一进程时的上限
  • 主线程 CPU 剖析，以及针对热点的三项优化
  • 代码和文件类功能在优化前后是否一致

不在范围内

本次没测
  • 多个 harness 进程 / 宿主池（BE 目前只能指向一个宿主）
  • 30–60 分钟长稳（单段压测都在 10 分钟以内）
  • 50 人以上（支撑机内存不够放更多工具沙箱）
  • 浏览器、Unity 等其他工具沙箱能力
  • 线上 ACS / ALB / NAS 环境（229 只读，未动）

04测试方法

真实链路、真实模型；每段压测控制在 10 分钟以内，压测前先预热常驻用户；同一组指标在优化前后各测一遍。

负载

每个虚拟用户的一轮对话

发送：用 bash 执行 hostname && date，然后用一句话告诉我结果。

主助手是路由，没有 bash，会查资源、实例化数字员工；员工在该用户的工具沙箱 B 上执行 bash，再回报。每轮 2–12 次工具调用、2 层 agent，整轮 30–100 s。这是真实业务路径，不是简化负载。

每段 N 个用户同时开始（间隔 150–500 ms 错开），每人连续 2 轮（5 人档 3 轮），轮间隔 5 s，单轮超时 240 s。

06原因分析

在 10 人并发负载下，对运行中的宿主主线程做 150 s CPU 剖析。主线程几乎没有空闲，时间主要花在拼系统提示词和垃圾回收上。

① 查一个工具，重建整张表

DSH core/tools ToolRegistry.get

get(name, scope) 的实现是 this.view(scope).visible.get(name)：每查一个名字，都把作用域链上所有工具复制进新的 Map、逐个检查过滤规则。拼提示词时每个委派工具都会查一次，每一步都在做。占主线程约四分之一，并制造大量垃圾。

② 委派工具全进程遍历

DSH tool-subagent delegationTools

delegationTools 是模块级集合，共享宿主上装着所有用户、所有 agent 的委派工具定义。提示词里的委派段落每一步都对集合里每个定义经 cordis 代理调用一次 tools.get，耗时随进程内 agent 总数增长 —— 用户越多越慢。DSH 默认一个进程只服务一个用户，所以原来不明显。

③ 运行时参数

Node 22 默认值

默认堆约 2 GB，常驻 25 人左右溢出。AsyncLocalStorage 在 Node 22 上基于 async_hooks，每个 Promise 都有开销（约 14%）；新生代空间小，频繁的短命对象导致垃圾回收占比高。

07优化内容

分支 perf/harness-single-thread（基于 origin/D0.6.0，未推送）。两个 DSH 补丁沿用仓库已有的 0.2.1 构建期补丁方式：打镜像时对 DSH 源码做精确文本替换后重新编译，三个 Dockerfile（Dockerfile、Dockerfile.slim、Dockerfile.extensions）都已接入；源码与上游不一致时构建直接失败。

提交改什么文件结果等价性的验证

10会话库（openGauss）压测

单独回答三个问题：会话写入能撑多少活跃用户；一个用户有大量会话时写入和读取会不会变慢；BE 和会话共用一个库时谁先到上限。

方法

被测对象118 上的 openGauss 6.0.3（8 vCPU / 14.8 GB 共享机、单块云盘，shared_buffers 1 GB，max_connections 200）。写入单独的 sdb_load schema，不碰业务表；测完已删表。
数据今天压测中真实产生的会话（含委派子会话），从库里导出：2272 个会话、91,497 条事件，平均每条 2.9 KB。随机抽 30%（724 个会话、29,639 条，平均 3.0 KB，p99 72 KB），分布与全量一致。

12发现的问题

都会挡住更大规模的使用，与本次优化无关（第 3 条已由优化处理）。

  1. BE 死锁：卡死聊天线程，最终所有人收不到回复BE严重

    现象：用户上下文冷启动超过 60 s 后，BE 的 8 个聊天线程有 7 个卡在 SessionService.save 等数据库；openGauss 里 7 对一一对应的 "idle in transaction" 持锁连接和阻塞的 INSERT INTO byai_session。之后所有用户（包括已就绪的）都收不到回复，客户端也看不到错误。

    原因：聊天异常处理 ScriptService.saveExceptionRequiresNew 用新事务再写一次会话，而外层事务已插入同一行且未提交，两个连接互相等待，数据库检测不到。

    处置：测试中杀掉持锁连接恢复；之后改为压测前逐个预热，避免触发。建议：异常路径不要在新事务里重写外层未提交的会话行。

  2. 平台全局最多 30 个运行中沙箱平台配置高

    系统参数 ENABLE_USE_SANDBOX_NUM=30（从 229 复制）。超过后工具沙箱启动报 "Business access is busy"，插件每 3 s 重试，最多 19 次。每人一个 B 的话，这个值直接限制总人数。测试中改为 200；建议确认 229/线上的取值。

  3. Node 默认堆约 2 GB：约 25 个常驻用户时宿主崩溃harness已在分支处理

    提交 d4e65d6fc 默认 8 GB。部署注意：堆上限要与宿主容器内存匹配，容器内存更小时会先被容器杀掉。

  4. 分离模式下 grep / glob 每次失败harness / B 镜像中

    报 ripgrep provider failure。DSH 解析的是 A 本地打包的 rg 路径 /workspace/node_modules/.pnpm/@vscode+ripgrep-linux-x64@1.18.0/…/bin/rg，却在 B 上执行，B 上没有这个文件（B 自带 /usr/bin/rg）。模型会退回用 bash 搜索，结果通常仍对，但多绕几步。建议：B 镜像在同一路径放 rg，或 tool-env 插件把 rg 指到 B 的 /usr/bin/rg。

  5. 冷启动互相拖慢，超过 60 s 时消息静默丢失harness + BE中

    10 个同时冷启动每个 245–251 s；BE 等待就绪只等 60 s，而对宿主的 PUT 超时是 100 s；超时后客户端收不到错误。BE 的就绪检查走一个实际只有 4 个线程的启动线程池，所有 DSH 消息都要经过它。

  6. openGauss 唯一 SQL 统计放大写入延迟数据库配置 / 插件中

    instr_unique_sql_count 调大到 5000 时，会话写入在 3000 个会话时的 p99 从 57 ms 变为 474 ms，饱和吞吐从约 1800 降到约 1200 事务/秒。原因是插件批量插入的 VALUES 行数不固定，每种行数都算一条唯一 SQL。建议：生产保持默认 100；或把插件的批量写入改成固定形状（例如数组参数一次插入）。

  7. openGauss 容器没有内存上限，内存不足时被内核杀掉部署中

    第一次混合压测时，118 上同时有 50 个工具沙箱、BE、数据库和发压容器，整机内存耗尽，内核杀掉 gaussdb，约 13 s 后自动重启。期间 50 人聊天变慢但全部完成，220 上的宿主没有崩溃（会话库插件对断连的处理有效）。这是测试布置导致的；建议生产给数据库预留内存或设上限，不与沙箱混部。

  8. 每断开一条到工具沙箱的连接留下一个僵尸进程harness 镜像已在分支修复

    Node 当 1 号进程不回收被过继的 ws-proxy；B 空闲释放后连接断开，僵尸持续增加，最终耗尽进程号。229 的宿主容器同样没开 --init。提交 9e6e5f926 用 byclaw-pid1 修复，见第 11 节。

  9. 每条工具沙箱连接要两个进程、约 14 MBharness / tool-env中

    ssh 主连接 + 独立的 ws-proxy Node 进程。50 人规模没问题，但连接上千时内存线性增长；连接放进同一进程只要约 40 KB/条。另外镜像里的 ws-proxy 是旧版（Node 自带 WebSocket、地址作参数），与分支上的新版不同。

  10. BE 以 DEBUG 级别记录每条 SQL（含聊天内容）；建会话就要 2.5–3.7 sBE低

    日志量大、排查困难；BE 转发是优化后首词里最大的一段。

13局限性

  • 没做长稳：每段压测不超过 10 分钟（执行环境限制），没有 30–60 分钟的内存泄漏和连接泄漏观察。
  • 50 人以上没实测：118 放不下更多工具沙箱；单进程约 60 人是根据 50 人时剩余 22.7% 主线程空闲推算的。
  • 只有一种负载：主助手 → 员工 → bash。模型行为有随机性，每轮工具调用 2–12 次不等，整轮耗时方差大。
  • 与线上的差异：B 跑在 opensandbox（Docker）而非 ACS；A→B 经 nginx 代替 ALB；A 与 B 不共享磁盘（229 上共享 NAS）；BE 单实例在 118 上与数据库共用 8 核。
  • 失败分类：ask_user_question 导致的超时是模型在等用户回答，不计为系统故障；委派员工 240 s 内未回报的计为失败。
  • 会话库数值只代表这台测试机：118 是 8 核共享机、单块云盘，数据库与 BE、平台、发压进程共用 CPU；生产规格不同时需按 CPU 和磁盘换算。会话库回放用的是 30% 抽样语料（与全量分布一致）。
  • 长连接测试的 B 是替身：一个容器承接全部连接，B 侧用回显程序代替 DSH helper，所以只衡量 harness 一侧的开销；进程内方案测的是 WebSocket 本身，没有叠加 ssh 加密。
  • BE 的数据库负载是推算的：只能实测 50 人真实聊天的 BE 负载；"BE 先压满库"的用户数是按每用户 CPU 线性外推，没有实测。
  • 第 1 轮数据含测试方式的影响：所有用户同时登录 + 工具沙箱一起冷启动，所以稳态（第 2 轮起）更能反映 harness 本身。

14结论与下一步

结论
一个 harness 进程：优化前约 10–12 人，优化后 50 人实测可用，主线程还有约 20% 余量

优化前的瓶颈是 DSH 在共享宿主场景下的两段 O(全进程) 写法和 Node 运行时默认值；修掉后 harness 不再是首先碰顶的部分，接下来是支撑侧（B 的内存、BE CPU、BE 建会话耗时）和模型首字的尾部。

会话日志存 openGauss 的写入容量约 6000–7000 个活跃用户（8 核测试机），远大于 harness 侧的需求；单用户大量会话不是问题。共用一个库时，BE 的数据库开销才是先碰顶的部分。

要撑 100 人同时活跃

按本次数据推算
  • harness：2 个优化后的进程（每个约 50 人），或进一步优化后 1–2 个；需要宿主池（BE 按用户分配宿主，已有 PRD，未实现）。内存参考本次实测：50 个常驻、50 人同时活跃时宿主容器约 7.0 GB。
  • 工具沙箱：100 × 约 80 MB ≈ 8 GB 起，另一台机器或线上 ACS；平台沙箱上限要大于 100。
  • BE：先修死锁；就绪等待与冷启动时间对齐或登录预热；启动线程池放大；看 BE 建会话的耗时。
  • 长连接：3 倍连接数在 50 人规模下按现在的形态够用（约多 2 GB）；先合入僵尸修复。客户端接入后连接若到上千条，改为在 harness 进程内持有连接（每条约 40 KB），并确认 ALB 连接上限与本地端口范围。
  • 数据库：会话写入在 100 人时只用到容量的约 1–2%，不需要为它扩容；要关注的是 BE 的数据库开销（约为会话的 14 倍）。保持 instr_unique_sql_count 默认值，给数据库预留内存。
