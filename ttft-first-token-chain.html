一句话
首 token 前的耗时分两类：每轮都有的轮询与批处理，以及冷启动。

热路径：轮询、批处理和串行远程调用，叠加起来从几百毫秒到约 2.4 秒。其中最大的一块是 Harness 收取命令时的轮转阻塞读，最多空等 2 秒，平均约 0.5 秒。

冷路径：工具沙箱 B、Harness A 或共享池需要启动时，首 token 会被拖到几十秒。B 在空闲 300 秒后断开，下一轮必须等它重新起来，因为这一轮要从 B 读指令文件和 Skills。

先看这一句话从浏览器出发，要经过哪些地方。↓　FE → BE → Harness（A）→ 工具沙箱（B）→ 模型 → 原路返回

02整条链路

五条泳道，十个步骤。去程走 Redis 控制流，回程走会话数据流；全程只有 FE↔BE 一段是 WebSocket。

图上每个框背后都有具体代码。↓　逐段说明做了什么、在哪里、可能卡多久。

03逐段走查

高亮的三步是耗时热点。路径简写：FE = byclaw-fe/src/，BE = byclaw-be/…/byai/，INT = middleware/byclaw-harness/plugins/byclaw-integration/src/，FW = vendored by-framework 1.7.0 包。

  1. FE点发送，写一帧 LLM_MESSAGE通常 ≈0

    queryInputBase.tsx:494 → useChat/index.ts:1053 sendQuery → useSseSender/useSend.ts:57。全局 WebSocket 在登录和布局挂载时就已建好，发送时不再握手；会话也不由前端创建，新会话由服务端回 createSession 事件。

    会变慢的情况：构建开关 PERSONAL_STORAGE_ADMISSION_ENABLED 打开时，每次发送前同步请求 /storage/personal/readiness，没就绪就轮询（15s 起，退避到 60s）；WS 断开时最多等 10s 重连；会话停在历史分页时，先整页重载再重发。

  2. BE接收与准备参数数十毫秒级

    WebSocketHandler.java:113 → ChatService.llmChat（额度）→ AssistantChatService.chat:190：平台 storage/quota-check 远程调用（:214）、默认助手和员工查库、新会话写库；ScriptService.prepareParams 推 initialization 给前端，用户消息异步写库，ParamService.getParams 查员工和技能。

    历史和记忆不在 BE 组装，只把会话引用传给 Harness。

  3. BE路由与就绪检查热点

    RouteService.java:173：resolveTarget + ensureWorkerReadyBeforeFirstSend，共用一个默认 60s 的时限。目标是 BYCLAW_DSH_<user>；共享池用户每轮都调 SharedSandboxGateway.tryAcquire，而且调了两遍，最多 2–6 次串行平台 HTTP 调用。worker 在线就直接走。

    冷启动：worker 离线时同步拉起（平台 launch 或向共享 host PUT /v1/users/{user}，请求超时 100s），然后每 100ms 查一次 Redis 注册表，最长 60s。派发失败会重启并等 5×60s。这些都跑在核心线程只有 4 个的 sandboxStartupExecutor 上，热请求可能排在冷启动后面。

  4. BE派发到 Harness一次 XADD

    sendMessageWithWorkerRetry 组装载荷（新签的 JWT、runtimeType=dsh、cwd、模型、群聊引用），通过 by-framework 写到 byai_gateway:ctrl:agent_type:BYCLAW_DSH_<user>。派发前先建好回程消费组和会话锁。

  5. Harness A收取命令、打开会话热点

    FW runner.ts:530 poll()：先对每个流做一次非阻塞读，都空的话只对其中一个流做 BLOCK 2000，按轮转选。worker 监听 BYCLAW_DSH 和 BYCLAW_DSH_<user> 两个流（INT index.ts:396），BE 只写后一个，所以有一半概率阻塞在错的流上（见图 2）。

    读到后：执行记录读写 → sessions.ask → findPending → 同一用户同一会话排队 → handleFor 复用内存会话，否则从 A 的磁盘重放事件日志恢复，或新建。

  6. Harness A ↔ B组装本轮：模型配置、setup、指令文件与 Skills热点

    模型配置每轮都读 Redis，不缓存（model-runtime.ts:1060）；复用会话时 sessionSetup 也每轮重跑（session-runtime.ts:2451）。然后 DSH 通过 SSH 从 B 读 AGENTS.md 和 Skills，读完才发模型请求。

    B 没连上时（dsh-tool-env/src/connection.ts:104-115，日志 tool environment start requested by）：BE 申请或拉起 B（60s 重试窗口，每 3s 一次）→ 每 500ms 探活（最长 180s）→ SSH 握手 → 回放积压的操作。B 空闲 300s 后断开（BYCLAW_TOOL_ENV_IDLE_MS），下一轮从头再来。B 不可达时会删掉重建，最坏约 2×(60+180)s。

  7. 模型流式请求，等首包取决于模型服务

    供应商和模型来自 Redis 记录，HTTP 走 undici（model-fetch.ts）。首包处理在 DSH 内核的 agentLoop 里，本次没有细读。

  8. Harness A攒批写回 Redis≤80ms

    TimedChunkBatcher（session-runtime.ts:254）攒够 96 个字符或等满 80ms 才发；每块一次 XADD + EXPIRE 到 session:<sid>:data_stream。思考和正文分别攒批。

  9. BE消费回程流，推给前端≤270ms

    ReactiveSessionStreamReceiver.java:126 非阻塞 XREADGROUP，空闲时等待从 5ms 翻倍到 250ms 封顶；拿到后再等 20ms 攒批（RedisStreamMessageListener.java:87），然后逐条 writeAndFlush 到 WS。模型想了好几秒才出首包时，首包很可能正好碰上 250ms 的空档。

  10. FE应用事件，显示第一段文字≤30ms

    CHAT_STREAM → chatRuntime.ts:619 → 首个 reasoningLogDelta（思考面板）或 answerDelta（正文）。非终止事件合并 30ms 再刷（chatRuntime.ts:42），然后 redux 深合并整条消息。首 token 之前前端只显示本地转圈，没有“正在准备沙箱”的状态。

把十步按“每轮都有”和“冷启动才有”拆开。↓　热路径看毫秒，冷路径看秒。

05三个优先嫌疑

第 2 点我已经对照框架源码核实过；第 1、3 点的机制在代码里清楚，量级要实测。

① B 冷启动在首 token 前

秒级到几十秒 · 冷路径

这一轮要从 B 读指令文件和 Skills，B 没连上就先启动它。B 空闲 300s 断开，所以隔几分钟再聊的第一句话最容易慢。可选方向：把指令文件和 Skills 在 A 侧缓存，或把 B 的启动移出模型请求的关键路径。

② 收取命令的轮转阻塞读

≤2s，平均约 0.5s · 每轮

worker 监听两个流，BE 只写 BYCLAW_DSH_<user>，但阻塞读在两个流之间轮换。阻塞在 BYCLAW_DSH 上时，新消息要等 2s 超时才被读到。只改框架一处（一次 XREADGROUP 同时 BLOCK 多个流）就能稳定省掉。

③ 共享池的串行平台调用

每轮 2–6 次 HTTP · 并发放大

tryAcquire 在路由和就绪检查里各调一次，而且跑在只有 4 个核心线程的启动池上。有人在冷启动时，热用户的请求也会排队。可选方向：一轮内复用结果，热请求不进启动池。

以上都是读代码得出的上限。↓　现有打点已经能把链路切开，按 requestId 串起来就能拿到实测分布。
