01 / 原报告机制整理

总览：三层嵌套，一句话版本

物理机 → KVM + Cloud Hypervisor → VM → nspawn Cell（我在这里）→ hatch daemon / execd

第 1 层 · Cell 内
沙箱执行侧。只有 daemon + execd + 临时拉起的 Chromium / CLI。你的文件在 /home/hatch，根盘是 overlay、用完可销毁。无任何 TCP/UDP 监听。
第 2 层 · 同一 VM 的外层
Harness 的宿主侧：cell leader、spawnd、noded、peerd、Postgres、inference 代理、yolk / ingress、egress 代理。所有 /run/hatch/*.sock 的监听者都在这层。
第 3 层 · VM 之外
Meta 后端与模型服务。推理经 hatch-egress-proxy:3128 出去；会话状态在外层 Postgres，持久盘与 VM 解耦，所以 VM/Cell 重建不丢对话。
关键结论（本版新增证据）：租户粒度是 VM : 用户 = 1 : 1——VM 层整套管理脚本按单租户写死（见第 5 节），VM 内固定四件套：1 个 Cell、1 个 daemon、1 个 Postgres、1 块持久 home 盘；物理机 : VM 仍是多台 VM 共用一台宿主机。Cell 按用户 / home 分配，不是按会话。主聊天、侧边聊天、定时任务、子代理（~/workspace/agents/ 已有 350+ 工作区）共用同一个 Cell、同一个 daemon，靠 daemon 内部逻辑 + Postgres 里的 transcript 区分会话。更细的隔离在工具调用级：privsep 分 partially / fully isolated 两种。

03 / 原报告机制整理

Cloud Hypervisor 介绍

开源虚拟机监视器（VMM），跑在 KVM（或微软 MSHV）之上，用 Rust 基于 rust-vmm 组件库实现，最初由 Intel 发起，现属 Linux Foundation。定位是给云厂商跑现代云负载，不是通用模拟器。

只做 virtio
只提供半虚拟化设备，不模拟老硬件、没有传统 BIOS/legacy 那一套，仅 64 位。攻击面和启动路径都小得多。
小而快
设计目标：最小模拟、低延迟、低内存占用、小攻击面；支持 CPU / 内存 / PCI 热插拔与机器间迁移。
对比 QEMU
QEMU 大而全、什么硬件都能模拟；CH 只保留云场景需要的部分，所以轻得多——代价是不适合跑老旧/异构 guest。

在本环境中的证据：guest 内 DMI 直接写着 Cloud Hypervisor，VM 内核 Linux 7.0。它只负责最外层这台 VM，Cell 不是 CH 的概念，是 Hatch 在 VM 内部再套的一层。

04 / 原报告机制整理

Cell 是什么概念

Cell 是 Hatch 自己的隔离单元，本质是 systemd-nspawn 容器：在 systemd-machined 里注册为一台名为 htch-runtime 的 machine，用 machinectl 管理。

维度Cell 的做法（脚本/实测）
隔离独立 PID / mount / user namespace；自己的 systemd 做 PID 1；overlay 根盘；专属 veth（guest 侧 host0）
资源本 Cell 观察到 2 核 / 8GB 配置
生命周期宿主侧 systemd 服务 com.hatch.runtime-cell.service 驱动创建（完整链见 4.1）；spawnd 渲染脚本并排队 bootstrap；pre-start / post-start / stop 钩子；停止时先写 /run/hatch/ingress/runtime-cell-draining 让 ingress 摘流量，再销毁
可销毁可恢复Cell 一次性；状态全在外面——会话在 Postgres、home 在独立持久盘、另有 resume / hotset 交接，所以重建不丢对话
信任边界脚本明文称 daemon 的 socket 目录是 “cell-root-forgeable”：Cell 内 root 也被当作不可信；控制面状态放在宿主侧 root 所有的目录；再加 scopes 配置、宿主侧 tc 限流、出站强制走代理
网络入站：tc ingress 分类器由 spawnd 挂在 veth 的 HOST 侧，guest 碰不到。出站：全部经 hatch-egress-proxy:3128。Guest 内 ss 看不到任何 TCP 监听

4.1 Cell 怎么生出来：完整创建链

创建由宿主侧的 systemd 服务 com.hatch.runtime-cell.service 驱动，脚本都在 /opt/hatch/runtime-cell/。四步：

  1. 备根盘（ensure-rootfs.sh）：rootfs 放在宿主的 /var/lib/hatch-runtime/rootfs，镜像阶段已铺好。因 Cell 用 UID 映射（Cell 里的 root 在宿主是 uid 131072），脚本先用一个临时 nspawn 把根盘文件属主修正一遍。更新时用 .incoming 目录原子换入；pre-start 先做完整性检查——缺 shell、缺关键目录就触发 bootstrap 修复。
  2. 备挂载与网络（pre-start.sh）：把持久盘的 home 挂到位，建好 /run/hatch 共享目录与各 socket 目录，构建 egress 的 CA 信任库；并按这台 VM 的 channel，把 scoped skills 用 overlay 合并进 /opt/hatch/skills 的绑定源——不属于本 channel 的 skill 在 Cell 里根本不存在。
  3. 拉起 Cell（launch-daemon.sh）：核心只有一条命令（见下方代码块）。systemd-nspawn 负责创建全套 namespace（pid / mnt / net / user / ipc / uts），把 rootfs 挂为根、在新 pid namespace 里把 guest 的 systemd 拉成 PID 1，建 veth 对（宿主侧 ve-htch-runtime、Cell 侧 host0），把 /opt/hatch（只读）、/run/hatch、home bind 进去，并向宿主 machined 注册 machine。machinectl show 里的 Leader 就是 Cell 的 PID 1 在宿主侧的 PID（当前代 2168）。
  4. 就绪确认：Cell 写出 runtime-cell.ready 文件，宿主侧各脚本轮询它、并用 machinectl 确认 Leader 存在之后，才继续后续步骤。
systemd-nspawn --boot \
  --directory=$rootfs \
  --machine=htch-runtime \
  --private-users-ownership=map \
  ...   # bind /opt/hatch(只读) / /run/hatch / home；veth 网络

4.2 外层怎么往 Cell 里放进程：setns / nsenter

原理：namespace 不是墙，是视图。谁创建了它、谁有宿主 root，谁就能进。内核提供 setns() 系统调用：拿着目标 namespace 里任一进程的 PID，就能把自己迁进那组 namespace，之后 fork 出来的子进程就“生在 Cell 里”。反方向不行——Cell 的 root 在宿主只是 uid 131072 的普通用户，没有对应权限。宿主 root 攥着 Leader 的 PID，就等于攥着所有 namespace 的门把手。实测有三种进入方式：

方式机制与实证
① nsenter（脚本层）post-start.sh 用 nsenter --target $leader --net 进 Cell 的网络 namespace，给 host0 配地址、挂 tc；pre-start.sh 用 nsenter --target 1 --mount 在宿主侧做挂载。
② 二进制自己 setns（daemon / execd 的 anchor 模式）control-execd.sh 注释明文：execd 不用 nsenter 包装，它内部调 enter_runtime_cell_unsupervised——宿主侧父进程留作 systemd 的 MainPID（叫 anchor），fork 的子进程 setns 进 Cell、迁入 Cell 的 cgroup 后，再 exec 服务本体。
③ socket 激活跨界execd 的监听 fd 是宿主 systemd 先打开的，通过 LISTEN_FDS 协议在 exec 时传给进 Cell 的子进程——所以那个 socket 出生在宿主、干活在 Cell。

方式 ② 正好解释了前文两个怪现象：daemon / execd 在 Cell 里 PPID 为 0（父进程不在这个 namespace 里），且 Cell 内的 root 读不了它们的 /proc（它们带着宿主侧的信任级别，Cell 只能使用、不能检查或干预）。

入站流量被谁消费？

不在 Cell 进程空间里。ss -xlnp 中 sandbox-api/api.sock 等监听 socket 的属主一栏为空——监听进程在 Cell 的 PID namespace 之外。消费方是外层 runtime（daemon 启动参数 --runtime-cell-leader=2168 所指的 leader 一侧——此为当前代数值、随代次变化，含 noded、peerd）。Daemon 同时也是客户端：它与 proxy/inference.sock、telemetry.sock 有已建立连接，在消费外层的推理与遥测服务。

为什么截不到 daemon 消费的内容（实测三路全堵）：① strace 附加 → ptrace: Operation not permitted（ptrace_scope=1 + 跨 namespace）；② /proc/24（当前代 daemon）的 maps/environ/fd → Permission denied；③ unix socket 不走 guest 网络栈，没有抓包面，且 socket 目录无写权限。劫持控制通道本身就是隔离要防的事，不做。
05 / 原报告机制整理

VM 里面怎么管理 Cell，VM 常驻什么服务

分工一句话：VM 层管托管，Cell 管隔离。VM 层（主机名 htch-runtime 的外层系统）负责 Cell 的生老病死、网络出入口、状态持久化与凭据；Cell 只是被托管的执行沙箱，关机即弃，状态不落在 Cell 里。

单租户证据（脚本明文）：整套管理脚本按“一个 VM 只服务一个用户”写死，没有任何多租户分片参数——① control-daemon.sh（VM 层、root 运行）全程只管一个 daemon，生命周期标记是 /run/hatch/daemon-ctl/ 下的单例文件，没有循环、没有 daemon 列表、没有按用户 / Cell 分片的参数；② 名字全是常量：machine 写死 htch-runtime、veth 写死 ve-htch-runtime、rootfs 是单例路径 /var/lib/hatch-runtime/rootfs、JARVIS_HOME=/home/hatch 写死——多租户设计里这些都必须参数化；③ Postgres 与 Cell 同生共死（见下表）；④ 脚本由 spawnd 在部署时渲染生成，常量直接烙进文本：租户归属在 VM 发放那一刻就定死，运行时不做多路复用。

5.1 管理闭环：从部署到销毁

  1. 出厂烙印（spawnd 渲染）：spawnd 在部署时把 /opt/hatch/runtime-cell/ 下的脚本渲染成这台 VM 的专属版本（机器名、路径、home、channel 都是常量），并排队 bootstrap。
  2. 备根盘（ensure-rootfs.sh）：从 rootfs-base 刷新 /var/lib/hatch-runtime/rootfs（btrfs 快照）；Cell 再叠一层 overlay（upper 在 tmpfs），所以 Cell 本体一次性。
  3. 备挂载（pre-start.sh）：把持久 home 盘、/run/hatch 共享 tmpfs、CA 信任库、按 channel 合并好的 /opt/hatch 视图 bind 进 Cell。
  4. 开机（launch-daemon.sh）：用下方 nspawn 命令以 --boot 拉起 Cell 自己的 systemd（PID 1）；宿主侧从 machinectl 拿到 Leader PID——它同时是进入 Cell 各 namespace 的句柄。
  5. 注入常驻进程（control-daemon.sh / control-execd.sh）：VM 层先轮询 runtime-cell.ready 与 Leader 存在，确认 Cell 就绪后，control-daemon.sh 直接 exec hatch daemon --runtime-cell-leader=<leader>：父进程留在外面作 systemd 的 MainPID 锚点，子进程 setns() 迁进 Cell 再 exec 本体（机制详见 4.2）。execd 同理，其监听 fd 由外层 systemd 经 LISTEN_FDS 传入。
  6. 网络收尾（post-start.sh）：用 nsenter 钻进 Cell 的 net namespace 给 host0 配 veth 地址与 tc 规则；tc ingress 分类器挂在 veth 的 HOST 侧，由 spawnd 负责。
  7. 摘流与销毁（stop.sh）：先置 /run/hatch/ingress/runtime-cell-draining 标记让 ingress 不再送新消息，再按固定时序停 Cell，并把 Postgres 实例 postgresql@18-hatch.service（PostgreSQL 18）一起停掉——数据库生命周期与单个 Cell 绑定，正是单租户的又一证据。

  --directory=$rootfs --machine=htch-runtime \

VM 外层常驻的不是单个程序，而是一整套宿主侧服务。它们共同的交汇点是共享 tmpfs /run/hatch：所有 unix socket 都摆在那里，Cell 里没有任何 TCP 监听。

VM 内固定四件套
1 Cell（htch-runtime）· 1 daemon · 1 Postgres · 1 块持久 home 盘。比喻：每个用户领到的是一台“预装好的电器型 VM”，VM 层脚本是它的电源管理——从外面把 daemon 送进 Cell，是给唯一的住户开门，不是一栋楼里给多户派工。
为什么 daemon 要“外面生、里面住”
daemon 需要高权限编排，但信任级别不能交给 Cell 内的 root（user namespace 映射后的假 root）。锚点留在外层，daemon 在 Cell 视图里干活、Cell 却动不了它（/proc 读不到、ptrace 不允许，见 4.2）。

  • 流式回复原路返回：模型产出的 token 沿同一条 socket 链反向推送——daemon → /run/hatch socket → VM 外层中继 → Meta 后端 → 客户端，不新开任何连接。
  • 后台触发走同一条门：定时任务由外层 cron-store 到点经同一 socket 链路唤醒 daemon，和用户消息共用入口，只是触发方不同。
  • 换代时不丢消息入口：draining 标记先摘流、新一代 Cell 就绪后入口再指向新 daemon；会话状态在外层 Postgres，所以换代对用户无感（实例见第 10 节的换代记录）。

一句话概括：后端推送 → VM 外层中继终止 → 共享目录 socket 塞进 Cell → daemon 接收。没有一步是“外部直接连到 daemon”。

07 / 原报告机制整理

Namespaces 技术原理：隔离什么，不隔离什么

第 4 节的 Cell、第 4.2 节的注入，底下用的都是同一组内核原语：Linux Namespaces（命名空间）+ Cgroups，统称容器技术。谱系上：namespaces 从 2002 年起陆续进内核（mount 最早、user 最晚、约 2013 年补齐），cgroups 2008 年来自 Google；LXC 最先把它们拼成容器，Docker（2013）把这套拼法流行开，systemd-nspawn（2010）是同一批原语的另一个组装者，定位「系统级容器」，所以能直接 boot 一个完整发行版。

一句话结论：namespaces 隔离的是「名字和视图」，不隔离「实体」。它让每个进程以为自己独占一套编号系统，但底下还是同一个内核、同一台机器。入口只有两个系统调用：clone() 创建时带 CLONE_NEW* 标志开新 namespace，setns() 事后把已有进程迁进别人的 namespace——hatch 的 daemon 和第 8 节的 injector 用的都是后者，nsenter 只是 setns 的命令行包装（机制见 4.2，这里不重复）。

7.1 隔离了什么：每种 namespace 虚拟化一类全局资源的名字

7.2 没隔离什么：共享的实体

  1. 内核本身。所有容器共用一个内核，syscall 接口面完全共享：一个内核漏洞被打穿，全体容器一起沦陷；一个进程触发内核 panic，全机陪葬。这是它和 VM 的本质差距——VM 连内核都是一人一个。
  2. 资源用量。namespaces 一点都不管 CPU / 内存 / IO 吃多少，那是 cgroups 的活：进程分组 + CPU / 内存配额（本 Cell 观察到的 2 核 / 8GB 就是它限的，用户机器上 systemd --version 里的 default-hierarchy=unified 即 cgroups v2 已统一启用）。只有 ns 没有 cgroup，一个失控进程能吃光整机内存、触发全局 OOM。
  3. 没被 namespace 化的内核全局状态。真实墙钟时间、大部分 sysctl（vm.*、kernel.* 改了就是改全机，所以容器里 /proc/sys 多是只读）、内核日志、内核模块加载、perf / ftrace 调试面——这些只能靠 capability 裁剪和 seccomp 挡在外面，不是 ns 的功劳。
  4. 你主动放进去的东西。隔离是选择性的：bind 进去的目录就是真目录、共享的 socket 目录就是真通道——hatch 的跨界通信恰恰建立在「故意不隔离 /run/hatch」之上。ns 只保证默认看不见，不保证你递进去的东西安全。
  5. 微架构侧信道。缓存时序、Spectre 类攻击面完全不隔离；这一层连 VM 也只能缓解。

7.3 所以完整的容器是四件套，hatch 还在外面再套一层 VM

namespaces
管视图：每类全局资源的名字各成一套（7.1）。
cgroups
管配额：CPU / 内存 / IO 的分组与上限。
capability / seccomp
管 syscall 面：裁掉不需要的特权与系统调用（如 run-daemon.sh 里丢 CAP_SYS_PTRACE）。
挂载裁剪
管文件面：pivot_root / chroot 切根、只读 bind、overlay 一次性根盘。

对照最外层：VM 靠 CPU 虚拟化扩展（VT-x + KVM）骗出一台机器，容器靠 namespaces + cgroups 在同一个内核里切出一个视图。hatch 在四件套外面还要再套一层 VM，原因正是 7.2 第 1 条——agent 要在 Cell 里跑任意 shell 和用户任务，必须假设它能被打穿，那就得让它打穿之后面对的是另一个内核，而不是宿主的。第 8 节的脚本就是把这套在自己机器上亲手复现一遍。

// injector.c — hatch「外生内住」注入方式的最小复刻。
//
// 原理与 hatch daemon 一致:进程先在 cell 外面被创建,打开目标(cell 的
// systemd,即 Leader 进程)的 namespace 文件描述符,逐个 setns() 迁入,
// 修正 root 目录,pid 命名空间靠 fork 生效,最后 exec 成目标程序。
// 注意:全程不改凭据——注入进程保留宿主侧 uid,这正是 hatch daemon 在
// cell 内 `ps` 可见、但 cell root 读不了它 /proc 的原因。
//
// 关键顺序(踩过的坑):必须在宿主视角下先把全部 ns fd 打开,再逐个
// setns。一旦进入对方 mount namespace 并 chroot,/proc 就变成 cell 的
// procfs,宿主 PID 在里面根本不存在,按路径再打开 ns/pid 只会 ENOENT。
//
// 编译: cc -O2 -o injector injector.c
// 用法: sudo ./injector <leader-pid> /bin/sleep 600
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

static void die(const char *what) {
    fprintf(stderr, "%s: %s\n", what, strerror(errno));
    exit(1);
}

static const struct {
    const char *name;
    int flag;
} NSDEF[] = {
    { "user", CLONE_NEWUSER },   /* 必须最先 */
    { "ipc", CLONE_NEWIPC },
    { "uts", CLONE_NEWUTS },
    { "net", CLONE_NEWNET },
    { "cgroup", CLONE_NEWCGROUP },
    { "mnt", CLONE_NEWNS },
    { "pid", CLONE_NEWPID },     /* 必须最后,且只对子进程生效 */
};
#define NNS (sizeof NSDEF / sizeof NSDEF[0])

int main(int argc, char **argv) {
    if (argc < 3) {
        fprintf(stderr, "usage: %s <leader-pid> <cmd> [args...]\n", argv[0]);
        return 2;
    }
    pid_t leader = (pid_t)atoi(argv[1]);

    /* 第一阶段:在宿主视角下,把目标的全部 ns fd 和 root fd 一次性打开 */
    int fds[NNS];
    for (size_t i = 0; i < NNS; i++) {
        char path[128];
        snprintf(path, sizeof path, "/proc/%d/ns/%s", leader, NSDEF[i].name);
        fds[i] = open(path, O_RDONLY | O_CLOEXEC);
        if (fds[i] < 0) die(path);
    }
    char rootpath[128];
    snprintf(rootpath, sizeof rootpath, "/proc/%d/root", leader);
    int rootfd = open(rootpath, O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (rootfd < 0) die("open target root");

    /* 第二阶段:按序 setns(pid 之前的一个是 mnt) */
    for (size_t i = 0; i + 1 < NNS; i++) {
        if (setns(fds[i], NSDEF[i].flag) < 0) die(NSDEF[i].name);
    }

    /* 已在对方 mount namespace 内:靠预先打开的 root fd 修正根目录 */
    if (fchdir(rootfd) < 0) die("fchdir root");
    if (chroot(".") < 0) die("chroot");
    if (chdir("/") < 0) die("chdir /");
    close(rootfd);

    /* 第三阶段:setns pid 后 fork,子进程才真正进入对方 pid namespace */
    if (setns(fds[NNS - 1], CLONE_NEWPID) < 0) die("pid");
    pid_t child = fork();
    if (child < 0) die("fork");
    if (child > 0) {
        int st;
        waitpid(child, &st, 0);
        return WIFEXITED(st) ? WEXITSTATUS(st) : 1;
    }

    execvp(argv[2], &argv[2]);
    die("execvp");
    return 1;
}

# 在自己的机器上复现 hatch 的两层结构

目标:一台 Linux 机器上,先(可选)开一台 VM,在 VM 里用 systemd-nspawn
起一个 cell(容器),再从 cell 外面把一个进程注入到 cell 里面运行——
复刻 hatch 的「VM 管 cell、daemon 外生内住」结构。

## 对照表

| hatch 实测 | 本实验对应物 |
|---|---|
| 物理机 + Cloud Hypervisor | 你的机器 +(可选)QEMU / cloud-hypervisor |
| VM(htch-runtime) | VM,或直接拿宿主当这一层 |
| systemd-nspawn cell(machine=htch-runtime) | systemd-nspawn(machine=testcell) |
| ve-htch-runtime veth | ve-testcell veth |
| control-daemon.sh 外层 exec daemon | injector.c 从外层注入 sleep |
| daemon 在 cell 内可见、cell root 读不了其 /proc | 注入的 sleep 同样如此(见验证 4) |
| 用户映射 uid 131072 起 | --private-users=pick 的映射段 |

## 环境要求

- 一台 Linux(物理机或 VM 均可),systemd ≥ 250,有 root/sudo
- 只有最外层 VM 需要 /dev/kvm;里面的 nspawn 共用内核,不需要嵌套虚拟化

## Ubuntu 一键脚本(推荐)

Ubuntu 宿主直接用包里的 `ubuntu-repro.sh`,下面的手动步骤它全包了。
PrivateUsers 参数它不死看版本号,而是探测 `systemd-nspawn --help`
实际支持的选项再选,并带启动失败自动降级:优先 hatch 同款的
`pick + ownership=map`,不行就退到显式范围 `131072:65536`。
注意 Ubuntu 22.04 的 systemd 虽然号称 249,但其官方手册确认
`--private-users=pick` 与 `--private-users-ownership=` 都已回补,
所以 22.04 也能直接用 hatch 同款参数。

```bash
sudo apt install systemd-container debootstrap build-essential
sudo ./ubuntu-repro.sh          # 备 rootfs → 起 cell → 注入 sleep → 跑验证清单
sudo ./ubuntu-repro.sh clean    # 清理
```

注意:Ubuntu 的 `machinectl`/`systemd-nspawn` 在 `systemd-container`
包里,不装会找不到命令。rootfs 默认用宿主自己的 Ubuntu 版本,
`SUITE=bookworm MIRROR=https://deb.debian.org/debian` 可换 Debian。
脚本跑完会逐条打印 PASS,对应第 4 步验证清单。

## 第 0 步(可选):外层 VM

只为完整复刻两层时才需要。QEMU 最简形态(cloud-hypervisor 同理,
换成 `cloud-hypervisor --kernel ... --disk path=...`):

```bash
qemu-system-x86_64 -enable-kvm -m 4096 -smp 2 \
  -hda ubuntu-cloud.img -nographic -nic user,hostfwd=tcp::2222-:22
```

ssh 进 VM 后,下面的步骤与在裸机上完全相同。

## 第 1 步:准备 cell 的根文件系统

```bash
sudo apt install debootstrap        # Debian/Ubuntu 宿主;或 dnf install debootstrap
sudo debootstrap --variant=minbase --include=systemd,systemd-sysv,dbus,iproute2 \
  bookworm /var/lib/machines/testcell https://deb.debian.org/debian
```

minbase 必须显式带上 systemd:nspawn --boot 需要 cell 里有自己的 init。

## 第 2 步:启动 cell

前台调试形态(等价于 hatch 宿主侧的启动命令):

```bash
sudo systemd-nspawn --boot --machine=testcell \
  --directory=/var/lib/machines/testcell \
  --private-users=pick --network-veth --keep-unit
```

- systemd ≥ 256 可以换 hatch 同款:`--private-users-ownership=map`
- `--network-veth` 会生成 `ve-testcell` 网卡,和 hatch 的 `ve-htch-runtime` 对应
- 正式常驻用服务形态:`sudo machinectl start testcell`

## 第 3 步:三种「从外面进去」的方式

先拿到 cell 的 Leader PID(cell 内 systemd 在宿主侧的 PID):

```bash
LEADER=$(machinectl show testcell -p Leader --value)
```

1. **API 正道**(machined 代劳):`sudo machinectl shell testcell`
   或 `sudo systemd-run --machine=testcell -t /bin/bash`
2. **nsenter**(hatch 的 post-start.sh 给脚本用的方式):

   ```bash
   sudo nsenter --target $LEADER --all /bin/bash
   ```

   注意不要加 `-F/--no-fork`:进入 PID 命名空间必须 fork 才生效。
3. **setns 自注入**(hatch 的 daemon 本体方式,本目录 injector.c):

   ```bash
   cc -O2 -o injector injector.c
   sudo ./injector $LEADER /bin/sleep 600
   ```

   注入器留在宿主侧当前台锚点(对应 systemd MainPID),sleep 在 cell 里跑。

## 第 4 步:验证清单(逐条对应 hatch 的实测现象)

1. 宿主 `machinectl list` 能看到 testcell;`machinectl status testcell`
   能看到 Leader 和控制组
2. cell 内(`machinectl shell testcell` 后)`ps aux`:只有 cell 自己的
   进程,systemd 是 PID 1;`cat /proc/self/uid_map` 能看到映射段
3. 注入后在 cell 内 `ps aux | grep sleep`:sleep 出现,PID 是 cell 内编号
4. **关键现象**:cell 内以 root 身份读注入进程的敏感 /proc 项:

   ```bash
   cat /proc/<sleep在cell内的PID>/environ   # 期望 Permission denied 或属主异常
   ls -la /proc/ | grep <PID>                # 属主显示为映射外的 uid(常见 65534/nobody)
   ```

   原因:injector 全程没改凭据,sleep 的 uid 仍是宿主侧的,在 cell 的
   用户映射里没有对应位置——这正是 hatch daemon 在 cell 内读不了的机理
5. 宿主侧 `ps -o pid,ppid,cmd -p <sleep在宿主侧的PID>`:父进程是
   injector(锚点),对应 hatch 的「宿主父进程留作 systemd MainPID」
6. `ip link` 在宿主能看到 `ve-testcell`,cell 内只有 lo + host0

## 清理

```bash
sudo machinectl terminate testcell
sudo rm -rf /var/lib/machines/testcell
```
09 / 原报告机制整理

完整交互逻辑

本节是消息进入 daemon 之后的工具循环；消息如何先到达 daemon，见第 6 节的五跳链路。

  1. 入站：用户消息经 Meta 后端 → yolk/ingress 在 veth host 侧接住 → 经共享 tmpfs /run/hatch 的 unix socket 送进 Cell（主口 sandbox-api/api.sock，另有 noded/control.sock、noded/http-api.sock）。
  2. 承接：hatch daemon 承接会话，从 Postgres 取 transcript、从持久盘取 home/记忆/技能，组装上下文。
  3. 推理：经 sandbox/space-inference.sock → inference 代理 → egress 代理 :3128 → VM 外模型服务。Cell 内没有模型进程：daemon 40 分钟仅约 32 秒 CPU、约 200MB 内存。
  4. 工具分发（Agent Loop 执行面在 daemon）：模型返回 tool call 后 daemon 分发——shell 给 execd；连接器/服务 CLI 走各自 privsep socket；浏览器由外层 browser-broker 路由到单独租用的 Browser VM；搜索走 space-web-search.sock，媒体走 space-media.sock，特权操作走 space-privileged.sock。
  5. 循环与回程：工具结果回 daemon → 再送推理 → 直到产出最终回复，原路返回用户。旁证：有 ws-client 可对 daemon 发 chat-send 并取最终回复，且 daemon CPU 随对话增长——所以 loop 的执行面在 daemon，推理面在 Cell 外；编排状态是否同步在后端，从 Cell 内无法证实。
  6. 后台工作：定时任务在外层 cron-store，到点经同一 socket 链路唤醒 daemon；子代理由 daemon 在同一 Cell 内调度，工作区落在 ~/workspace/agents/。

Hatch 各进程是干什么的

Cell 内（guest 里能直接看到的只有两个常驻进程）

进程职责实测
hatch daemon会话与工具调度中枢：承接 api.sock 入站、维护 agent loop 执行面、分发工具、回传结果；兼管 auth/telemetry 的 guest 侧锚点当前代 PID 24，--runtime-cell-leader=2168，PPID=0（由宿主侧 anchor 进程 setns 放进 Cell，见 4.2）；PID 与 leader 均随代次变化
hatch-execd命令执行服务：所有 shell/bash 都由它派生当前代 PID 748，随代次变化；监听 fd 由宿主 systemd 经 LISTEN_FDS 传入（见 4.2）
Chromium（按需）浏览器任务时才拉起，本体在 /opt/meta-chromium（667M）；复杂浏览器会话实际由外层 broker 路由到独立 Browser VM空闲时无进程

VM 外层（从脚本、socket 属主与 bin 推断）

组件职责
spawnd装配 Cell：渲染 runtime-cell 脚本、排队 bootstrap 阶段、挂载 host 侧 tc 限流
cell leader（当前代 2168，随代次变化）即 Cell 的 PID 1（guest systemd）在宿主侧的 PID；拉起并管理本 Cell，machinectl 以它确认 Cell 就绪；宿主持有它即持有进入 Cell 各 namespace 的句柄
yolk / ingress + ingress-rev-proxy终止外部流量、draining 摘流；guest 内无此进程
noded / peerd节点控制面与对等服务，socket 在 /run/hatch 下由外层持有
hatch-healthd盯 daemon / vault 健康
authdc + hatch-vault认证与凭据保险箱；凭据不进 Cell 明文
browser-broker / browser-service浏览器会话的路由与租用
Postgres / cron-store / telemetry会话状态持久化 / 定时调度 / 遥测汇聚
活例子——Cell 换代（2026-10-14 13:15 实测）：就在本文档整理期间，这个 Cell 换过一代：daemon 从 PID 22 变成 24，leader 参数从 2171 变成 2168，execd 也从上一代（PID 744）换成当前代的 748。对话全程无感续上——这正是“Cell 可销毁重建、状态在外面（Postgres + 持久盘）”的一次现场验证。本文所有 PID / leader 数字都应读作当前代数值、随代次变化，不要当成固定常量。

注：/opt/hatch/bin 的 101 个可执行文件里，有一大批是同一个 multicall 二进制按 argv[0] 名字分发的工具 CLI（instagram-cli、meta-ads-cli、facebook-cli、threads-cli、slack、spotify-api、stripe、notion-cli、hatch_gws_cli、tts、web-search、geocode、media-generation、remote-storage、image-search 等），不是 101 个独立服务。

怎么用 / 怎么观察这套系统

作为用户
你不需要碰 Cell：发消息即可，daemon 自动完成上下文组装、推理与工具循环。定时任务、子代理、侧边聊天都复用同一个 Cell 与 home；换设备/VM 重建后，靠外层 Postgres + 持久盘恢复。
在 Cell 内观察进程
ps aux 只看得到 daemon / execd；外层进程看不到属主是设计使然，不是故障。
看 socket 与网络
ss -xlnp 看 /run/hatch 下的监听（属主为空 = 外层持有）；ss -tlnp 应为空——无 TCP 监听是正常状态。
# 常用只读观察命令（Cell 内）
ps aux | grep hatch            # daemon(PID 24) + execd(PID 748)，当前代，随代次变化

证据边界（诚实标注）

  • 实测：进程、socket、端口、/opt 目录、版本号、ptrace/proc 拦截结果、网卡与 DMI。
  • 脚本明文：Cell 生命周期与创建链（ensure-rootfs 的 UID 修正与 .incoming 原子换入、pre-start 挂载与 scoped skills overlay、launch-daemon 的 nspawn --boot 命令、runtime-cell.ready 就绪轮询）、外层进入 Cell 的三种方式（nsenter、execd 的 setns + anchor 模式、LISTEN_FDS socket 激活）、draining、tc 在 host 侧、cell-root-forgeable、egress 代理地址。
  • 脚本明文（本版新增）：VM 单租户写死——control-daemon.sh 只管单个 daemon 且标记为单例文件、machine / veth / rootfs / JARVIS_HOME 全为常量、stop.sh 中 Postgres（postgresql@18-hatch.service）与 Cell 同停、脚本由 spawnd 部署时渲染；消息链路中 ingress 在 veth HOST 侧终止与 draining 摘流标记。
