01端到端数据流全景

四列：客户端 · Meta 控制面与边缘 · 用户 VM · 外部。编号对应下表的协议与鉴权。

#链路协议 / 载体鉴权与约束
1登录HTTPS，OIDC（auth.meta.com/oidc）、passkey、OTP、2FA、SSO、设备登录得到账号会话；设备 ID 持久于 Keychain（EndoAuthDurableDeviceID）。
2控制面HTTPS JSON，/hatch/*（60 余条）；web 层经原生壳同源代理 /api/hatch/*账号会话 → auth_token + notary_token；机密 VM 的 delegation. 令牌需客户端 Ed25519 背书；租约 lease_vm / bind-cvm / issue-token。
3聊天通道WSS → hatch.metaaivm.com/v1/noise，参数 vm_id / auth_token / notary_token / app_id / request_id；内层 Noise_XX_25519_AESGCM_SHA256入口校验 auth_token 并按 vm_id 转发；握手里 VM 出示 SEV-SNP 证明（绑定其 X25519 静态钥）；机密 VM 还有 RV 密钥 HMAC 互证。
4入口 → VM转发 ingress_rev_proxy.NoiseTransportFrame（分块、AES-GCM 密文）边缘不持有 Noise 密钥，看不到明文；VM 网关解密后按 hatch.noise.ServiceRequest.service 分发。
5节点通道（反向）原生 HCHTigonRoutedNoiseGatewayTransport，同样到共享入口；node.register / heartbeat，VM 下发 node.invoke节点注册绑定 node_id + link_nonce；每个 invoke 过权限门控与 HITL 审批卡；文件结果经 NodeInvokeResultUploader。
6VM 出网透明代理 tproxy，可 MITM，按 SNI 拒绝，网络规则egress.approvals 按"域名 + 任务"审批；作用域权限（连接器 / 定时任务 / 聊天）；可撤销重置。
7连接器授权OAuth / API key / 用户名密码，回调到 /v1/*-auth/callback（authd）凭据由 authd 管理（/v1/credentials/* 全部标 service=authd，含 capture 与 1Password 集成），落盘在 vault 管理的 LUKS 加密卷上（推断）；共享给他人时只给描述符不给明文。
8语音rsys WebRTC（STUN/TURN）到 meta-ai-realtime.facebook.com；数据通道跑 Nebula（OpenAI Realtime 形状，Thrift）；ASR WSS；TTS SSE由 voice.calls.join / media_endpoint 建立；通话时上报位置（文案明示）。
9模型推理推断：VM 外的推理服务model.get/set 带 generation；hatch_big_boy_models 开关；模型名在包内被抹掉。
10用户间互联peers：邀请 → SAS 短认证串人工比对 → 收件箱投递；shared agents：对方 VM 经共享入口 + OAuth 令牌，connectionClass=shared_agent关系带代际号与修订号；共享 agent 连接要求 msg2 必须是证明、拒绝 RV 质询。
11证明校验VM 在 msg2 携带 thatch.attestation.v1.AttestationBundle；客户端本地验证VCEK→ASK→ARK 链、CRL、report_data 绑定、度量 ∈ image_manifest、芯片白名单、Plexi/Sigstore 透明证明、吊销证据。
12IM 渠道用户在手机 WhatsApp / Messenger / Telegram 里与 agent 对话；channels.link / status / unlink，companion 解锁渠道绑定经控制面完成；消息送达 VM daemon 的具体路径属推断（图中蓝点线）。
13内容与遥测fbcdn / rupload.meta.ai / Sparkle appcast（EdDSA）/ QPL、Crashpad、Sentry与 VM 隧道无关的旁路。
小结：鉴权发生在三个不同的地方：控制面（你是谁，给你 token）、入口（token 对不对，转给哪台 VM）、VM 内（Noise 对端是谁、RV 密钥对不对、这个动作/这次出网准不准）。边缘只能做第二件事。

03Agent 交互能力

以 VM 内的 daemon 为中心：左边是触发它的输入，右边是它能调用的三类工具后端与外部，下面是它读写的持久化，上面是推理。

能力出口 ① 服务端工具

tool.exec · web_fetch · imagine · zeitgeist

在 VM 内执行，出网经 sentinel。审批图标把 tool.exec 标为"地球"，推断为带网络的执行环境；"Hatch folder" 之外运行程序需额外授权。

能力出口 ② 本机节点

nodes.sync → invoke → invoke_ack / result

唯一在用户设备上执行的出口。电脑控制在后台虚拟显示器进行，文件、邮件、信息、日历等工具各有读/写/动作三级授权；web 客户端自己也是节点，接受 ui.navigate.* 等 27 个 UI 命令。

能力出口 ③④ 浏览器与连接器

browser_task.* · authd（credentials.*）· vault（LUKS）

VM 内租用浏览器执行网页任务，用户可随时 takeover；连接器 OAuth 回调与凭据库都在 authd（/v1/credentials/*），credentials.capture 可从浏览器登录中捕获凭据；vault 负责 LUKS 加密卷，是凭据的落盘处（推断）。

04一条消息穿过的 12 层

以 web 聊天层发出的一次 chat.send 为例。客户端打 7 层包，网络上过 3 跳，VM 侧对称拆包再分发。横条表示"这一层在哪段路径上存在"，断开处就是它被终止并重建的地方。

单入口为什么撑得住

DNS 实测 · 2026-11-01

hatch.metaaivm.com 是 CNAME 到 edge-metaclaw-http.c10r.facebook.com，落在 Facebook 全球边缘的统一命名空间 c10r.facebook.com 里；Messenger / WhatsApp 的长连接入口 edge-mqtt.facebook.com 同样是 mqtt.c10r.facebook.com。AAAA 记录 TTL 24 秒，是 GeoDNS 流量调度的典型特征。

一个域名不等于一台服务器：DNS 层按地区分到不同 PoP 的 VIP，VIP 后 L4 负载均衡再分到成百上千台边缘机，每台维持几十万到上百万条空闲 WebSocket。入口本身无状态，只校验 token、查 vm_id、搬运密文，CPU 开销接近零，可以任意加机器；真正有状态的是按用户切分的 VM，天然水平扩展。

推断：Katran / Proxygen 的分层来自 Facebook 公开架构，针对此服务没有直接证据；CNAME、TTL、401 响应头为实测。

真正的扩展压力在哪

不在这个地址上
  • vm_id → 主机 的查找服务：每条新连接都要查一次，要低延迟、高可用。
  • 连接数：每台 Mac 至少两条长连接（web 聊天层 + 原生节点）加心跳；保活流量是边缘要算的成本。
  • 每用户一台 VM：这才是最贵的部分，入口相比之下很轻。
  • 端口不是限制：65535 的上限针对"同一客户端 IP 到同一服务端 IP:端口"，服务端可接受无限多不同客户端。
  • 单域名的工程收益：一张证书、一条防火墙白名单、客户端一个常量；VM 身份放在查询参数和 Noise 里，不暴露在 DNS 上。

05长连接的生命周期

设计上是"尽量一直保持"：10 秒心跳、秒级重连、后台不放手。两个例外决定了它不是永远在线：VM 会被挂起，以及没人看的时候不主动唤醒。

心跳超时10 s → 关闭码 4002HEARTBEAT_TIMEOUT_MS、HEARTBEAT_TIMEOUT_CLOSE_CODE；探测无应答主动关闭再重连。
重连退避0.5 / 1 / 2 / 5 / 10 s，上限 15 sRECONNECT_DELAYS_MS、RECONNECT_WAIT_MAX_MS；30 s 标记慢重连；耗尽后 60 s 再武装。

stream 空闲5 minSTREAM_IDLE_TIMEOUT_MS；作用于连接内单条 stream，不断连接。
后台保持（原生）App Nap 豁免 + 后台活动断言"Began App Nap exemption for gateway keepalive"、BackgroundActivityLease；节点通道在 app 退后台后仍保温。
VM 挂起可重试的断开"Pinned VM is suspending; the connection is retryable"、"not reachable (suspended, deleted, or unmapped); retry with a force-wakeup credential fetch"。
VM 唤醒POST /api/hatch/vm/wake，10 s参数 vm_id / retry_count / connect_attempt_id；触发类型 foreground / recovery / late；界面 "Warming up"，预热等待上限 5 min。

小结：连接层面是典型的"永远在线"客户端设计；产品层面把"VM 是否醒着"当成成本开关，用"有人看"和"有任务"两个条件来决定要不要维持。

06消息级协议：RPC、订阅流与事件信封

答案一句话：一条 WebSocket，一层 Noise，里面是"HTTP 形状的 RPC"加"NDJSON 事件流"。没有独立的 JSON-RPC 或 gRPC；路由表里甚至没有 chat.send，发消息就是打开一条名叫 chat.stream 的流。

两种原语的线上格式

hatch.noise.ServiceFrame 内
  • 单次 RPC：request{verb, path, headers, body(JSON), end_body:true} → response{status, headers, body, end_body:true}。body 约定 {ok:true, result}，非 2xx 或 {error} 转为网关错误（内部叫 jarvis_rejection，429 单独识别为限流）。
  • 订阅流：request 同上但路由标 streamMode: subscription；第一个 response 帧是 ack（{ok:true,result} 或旧式 {type:"res",status:"ok",payload}），之后 body_chunk{data, end_body:false} 持续到来，data 是 NDJSON，每行一个事件信封。
  • 事件信封：{type:"event", event:"<名字>", payload, seq, ts_ms}。客户端按 (seq, messageId, lane) 合并；历史回放（chat.stream_events、chat.history）返回的行 {event_name, payload, seq, occurred_at_ms} 被转成同一种信封，只是 transport 标为 http 而非 ws。
  • 限制：订阅单条记录有上限（maxSubscriptionRecordBytes），超限的 activity 流会被重置；流空闲 5 min 超时；*.subscribe 在重连后自动重订，chat.stream 不会（它属于那一轮）。
  • 取消：reset{code: CANCELLED} 帧，或业务上的 POST /chat/cancel。

残留的明文协议与它的去向

type: req / res / event

代码里仍有一套直接在 WebSocket 上跑 JSON 的协议：{type:"req", id, method, params} → {type:"res", id, status:"ok"|"err", payload|error}，以及 {type:"event", event, payload, seq, ts_ms}。在 Noise 连接上它被显式禁用：发送端日志 "wsSendJson called under Noise, dropping (no plaintext path)"，接收端 "Rejecting plaintext frame on Noise connection"。

推断：这是 Noise 之前的网关协议。现在的事件信封格式就是从它继承的，只是被装进了 HTTP-over-Noise 的订阅流里；subscriptionHttpAckResult 同时接受新旧两种 ack 形状也印证了这一点。

与之无关的两个 "RPC"：web 包里捆的 vscode-jsonrpc 是给代码编辑器的 LSP 用的；protobuf 运行时用于 Noise 帧和证明包，不用于业务消息体（业务体是 JSON）。

消息原语路由 / 事件关键字段与行为
客户端发消息订阅流POST /chat/stream（daemon）body 含 text、attachments（先经 files.upload 上传，"stageBeforePublish"）、reply_to_message_id、session_id、stream_lane；发前先过本地审批门与"用户在场"检查；连接不在时进发件箱 queued_for_connection，重连后安全重试（isSafeOutboxRetry）。
收这一轮回复同一条流的 body_chunkdelta.* 事件message_start → text_append ×N → tool_start/tool_done → placeholder / presentation → compaction_start/done → message_done → turn_done；按 seq 合并，lane 区分 main / subagent。
收服务端主动消息长期订阅流POST /chat/subscribe → message.assistant 等后台任务、cron、其它设备发出的消息；payload 带 isBackground、agent_id / parent_agent_id、visibility、channel_context；ack 超时 30 s，断线重连后自动重订。
HITL 审批到达事件approvals.snapshot + 带 approval 的聊天消息快照含 pending / recent 全量，客户端据此刷新审批列表与权限视图；消息状态 pending_user_confirmation 时 composer 锁定（"sending is paused"）。
HITL 审批回答单次 RPCPOST /approvals/{id}/decide（sentinel）{approval_id, decision: allow_once | allow_always | deny | deny_always…, always_scope, expected_message_revision, notification_channel:"ui"}；可先 edit-message 改写待发内容；支持批量决策。
服务端下发 UI/设备命令事件 + 单次 RPCclient.invoke → POST /client/invoke-resultpayload {invoke_id, command_id, params}；无注册 handler 时记录错误；原生节点对应 nodes.invoke_ack / invoke_result，文件结果另走上传。
探活 / 在场单次 RPCPOST /api/ping {presence}每 10 s；presence 取 active / away，由页面可见性与焦点推导；是心跳也是"用户在不在"的上报。
其它状态同步长期订阅流activity / tasks / fs / computer / sessions / identity / spaces / navigation / theme .subscribe各自推送 *.updated、*.snapshot、spaces.data_invalidated 等事件；界面不轮询。
共享 agent 远程对话订阅流 + RPCshared_agents.remote.open（流）/ remote.send（RPC，带 client_message_id）走另一条 connectionClass=shared_agent 的 Noise 连接；事件 shared_agents.remote.message / closed。
小结：问"是 RPC 还是 WebSocket"的答案是"都是"：传输是 WebSocket，加密是 Noise，语义是 HTTP 形状的 RPC；流式和推送不是另一种协议，而是同一种请求的响应体一直不结束。

未验证的推断

  • 模型推理的位置：图中放在 VM 外，依据是 Meta 的常规架构与 model.set 的 generation 版本化；也可能部分在 VM 内。需要运行时观察 sentinel 的出网审批或 /model 响应。

  • 透明日志的在线查询：代码里 Plexi / Sigstore 证明随证明包携带、客户端离线校验；是否还会在线查询日志未见证据。
  • peers 的实际传输：路由在 daemon 下，经共享入口可解释；是否存在 VM 到 VM 的直接链路未知。
