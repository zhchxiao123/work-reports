核心判断

Tetral 的关键不是“换一种消息流”，而是把 Agent 执行权、输入承接、工具身份和结果结算变成可复查的持久协议。PostgreSQL 承担正式事实；Runtime 热态可以丢弃；Core NATS 只承担短暂预览。

01 / 机制拆解

结论与版本：它是一套 Agent 运行协议

Tetral 把 Agent loop 作为可调度的云运行时，将 Session、输入、模型请求、工具声明、结果和执行归属写成持久对象。它解决的是“已经接受的工作由谁继续、结果如何结算、运行进程消失后怎么协调”，跨越控制面、Harness 与沙箱管理。

持久事实

PostgreSQL 保存业务记录、Inbox、Queue、结果 receipt 与身份。对象字节另放 S3 兼容存储。

可丢弃热态

Runtime Pod 驻留上下文和执行 fiber；丢失后依据持久事实冷重建。

外部执行

Daytona、模型服务、MCP 与 Web 有独立失败边界，未知结果需要协调。

展示投影

SQL 正式事件和 Core NATS 短暂预览分开；预览不成为执行权威。

调研固定点

main 提交 409311382659…，2026-10-13；MIT。本文是源码与契约分析，并执行了 6 项纯逻辑测试，没有部署整套 Tetral。

截至调研，GitHub 可见发布为 v0.1.0-alpha.2（2026-09-10，pre-release，源码 3e9d791f…）。它早于当前拆分服务架构，不能把本文 main 的行为当成 alpha.2 已交付能力。

03 / 机制拆解

对象模型：Workspace → Session → Thread → Request

Workspace：数据库租户↓Agent policy + Environment generation / artifact↓Session：持久会话与一个逻辑 Sandbox↓Thread：main / child / reviewer 的上下文与执行 lane↓Request → 完整语义成员 → ToolUse → ToolResult

Agent 和 Environment 是可版本化的配置/资源；Session 承接具体运行。Thread 分开上下文、输入与生命周期，Request 记录一次模型调用。工具身份来自持久 ToolUse，而不是随恢复生成一个新调用 ID。

Runtime binding

Session 当前驻留哪个 Pod、哪次 Runtime boot、哪个 binding generation；用于拒绝旧执行者的新提交。

Sandbox binding

逻辑沙箱对应哪个 provider resource、Environment 与文件投影修订；它与 Runtime binding 独立。

一个子 Agent 是独立 Thread，但仍共享父 Session 的 Sandbox 和文件系统。Thread 上下文隔离不能被写成独立容器或操作系统隔离。

04 / 机制拆解

一条输入的全链路：接收、托管、执行、可见

  1. 验证与接收。Auth 确定当前 Workspace 权限，API 写业务输入；相关 Inbox 与 queue_jobs 在同一事务出生。
  2. 领取工作。Runner 从 Queue 获得带 token 的租约，重读源事实并检查因果 lane。
  3. 找到执行者。复用有效 binding，或选择新 Runtime Pod；请求直达精确 Pod 与 boot identity。
  4. 承接输入。Runtime 经 Bridge CommitInputs 保存输入，热态接受；Queue 根据对应交付契约 ACK。
  5. 完成一个 turn。ThreadLoop 发模型请求、提交完整成员、声明与执行工具、结算结果，最终封口 Request / run。
  6. 发布展示。正式输出来自 SQL；模型期间的 NATS 文本预览可丢失，不改变上述事实。
确认点它实际确认什么
API 接收业务输入与持久工作已登记
Queue ACK对应通知已被持久协调/承接，或确认已处理；不普遍代表 Agent 完成
Bridge receipt某个固定声明/结果已提交，重复请求可读取同一结论
Request End / ToolResult模型请求与特定工具的持久终态，各有独立条件
SSE 数据发出服务端输出展示帧；不自动证明浏览器已收或用户已读

Interrupt 的 ACK 条件更强：仅“Runtime 已接受”不够，必须取消/join 工具范围、提交 Request End 与 exact receipt 后才能释放 Thread barrier。

05 / 机制拆解

PostgreSQL Queue：事务、租约与因果仲裁

EnqueueTx / EnqueueBatchTx 使用生产者自己的事务，避免业务已写入而通知未出生的双写窗口。Queue payload 主要是持久引用；用户正文和凭证留在业务表。分区 counter 同事务推进，active 去重命中不推进序号。

pending→leased + token→acknowledged或retry / defer / cancelled / dead_lettered

最终提交 fence

事务锁住对应 Queue 行，再用数据库 clock_timestamp() 检查 token 与有效期。等待锁期间过期的旧 lease 不能继续提交。

租约过期不是业务失败

任务回到 pending，新的持有人先检查持久事实。旧实例可能已提交结果，只丢失 ACK，不能直接重复效果。

Session-exclusive lane 排斥该 Session 的 Thread 工作；Thread lane 排斥自身与 Session-exclusive，兄弟 Thread 可并行。unique index、advisory 仲裁锁和事务内重验共同生效。候选领取使用 FOR UPDATE SKIP LOCKED；进程内公平 cursor 是偏好，不是多副本全局公平 SLA。

唤醒通过 PostgreSQL pg_notify，是提示而非消息权威。监听重连会重新 wake，周期扫描仍能发现持久任务。这里的 Queue 不是 Core NATS，也不是将 outbox 必然 relay 到 JetStream 的模型。

固定源码：counter 与 enqueue · lane eligibility · 最终 lease 校验 · 重连唤醒 · 约束索引

06 / 机制拆解

ThreadLoop：持久事实驱动纯 reducer

已提交 facts→冷加载 checkpoint→纯 reducer / nextStep→一次 dispatch→Bridge ACK

ThreadLoop 拥有事实应用与副作用调度。内部状态包括 idle、ready_to_request、request_open、request_sealed / waiting_for_tool_results、ready_to_finish，最后 FinishIdle；这些不是对外 API 的状态枚举。

冷加载重建提交的上下文与 turn facts，不保存一份待重放的热 dispatch。重复 tool_use_committed fact 只生成稳定 transition，不能再次获得 dispatch。常规热投影等待 Bridge ACK；interrupt closeout 是文档单独约定的 hot-first 例外。

单 Thread 单执行者与普通输入

进程内 ThreadRunSlot 只有一个 owner，多个调用者可 join。普通输入排入已接受输入视图，留给合法的后继 run；显式 interrupt 才安装 stopping fence。取消某个 join 等待者不等于取消 owner。兄弟 Thread 可以并发，跨进程排他由 Queue、Bridge 和 binding 保证。

Provider retry 与 compaction retry 有独立有限预算。重复成功工具、重试模型、任务收尾各有状态条件，不应由“再尝试一次”的无界循环隐式决定。

固定源码：冷加载 · nextStep · 一次工具 dispatch · run slot · 有限预算

08 / 机制拆解

工具：声明、审批、并发和结果结算

完整 tool-call → 可用性检查 / approval gate↓公共 ToolUse 持久 ACK → reducer 授权 dispatch↓Session permit → exact executor → ToolResult settlement ACK

未知/禁用工具走 internal repair，让模型修正；合法但拒绝的工具则有公共授权结论。审批与并发调度是两个维度：full_access 允许已启用工具；ask_for_approval 等人工；approve_for_me 调内部 reviewer。已确认 reviewer 失败回落人工，未持久结算的 reviewer outcome 不允许直接继续。

Session 默认最多 8 个工具 permit。Write/Edit 按目标 path 串行，apply_patch 按全部修改路径，memory 使用 Session exclusive，child control 按 task_name。Bash / exec_command 和 MCP 分类为 parallel_safe，只是调度策略，不能证明任意外部业务副作用不会冲突。

结果的事务边界

Bridge 从原始 ToolUse 反查固定 family 与 Request；检查当前 process / binding，原子写 ToolResult、Assistant projection、bookkeeping 与 receipt。同身份同摘要返回 duplicate；换摘要拒绝 conflict；已另行结算返回 stale。

这约束的是内部结果记录。第三方效果是否只发生一次，还要看外部系统的幂等与查询协议。

固定源码：门禁矩阵 · permit · 调度分类 · 事务结算

09 / 机制拆解

Sandbox：按需激活与未知执行结果

Session 接收时不预先创建 Daytona 资源。首个已批准的 Sandbox 工具触发逻辑沙箱激活与文件/技能/Memory materialization；同一资源有 singleflight。当前实际 driver 是 Daytona，虽然有 provider seam，尚无 CubeSandbox driver。

pending → waiting activation / materialization↓preparing（暂存命令，未运行用户命令）↓AuthorizeRunning 事务 → running → provider submit↓terminal_unconsumed → Bridge ToolResult → consumed

AuthorizeRunning 重验 exact binding、修订、release/cancel 状态、资源凭证、helper 与数据库时间，然后才提交外部执行。队列租约的 live authority 在最终业务写前再次检查，heartbeat 在 Queue ACK 前停止。

执行已经 running，worker 却退出时

有 provider execution ref，恢复者观察原执行；缺 ref 时优先检查已有 staged 结果，无法证明则写 unknown_outcome，不能盲目重新 submit。外部执行已开始、provider ref 尚未保存是跨系统窗口，无法仅靠数据库 receipt 宣称任意命令 exactly-once。

terminal_unconsumed 是暂存状态，不是已经向用户提交的 ToolResult；只有 Bridge 结算后才进入正式投影。迟到竞争者的正文会被清理，保留摘要/receipt。

Environment build 用队列 defer 进行异步观察，默认硬超时 30 分钟；超时代表 Engine 不再等待，并不等于 provider 已取消构建。网络策略在创建 provider sandbox 时设置，更新 Environment 不改写现有 sandbox 的网络。

10 / 机制拆解

Files、Skills、Memory 与外部 Connector

对象字节与元数据

大文件/附件位于 S3 兼容存储，数据库保存身份、版本与引用。文件/Skill 是只读资源投影，工作目录可写。

Prompt 组合

platform → Agent system → Memory 元数据 → Skills listing。列出路径与说明，不自动将所有 Skill / Memory 全文塞入上下文。

Memory 工具经 Bridge 校验 writable binding，数据库版本化 mutation 与 receipt 先提交。有活沙箱时入队更新投影，冷态可 skipped_cold。replace 检查 old_text；delete / rename 要 expected_text，避免覆盖并发改动。沙箱文件是视图，数据库版本是权威。

MCP：claim、stored result、replay

Connector 根据已批准的 ToolUse 反查不可变工具/input，不接受 Runtime 重新指定任意 payload。只有 new claim 执行，已存结果回放；Commit 丢 ACK 时重试同一不可变提交，不把未知结果解释成未执行并释放 claim 重做。

若外部动作已发生，而 executor 在 durable Commit 前死亡，数据库仍不能证明外部结果。过期 claim 接管不能自动消除这一窗口；需要业务幂等 key、查询/对账和明确 unknown 状态。

Web Connector

搜索/打开/查找有有界外部调用，结果 snapshot 的引用存数据库、正文存 blob。readonly reopen 与新的 fetch 分开，receipt 与 claim expiry 约束结果提交。来源变化和上游失败仍是外部边界。

固定源码：Prompt 组成 · Memory / Skills 索引 · Memory mutation · MCP claim · lost ACK replay · Web snapshot

11 / 机制拆解

子 Agent：持久 Thread、上下文快照与完成邮件

spawn_agent 创建相同 loop 驱动的 child Thread，继承当前模型。fork 选择完整 user-led turns 的 ordered message refs；Bridge 校验后保存不可变 prefix。后续 parent 历史变化不会重写 child 的初始上下文。

验证 ToolUse / task_name→child + prefix+sent / received mail+Inbox / Queue / receipt

上述记录同一事务提交，source replay 返回同一 child；task_name 在 parent 下唯一。spawn 的 delivered 表示初始托管被承接，不等于 child 完成。send_message 用固定 delivery identity，完成回信在 child 结算事务中出生，不靠事后扫描补通知。

Parent / child 有独立 Thread context 与 lane，共享 Session 文件系统与工具 permit。close/interrupt 先冻结 descendant census，按 exact control ACK 收齐并持久关闭 subtree；resume 校验 quiescent checkpoint，不是删掉 child 后重建一个同名对象。

文档中 inter-agent 的 exactly-once 应限定为 delivery ID 对应的持久 envelope / input 投影。它不扩展成 child 内任意 Shell、MCP 或 API 副作用只执行一次。

固定源码：spawn / fork · 原子创建 · 完成 mail 与 custody · 子 Agent 控制契约

两种 checkpoint：上下文压缩与进程迁移

对象保存什么用途与限制
Context / message store已提交消息、immutable child prefixMessage sequence 与 Event sequence 不是同一坐标
Compaction checkpoint较旧历史的模型摘要 + 保留近期内容有损 Prompt 压缩，不能替代工具/owner/Request 事实

主动压缩结合上次 usage / 模型 limits 与新上下文 chars/4 估算；冷启动或切模型缺热提示时，有 provider context overflow 的反应式 backstop。近期保留目标约 8,000 estimated tokens，summary output ceiling 4,096，checkpoint mint cap 60 KiB。fit-check 失败会拒绝，不默默截断。

13 / 机制拆解

调度与失联：精确身份比心跳更重要

新 placement 使用 power of two choices：探测两个候选，偏向 resident Session 数更低者，同时检查 readiness、容量与 memory cutoff。最多两轮四个候选；这些是当前 policy 上界，不是吞吐或恢复时延基准。有效既有 binding 可复用，最终事务重验身份，并接受并发已经建立的合法 binding。

Pod UID+runtime_process_id（一次 boot）+binding_generation

注册只是 starting candidate；合法 accepting report 才 promotion，原子 retire 旧 process。同一个 Pod 内进程重启也不能冒充旧 owner。Runner 直连该 Pod，单次 RPC attempt 失败后的投递重试归 Queue，不经随机负载均衡。

可以证明 loss

fresh Kubernetes GET 确认 Pod 不在/UID 替换，或已有持久 process retirement；事务锁后仍需重验匹配身份与数据库时间。

只能暂时 unavailable

watcher 未同步、GET 失败、注册暂缺或仅心跳过期。误判 loss 会制造双执行者，不能直接 repair。

Repair 将 exact Inbox 交回、封口 open Request、结算确证孤儿工具，保留仍能恢复的外部 custody，释放旧 residency。不重建尚未提交的 Provider token。Runtime Pod loss 不释放 Session Sandbox，两种生命周期独立。

固定源码：placement · process promotion · loss classifier · 锁后重验 · 修复事务

14 / 机制拆解

故障推演：可以恢复什么，仍未知什么

选择一个窗口，观察持久事实、恢复动作与不能推断的结果。以下是源码顺序推演，没有进行真实基础设施故障注入。

Interrupt 与“取消请求”不是同一状态

Runtime 安装 stopping fence，join outstanding writes / provider / tool scopes，封口原 Request，结算 exact unfinished ToolUse，之后才允许后继 run。HTTP 超时、请求取消、外部工具已停止、结果已持久写入，是四个不同边界。已提交的 child interrupt 不会因调用者停止等待而撤销。

恢复的核心是重建已知 ledger 与 custody。对于无法证明的外部结果，保持 unknown 比伪造 success 或一律重试更可靠。已经存在 receipt 的 ACK 丢失，与外部动作发生但尚无 durable receipt 的失败，必须走不同处理。

固定源码：输入 handback · 恢复源验证 · interrupt ACK gates · 外部执行观察

身份、RLS 与 Git 凭证：隔离边界在哪里

边缘 Envoy Gateway 调 Auth Check，清除原始凭证与不可信身份 header，再注入 Ed25519 签名的内部 principal。API / Event Stream 验 audience、精确 method/path、expiry；Workspace 来自已验证 principal。

API key 优先选择，错误 key 不回落另一种 Bearer 身份；OIDC federation 必须注册 issuer 和 grant，并检查当前 authority revision。当前唯一可分配角色是 workspace_full_access，不能据此宣传已经支持任意细粒度 RBAC。

数据库租户

Workspace 是唯一 tenant。复合身份/predicate 与 FORCE RLS 配合，服务账号使用 NOBYPASSRLS，启动时验证 schema 与角色契约。

内部执行权

workload identity 与短期 token 绑定调用方、Pod UID / process 等范围。Session / Thread 仍须验证显式归属与 visibility。

Git Proxy：把真实仓库凭证留在代理

Sandbox 使用短期 ticket，数据库只存 ticket 摘要；Proxy 校验仓库 allowlist，向固定 github.com 的有限 smart-HTTP 路径注入真实凭证。ticket 不放在 URL 中；轮换经过 pending-install → live。它保护凭证分发边界，不自动为共享文件系统提供更细的 Thread 隔离。

下表是结合本站已有调研的架构判断；只比较明确边界，不是吞吐排名，也不表示已把 Tetral 接入我们当前系统。

对当前 DSH 项目最有价值的借鉴

  1. 把 input accepted、execution started、result committed、output published、client received 分成不同事实。
  2. 稳定 ToolUse / operation identity 与结果 receipt，旧 owner 提交需经过 generation fence。
  3. 跨进程恢复先查询已知效果；把 unknown 当显式状态，避免默认重做有副作用工具。
  4. 区分 Harness / Runtime 与 Sandbox 生命周期；运行进程丢失不应自动抹掉工具环境。
  5. 将 lossy preview 与 durable public output 分开，并为 UI 设计明确续读契约。

当前本地 DSH 文档/代码已有持久事件 → public projection outbox → 单 owner JetStream 发布 → 浏览器授权 SSE 的路线。Tetral 的 SQL 正式流 + NATS preview 是另一种组合；二者不应共享未经验证的 ACK / cursor 假设。本次未刷新远端 DSH 部署验收，也未改动其运行配置。

常见问题：先校准容易误读的承诺

Anthropic-compatible API 是否就是现有应用无改动接入？

公共接口采用兼容形状，并使用维护的 TypeScript SDK fork；Session、资源与持久运行协议有平台自己的行为。仓库将偏差列为 compatibility case。能复用接口习惯，不意味着每个 upstream 参数、事件与取消语义都完全等价；具体客户端要做契约验收。

“Sandbox 可丢弃”是否代表工作目录永远不丢？

已注册文件、Skill、Memory 和已捕获输出可以依据元数据/对象字节重新投影。临时工作目录还受 capture、provider 生命周期和结果提交边界约束。不能把任意未捕获写入都当作数据库已保存。

多副本能否让一个 Thread 的全部工具并行？

Thread 的合法 step、Session permit、路径互斥与外部 custody 决定并发；增加 replicas 不取消这些关系。兄弟 Thread 的并行也共享 Sandbox 文件系统，应额外考虑业务冲突。

是否可以只拿其中 Queue 替换 JetStream？

可以研究其 PostgreSQL 事务 queue 思路，但当前 Queue job family、因果 barrier 与 Bridge / Runner 身份协议耦合。它不是已公布的通用 Broker 替代接口；抽取需要重新定义工作契约与验收。

源码恢复分支丰富，就能认定生产可靠了吗？

它提供了可检查的设计与测试场景。可靠性仍取决于角色权限、外部 provider 行为、故障窗口、容量与升级操作的真实验证。本次仅报告源码确认和明确执行的 6 项局部测试。
