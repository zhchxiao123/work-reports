从 Super-agent 能借鉴什么基础设施

DeepSeek Harness 团队发布了 Super-agent 设计文章和研究原型。这里只看基础设施，不涉及它的产品形态。原型官方说明是研究代码，不是产品，所以我们取做法，不取代码。

01吸收哪些做法

做法它怎么做我们怎么用
尝试（Assignment）任务状态不跟随会话，每次执行都是一次可替换的尝试一轮对话可以有多次尝试。重启、换沙箱、换宿主都是“新一次尝试”，尝试序号同时充当重启计数
恢复说明重启后新起一次尝试，要求先检查目录、git 和外部状态，再决定是否重复外部动作作为续跑策略，不做工具的 safe/unsafe 声明。必须配次数上限，原型没有，我们要补
对账补投消息用稳定 ID，恢复时读“已落盘日志 + 队列”，缺了就重投不改 DSH core 也能补偿两个丢消息的窗口。我们以持久日志为准判断，避开原型“标了已读但没落盘”的反向窗口（推断）
先存后做状态变化和待办在同一事务，失败退避重试不加通用队列，把 DSH 日志当 outbox，只保护结局事件：先落盘，再发 Redis，再记已发送
长命令转后台前台命令超过 5 秒转后台，对话继续接收消息机制在 DSH 里。我们补时限和结果归属；不追求后台任务跨重启存活
健康面板每项一个写者，连续失败 3 次才告警，成功即清除宿主统一汇报 Redis、BE、存储写入延迟、模型重试、沙箱启动失败
测试方式假宿主、表驱动的领域测试借鉴结构。它没有真正的 kill -9 测试，这部分我们自己做

02不照搬的

  • 接入用户自己的电脑（BYOM）：DSH 最新版没有这样的 daemon，SSH 断线还会杀进程；文章也把它的安全风险列为开放问题。
  • 后台任务跨重启存活：要在沙箱上放常驻进程，代价大。先靠恢复说明处理。
  • 单 Router 批处理：对每用户一个上下文的共享宿主价值低。
  • 每项工作一个 git worktree：我们的会话目录已经隔离，只有同项目并发才冲突。
  • 外部 Watchdog 里的 LLM：原型代码里没有 Watchdog 实现。我们先用确定性检查（多久没进展）。
  • 凭证封装：原型自己说明命令封装不是安全边界，所以不能作为我们的方案。

03它帮我们发现的缺口

都是读代码的判断，尚未实测，列入第一批验证。

缺口可能的现象怎么补
后台任务的结果归属这一轮结束后任务才完成，输出可能到不了用户有后台任务时这一轮保持打开，带时限
后台任务没有时限挂死的任务一直占着工具沙箱超时结束并告诉模型
超长结果的存放位置写在宿主临时目录，模型却到工具沙箱去读改存到会话目录
宿主级准入一个用户可能拖累同宿主的其他人每用户轮次槽位、模型并发限制，给人的消息留名额
