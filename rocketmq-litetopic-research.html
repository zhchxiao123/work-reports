结论先行

LiteTopic 最有价值的是低成本、动态、可恢复的细粒度消息通道，适合会话响应、任务回执与按维度退让。它把连接与消息交付解耦，但完整 Agent 恢复依然依赖业务历史、执行所有权和幂等结果。

本次核实的四个关键细节：默认起点受内存条件影响；TTL 不因积压而停止清理；Java Suspend 不 ACK 当前消息；固定授权路径主要检查父 Topic 与 Group。

01 / 设计动机

轻的是通道成本，AI 价值在于寻址与解耦

AI 网关要把长任务的响应发回特定会话；多个 Agent 也需要向指定任务或对端传递结果。为每个会话创建普通 Topic / ConsumerGroup，管理与订阅成本会随会话数增长。LiteTopic 把这些短生命周期通道收进预先创建的父 Topic。

会话 / 任务可寻址

发送方用业务身份选择子通道；接收方动态订阅目标集合，避免所有实例接收后再过滤。

生产与连接解耦

后台任务可继续生产消息，网关实例负责消费与转发。浏览器连接重建不必重新启动推理，但这一点仍依赖后台任务的独立生命周期。

RIP-83 在本次读取时已标为 Shipped。其目标是补充 HTTP / gRPC 的异步通信方式；它不提供模型推理、任务规划或完整 Agent 检查点。

依据：RIP-83。下文的 DSH 接入判断是本项目分析。

02 / 对象与存储

父 Topic、LiteTopic、LMQ、消费组不是同一个对象

父 Topic：预先创建 / LITE 类型↓ 路由与业务命名空间LiteTopic：会话、任务或用户维度↓ 内部 LMQ / ConsumeQueue 索引共享 CommitLog 消息体 → 消费组位点 → 消费实例
对象管理什么设计边界
父 Topic类型、路由与 Lite 配置必须先创建；不能只调用子通道 API
LiteTopic细粒度有序索引与订阅目标父 Topic + 子名称共同寻址
LMQ轻量 ConsumeQueue 的基础机制LiteTopic 基于 LMQ；旧 LMQ 不都属于新 Lite 模型
ConsumerGroup消费进度与组级模式绑定父 Topic，位点不能与浏览器进度混为一谈
Client订阅集合、接收与处理同组实例可订阅不同子集合

固定版本将内部子通道编码为 %LMQ%$parent$child。这不是建议应用手工拼接的公共身份。消息体仍在 CommitLog，子通道主要建立轻量索引；“独立通道”不等于每个租户拥有独立磁盘、CPU 或故障域。

03 / 消息交付路径

用就绪集合找有消息的通道，避免轮询全部订阅

Producer 写消息→CommitLog + LMQ 索引→Broker ready set→按 client POP→消费结果 / ACK
为什么它适合大量闲置、少量活跃的会话

Broker 跟踪组、client 与子通道订阅；通道有可消费消息时进入事件就绪集合。客户端面向自身身份获取多个通道的消息，不必对数千个空通道逐个发起拉取。

当就绪集合达到上限，或实例不活跃时

实现保留限额、重新扫描和重新分发路径。同组有多个订阅者时，可选择其他 client 接收。事件机制不意味着无限内存、永久实例亲和，或固定毫秒级故障恢复。

发送确认、Broker 存储、消费确认、业务结果和浏览器收到输出，是不同阶段。消息层无法直接证明一次工具调用成功，也无法使任意外部系统与 ACK 原子提交。

05 / 起读与恢复

第一次订阅，不能依赖默认起点恢复历史

5.5.1 的 POP 路径在某个 group + LMQ 没有消费位点时，传入 MAX 模式，但复用的初始化方法通常取 maxOffset−1（最后一条）；若首条仍在内存且相关条件满足，则可能取 0。先生产历史消息、随后用新消费组订阅，不能依赖这个冷热相关的默认行为。相同组的已有位点可用于实例换手；换组则是另一份消费进度。

起读选项固定版本需注意
未显式设置默认路径通常从最后一条；满足内存条件时可能从 0
显式 MAX订阅配置将位点设为当前队尾，与缺省 POP 初始化路径要区分
MIN / 指定 OFFSET可用于明确历史起点；受实际保留范围限制
TIMESTAMP相关 Broker 分支注明暂时静默禁用，不能宣称可按任意时间回放
TAIL_N该分支依赖已有位点，并从当前消费位点减 N；不是通用“最新 N 条历史”承诺

断线恢复推演

同一个 group + 未被清理的 LiteTopic

可从组位点继续消费；仍需检查“Broker 已 ACK”与“浏览器已展示”的差距。

网关消费位点 ≠ 用户已收到的位置。若网关写出 SSE 后立即 ACK，浏览器未收到时发生断线，下一网关从组位点接管仍可能跳过这段。需要应用 eventId / 序号、客户端游标和可重放历史；不能只保存一个 sessionId。

06 / 订阅与所有权

Shared、Exclusive 都不能代替业务执行 fence

Shared

默认允许同组多个 client 持有同一子通道订阅，竞争消费。不能把同组多个浏览器网关看成各自获得全量副本。

Exclusive

同组同子通道由一个 client 持有订阅；新订阅可逐出旧 client。5.5.1 通过 Broker 内存 tombstone 阻止被逐出实例继续 POP。

位点按 group 管理。固定版本 reset-on-exclusive 与 reset-on-unsubscribe 默认关闭，换手通常保留组进度；不要随意重置正在工作的共享组位点。

如果旧 owner 已经拿到了任务，即使其后被禁止 POP，也可能继续执行 shell、数据库写入或模型调用。Exclusive 处理消息交付归属；真正的会话推进仍需应用租约、owner_epoch、结果提交条件和稳定 operationId。

同一个会话有两个观察者怎么办

同组订阅是工作分配语义，不保证两个观察者都看到全部内容。可通过一个后端消费入口向多个浏览器广播，再用业务历史服务补读；或者设计不同消费组并承担位点与订阅资源成本。

07 / 重试与限流

Suspend 当前消息，意味着它还没有成功 ACK

Java LitePush 返回值5.2.2 的处理路径应用意义
SUCCESSackMessage在要求的业务结果提交后返回
FAILURE按策略本地重试，耗尽后进入 DLQ 转发路径必须接受重复尝试，并处理最终失败
ConsumeResultSuspendchangeInvisibleDuration；不 ACK 当前消息延后交付，可能重复调用 listener

Java Suspend 最短为 50ms。FIFO 服务还会暂停当前批次中同 LiteTopic 的剩余消息。它让单通道退让，不是自动实现跨机器的全局 GPU 配额、公平调度或任务取消。

官方限流示例需要结合确认语义阅读。

示例先执行 processMessage，成功后可能返回 Suspend。固定 Java 路径没有同时 ACK，因此非幂等业务可能再次执行。更稳妥的设计是先做容量准入，未获容量时 Suspend；已提交结果返回 SUCCESS，并对重试窗口做幂等处理。

listener(message):                         # 设计伪代码，不是可直接运行的 SDK 示例
  if operationAlreadyCommitted(message.operationId): return SUCCESS
  if !capacity.tryAcquire(message.tenantId): return SUSPEND
  try:
    result = executeWithStableOperationId(message)
    if !commitResultIfOwnerEpochMatches(result): return FAILURE
    return SUCCESS
  finally: capacity.release(message.tenantId)

长任务不宜无条件占住消费回调直到完成。可以先可靠登记任务再 ACK，由独立执行器推进；这要求任务账本承担后续恢复。若选择工作完成后 ACK，则要验证不可见时间、续租、重投与 owner 协调。

08 / 生命周期

空闲 TTL 不是消息保留期，也不保护积压

lite.topic.expiration 以分钟配置，默认 -1 关闭空闲清理；正值的上限为 43200 分钟。5.5.1 清理器按最后入库时间判断空闲，并通过扫描执行，因此到期不是精确计时触发。

最后一条消息入库→ 空闲时间超过阈值 →扫描清理 LMQ→CQ / 组位点 / order info / 订阅删除

关键实现是 hasConsumerLag() 直接返回 false：未消费积压和仍存在的订阅，并不构成清理保护。删除轻量索引也不能据此推断共享 CommitLog 的所有物理消息立即擦除。

短暂响应通道

可按最大离线恢复窗口设置 TTL，处理超时 / 已清理状态，并让客户端看到明确的恢复结果。

长期会话历史

另设持久历史与归档策略。关闭 Lite TTL 也不会自动关闭消息存储层的保留清理，或给出无限容量保证。Broker 还默认有 15 分钟最小保护与 2 分钟扫描；存储时间持续读取失败另有清理兜底分支。

09 / 隔离与容量

子通道有边界，租户 ACL 仍要实际验证

领域文档提出细分身份与权限；但固定版本 gRPC 的 SyncLiteSubscription 授权检查针对父 Topic 与 Group，没有独立核对子 LiteTopic 的资源权限。把租户 ID 写进名字不会自动阻止另一个具备父级权限的调用者订阅它。

应用应在网关从已认证身份构造目标通道，并核对用户、团队、会话 ACL；避免任意传入子通道名、组名或通配订阅。若业务需要 Broker 直接承担子级授权，必须验证自己的授权扩展与负向测试。

容量维度需要观测什么
通道数存活 / 创建 / 删除速率、CQ 与 offset 元数据、RocksDB 内存
订阅数组属性默认每 client 2000，Broker 总活动订阅引用上限默认 100000；通配展开、ready set 与扫描成本
吞吐活跃通道数、热点通道、batch 与共享线程池排队
恢复重连订阅延迟、积压恢复时间、位点保留与已清理响应
业务首 token / 完成时间、duplicate / unknown、跨租户拒绝

“百万 LiteTopic”是官方能力目标，不是本项目测出的并发活跃任务数、吞吐或故障 SLA。逻辑独立索引共享底层资源，热点、存储和线程池仍可能互相影响。5.5.1 有 lag count / latency / collect 开关，默认关闭；积压年龄并不等于工具执行耗时或端到端 token 延迟。任务处理延迟与用户端补读完整性需要应用埋点。

10 / AI 场景

三种用途，三份不同的状态责任

会话输出 / 网关换手

每个 session 一个通道，网关可换实例接管。应用继续保存 transcript、用户游标和事件序号；后台推理要独立于浏览器连接。

依据：官方 session 方案；完整恢复约束为本报告分析。

用户 / 模型维度准入

按用户或任务类别组织通道，容量不足时只暂停目标维度。全局配额与公平性由共享容量服务判断；Suspend 要放在副作用前。

依据：限流方案与固定 SDK 语义。

Supervisor / Worker 响应

普通请求 Topic 分配工作，Lite 响应通道按 taskId 收结果。Supervisor 保存期望子任务集合、完成状态、超时与去重，不能把“收到几条消息”当成编排完成。

依据：multi-agent 方案；编排责任为本报告分析。

不自动恢复的状态

模型上下文、工作目录、工具凭据、沙箱快照与外部副作用都在消息层之外。还需要 Harness、业务状态存储和 CubeSandbox。

这是对当前项目职责边界的推断。

每 token 一条消息并非必选。可以按时间或字节微批，携带 turnId、eventSeq 与 final 标记；在首 token 延迟、存储成本和可重放粒度之间做实测。消息大小、token 速率和活跃会话比例比总通道数更能说明实际负载。

11 / 与现有专题对照

LiteTopic、JetStream、Durable Streams 应按消费契约比较

问题RocketMQ LiteTopicNATS / JetStreamDurable Streams
核心组织父 Topic 下大量动态子通道Subject、Stream、ConsumerURL 寻址的 HTTP 流
工作分配组位点、Shared / Exclusive、POP 与 ACKDurable consumer、pull、ACK 与重投普通读用客户端游标；subscription 扩展另看实现
浏览器补读应用网关转换 SSE / WebSocket；组位点不等于 UI 游标NATS WebSocket 协议或应用网关普通 HTTP catch-up / live 读取更直接

比较依据：本报告固定 RocketMQ 证据 · NATS / JetStream 专题 · Durable Streams 专题。适用性判断是分析建议。

12 / DSH 接入设计

先实验响应通道，再评估任务交付与全局治理

当前 DSH + CubeSandbox 尚未接入 RocketMQ。本节是可评审方案，优先验证网关换手与后台任务解耦，避免直接替换全部任务和会话存储。

浏览器：sessionId + lastEventSeq↔已鉴权网关 / 历史补读↔Lite 响应通道←DSH owner → Cube 工具
{
  "eventId": "stable-business-event-id",
  "tenantId": "tenant-A",
  "sessionId": "session-123",
  "turnId": "turn-456",
  "eventSeq": 42,
  "operationId": "stable-tool-operation-id",
  "ownerEpoch": 7,
  "type": "tool.result",
  "payload": {"status": "committed"}
}

示意 envelope；MQ messageId、业务 eventId、组位点、浏览器 eventSeq 与 ownerEpoch 各有不同用途。

  1. 先定权威：持久业务记录管理会话、turn、结果与所有权；用 outbox 或明确的协调方案发布事件。
  2. 先订阅再启动：在起点与消费组准备完成后启动实验任务，验证新组缺省、显式 MAX 与历史 MIN 三种路径。
  3. 控制 ACK 窗口：不要将网关写出成功当成用户确认；历史服务按业务序号补缺。
  4. 独立执行生命周期：断线只取消转发订阅，后台任务继续；用户显式取消由任务协议执行并落状态。
  5. 验收后再扩展：测出重连、热点、幂等和容量行为后，再讨论任务队列或跨节点 owner 切换。

应当执行的故障与负载实验

  1. 预先写消息，用新组默认起点 / MIN 订阅；检查起点与实际历史。
  2. 同组网关 A 退出、B 接管；在 SSE 写出前后和 ACK 前后断线，核对最终浏览器事件完整性。
  3. Exclusive 换手后，让旧 owner 继续已取得的工具任务，验证业务 epoch fence。
  4. 在含积压、仍有订阅的通道上触发空闲 TTL，检查删除与恢复错误。
  5. listener 成功后返回 Suspend，记录调用次数；再验证准入前 Suspend 与幂等提交。
  6. 测试 FIFO / Standard、失败重试、最终 DLQ、长任务不可见时间与重启恢复。
  7. 测试跨租户子名、通配订阅、超配额、ready set 溢出，以及 Broker 故障切换。
  8. 分别测总通道数、活跃通道比例、单通道热点、RocksDB 资源和端到端输出延迟。
