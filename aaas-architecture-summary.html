Agent as a Service：一套架构同时服务个人和企业

Personal Agent 要在用户离开后继续工作，企业智能体要在内网和沙箱之间调度工具、等待人工确认。两者的共同要求是：Agent 的身份、任务状态和长期积累，不能绑定在某个客户端、某个进程或某个执行环境上。

一句话：把“持久的任务状态”“按需运行的计算”“可切换的执行环境”拆开，再用稳定的任务标识和执行协议连起来。ByClaw 已经走在这条路上，文章也印证了我们接下来要补的稳定性工作。

01核心区分：Harness 在沙箱里面还是外面

判断标准只有一个：Agent 循环实际在哪里运行。文章选择 Sandbox as Tool 作为服务化路径，但也说明这不是唯一答案，要看任务与环境的耦合程度。

对比Agent IN SandboxSandbox as Tool
做法Agent 和工具都装在同一个沙箱Harness 在服务端，需要动手时调用沙箱
适合高度依赖现有 CLI、复杂工具链、大量本地操作需要分别调度、长期运行的托管服务
资源调度推理和环境生命周期绑得紧可以按负载分别调度
长期状态要从环境里提取并外置围绕独立的任务记录组织
权限要区分运行组件和生成代码的权限可在远程工具边界集中检查，模型凭据留在沙箱外
代价同时判断进程和环境的状态多了网络交互，要明确工具到底执行了没有

02整体架构

四个可以组合的层次

  • ① 远端托管 Harness：客户端断开后，任务仍由服务继续。
  • ② 本地与远端交接执行：在检查点确认原执行者退出后，另一端取得执行权续做。
  • ③ Context 和 Memory 上云：状态和长期积累跨越单个 Harness 实例的生命周期。
  • ④ Brain 和 Hands 分离：工具按能力、权限和数据位置路由到本地、云端或内网。

03最值得借鉴的：长任务怎么挂起和恢复

等工具、等人工时不占推理资源，靠的是一条持久化的执行协议。

  1. 受理

    持久保存输入、会话和任务标识、配置版本；网络重试沿用同一请求标识。

  2. 启动推理

    调度层先取得执行权，再加载状态，由 Harness 推进。

  3. 派发工具

    检查权限，保存参数和稳定执行标识，再交给执行层。

  4. 保存等待

    工具耗时长时，保存检查点和待等待的工具集合，确认落盘后挂起并释放推理资源。

  5. 恢复

    结果保存后通知调度层，核对等待条件，取得执行权，合并结果后继续。

  6. 交付

    保存终态、回复和产物。浏览器断开不影响任务状态。

两个容易忽略的点

  • 聊天历史不够恢复：它分不清工具是还没派发、正在跑，还是已返回但没进入下一次模型输入。
  • 外部动作要保留 unknown：超时后工单可能已经建了。按执行标识查询，或转人工，不要直接重做。

04个人和企业复用同一套基础

维度Personal Agent企业事件驱动 Agent
服务对象个人及其持续目标团队、岗位或业务流程
触发对话、定时任务、用户授权的事件告警、消息、单据、业务状态变化
长期信息个人偏好、项目和工作记忆业务知识、规则、历史处理经验
人工参与补充要求、确认动作按角色和流程复核、审批
结果可继续使用的文件和任务结果可核验的业务产物和状态变化
