新数据流 · 第 1 步详解

发出消息：一条消息怎么只算一次

ByClaw 已经有 trace id，不需要再造一个贯穿全链路的新编号。缺的是两件事：把现有编号接到 DSH 已有的去重上，以及宿主重启后有人把这条命令接起来。

结论：trace id 足够标识“这一轮”，BE 之后全程用它，宿主再由 messageId 派生稳定消息 ID，重投时查日志和队列，不多开一轮。它防不了到达 BE 之前的重复，这一段用前端已有的 clientRequestId；同一提问的多次回答用 interaction_id；工具调用用 DSH 的 callId。

01现有的编号各管什么

这些编号都已经有了，不需要新增。

编号谁生成标识什么在新流程里的用途
clientRequestId前端，每次发送新生成用户的一次发送动作BE 入口去重。用户手动再发一次是新的编号，算新消息，这是对的
trace idBE，由用户消息 ID 和回答消息 ID 编码而成这一轮对话账本里“这一轮”的键；断线找回、停止都用它
messageId（回答消息 ID）BE这一轮的回答命令重投时不变，by-framework 已按它跳过已结束的执行。同时派生 DSH 的稳定消息 ID，宿主查“已落盘日志 + 队列”去重，重启后仍有效
interaction_id宿主，发起提问时一次“等你回答”回答去重：第一份生效。同一轮的多次回答共用 trace id，不能靠 trace id 区分
callIdDSH，模型发起工具调用时一次工具调用传给自有工具作幂等键。只在宿主和工具之间用，不穿过 BE 和 Redis

02现在和以后差在哪

前半段几乎不变，改动集中在宿主收到命令之后。命令一直留到结局落盘才确认，正好给续跑器当待办清单。确认不能提前：消息要过完预处理才写入日志，提前确认会真的丢消息。

03出问题时怎么走

情况现在以后
写入 Redis 后、开始处理前宿主崩溃命令卡在待确认列表，新进程同名，不会重新领取；一直转圈续跑器扫描到这条命令，按稳定 ID 查日志和队列，都没有才按新命令处理
写入日志后、确认前宿主崩溃没有这一步续跑器发现已有绑定记录，按日志判断接下来怎么做，稳定 ID 保证不多开一轮
执行到一半宿主崩溃同样一直转圈；DSH 只在有人打开会话时才补上中断结尾，不会继续续跑器打开会话，这一轮被标记为中断；新起一次尝试并附恢复说明，次数到上限就明确失败。未完成的工具交给模型判断
同一提问的回答提交三次多余的恢复命令失败，可能让这一轮被提前收尾按 interaction_id 匹配，第一份生效，其余返回“已收到”，不发结束事件
用户看不到回复，手动再发新的 clientRequestId 和 messageId；这一轮还在跑时，多数被“会话运行中”挡回不变。这是用户的新动作，不应被当成重复
发送时断线前端最多等 10 秒重连，失败就把这条回答标为取消，不自动重发不变。以后如果加自动重发，必须先做下一节的入口去重

04要改什么

阶段 0

不改架构

宿主启动时扫描上一代遗留的命令，明确报失败并确认。接上稳定消息 ID 和查重。已消费的提问回答当作重复处理，不发结束事件。

阶段 2 和 3

续跑与索引

阶段 2 写绑定记录，续跑器接上遗留命令。阶段 3 由 BE 维护索引，Redis 丢失时重投未结束的轮次。确认时机不变。

按需

加自动重发时再做

BE 入口按“会话 + clientRequestId”记下已分配的 trace id，同一帧再来就返回原来那一轮。现在没有自动重发，不急。

还没确认的

  • 钉钉等第三方渠道进来的消息有没有稳定的 clientRequestId，是否会重复投递。
  • 前端帧已发出、BE 没收到时，前端是否有超时提示。
  • 用户消息是 BE 内存队列约 500 毫秒批量入库，和命令写入 Redis 的先后关系；BE 恰好在这时崩溃，可能出现有命令、没有用户消息的情况（推断）。
