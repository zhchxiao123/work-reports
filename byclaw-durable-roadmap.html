ByClaw · Agent 链路 · 稳定性

让 ByClaw 的每一轮对话“不丢、不卡、不重”

拆分完成后，对话在共享宿主里，工具在每个人的工具沙箱里。组件多了，任何一个重启、断线或重复投递，都可能让一轮对话卡住或答一半。本规划借鉴 Pi Durable 的思想，并按 DSH 最新版（0.2.2-alpha.2）的代码重新核对：DSH 已经做了很多，我们只补它缺的“进度”这一层，逐步演进。

结论：不换 Harness，也不另建一份内容存储。DSH 的会话日志已经记下“说了什么、做了什么”，也能在恢复时收尾；它缺的是“重启后谁来接着做”。所以账本 = DSH 日志 + 我们补的进度记录。先止血，再升级 DSH，再补进度和启动续跑；多宿主和独立流服务等真实需求出现再做。

01目标：稳定是什么意思

对用户来说，稳定就是下面四句话。后面每一项改动都对应其中一句。

不丢

说过的话、给出的回答、做过的事，任何一个组件重启后都还在，能接着做。

不卡

每一轮对话一定有结局：完成、失败或等你回答。不会无限转圈。

不重

同一条消息、同一个回答提交几次都只算一次；有副作用的命令不会被悄悄再执行。

说得清

出了问题能告诉用户发生了什么、要不要重试；运维能查到每一步的状态。

02现在的链路与问题

一轮对话经过前端、BE、Redis、共享宿主、工具沙箱五站。问题不在某一站，而在于“这一轮做到哪了”没有一个地方说了算。

#问题根因违反
1宿主重启时，进行中的一轮永久挂起命令留在待确认列表，新进程沿用同名 worker，又跳过“自己的”待确认命令；DSH 的恢复只在有人打开会话时发生，而且只收尾不续跑，启动时没有人去扫描；BE 对一轮没有超时不丢 · 不卡
2同一个提问的回答重复提交，这一轮可能被提前结束“等你回答”不是持久的等待；多余的恢复命令失败后发出结束事件，BE 见到结束事件就收尾不重 · 不丢
3委派、团队任务卡住时一直转圈闸门只有“5 分钟提醒一下”，没有失败出口不卡
4Redis 出问题就丢在途的回答，事件写失败被静默吞掉Redis 既当通道又当事实来源不丢 · 说得清
5沙箱丢了，正在跑的命令没有明确交代DSH 已在执行前落盘工具调用，恢复时能告诉模型“结果未知”，但进程内丢失沙箱和重启后的处理没有串起来；SSH 命令没有幂等键说得清 · 不重
6同一帧重复到达 BE 会被当成新消息trace id 在 BE 收到后才生成，入口没有按前端已有的 clientRequestId 去重。现在前端不自动重发，风险不高，加自动重发前必须解决不重
7前端断线重连靠快照替换加自己去重服务端没有“从第 N 条继续”。DSH 自己的客户端也是重连后重取快照，所以这不是急需解决的问题不重
8宿主正常停机时，排队的消息可能被清空（读代码推断）DSH 优雅停机走取消流程，会清掉排队输入；进程被直接杀死反而保留不丢
9共享存储挂住时，可能拖住整台宿主（读代码推断）写日志的 fsync 没有超时，一个用户的存储卡住可能占满公共线程池，影响同宿主的所有人不卡
已经做得好的部分演进时要保住：BE 重启后的接管与快照重建、最终事件的去重、宿主重启后提问的冷恢复、worker 重新拉起。

03Pi Durable 给我们的思路

Pi Durable 是 Pi 编程助手团队开源的“持久 Agent 运行库”（npm 1.4.0，仍标 Experimental）。它要解决的正是上面这类问题：进程随时会死，Agent 要能接着干。我们不搬它的代码，借它的四条契约。

①

先落盘，再可见

“Only committed state is observable.”

所有变化走一条原子提交线：用户输入、模型回答、任务状态、业务数据在一次提交里落盘，落盘之后才推给任何人看。界面只渲染已提交的状态，不靠拼事件。

→ ByClaw：实时文字可以先显示（DSH 也如此），但结局要等落盘后才算数；Redis 只当通道。

②

先记意图，再动手

提交意图 → 执行 → 提交结果

工具执行前先提交“要做什么、参数是什么、能否安全重跑”。崩溃后，只有声明“可安全重跑”的工具才重跑；其余给模型一个“被中断、可能已部分执行”的结果，由模型判断。

→ ByClaw：DSH 已经做到，工具调用落盘后才执行，恢复时模型会收到“结果未知”。我们只需把它串起来。

③

任务有状态，重启接着跑

pending · running · waiting · sleeping · completing · terminal

一轮对话、一次模型调用、一次工具调用、一个子任务都是带检查点的任务。重启时 running 回到 pending 继续；waiting（等用户、等子任务）原样保持。反复崩溃到上限就明确失败，不无限重试。

→ ByClaw：这是 DSH 缺的部分，也是我们的主要工作：启动时找到没做完的轮次，决定续跑或明确失败；每轮一定有结局。

④

一份账本只有一个主人

“One process owns a storage at a time.”

同一份存储同一时间只由一个进程打开，别的客户端连到这个进程。它不提供锁和接管，这部分要应用自己做。

→ ByClaw：单宿主时 DSH 的文件锁够用；多宿主要自己做带纪元号的租约，因为文件锁在 NFS 上不可靠，也没有 fencing。

为什么不直接换成 Pi Durable

借契约，不搬代码
  • 它自带模型循环：换上等于替换 DSH，连带所有插件。
  • 还是实验版本：主线有未发布的破坏性改动，事件接口刚刚重做。
  • 远程执行不合适：它的 SSH 执行端在断线时会杀掉进程，和我们沙箱随时释放重建冲突。
  • 缺几块：没有工具审批、没有删除会话、没有等外部信号的原语、没有跨进程锁。

它也明确不保证的事

我们同样不承诺
  • 外部副作用只执行一次：库只给任务编号和记忆，幂等要工具自己做。
  • 机器掉电不丢最后一次提交：取决于存储，SQLite 默认配置下可能丢。
  • 多个进程同时写一份账本：明确不支持。
  • 强行终止不配合的代码：卡住的工具只能靠取消信号和超时。

04架构怎么一步步演进

不是一次切到终态。每一步都是当时投入产出最好的形态：可以单独上线，停在这里也合理，下一步不推翻上一步。阶段 0 到 3 是必做的，阶段 4、5 等真实需求出现再做。每个阶段的内容和进入条件见第 06 节。

账本分两层

内容已有，只补进度

“说了什么、做了什么”继续在 DSH 日志里，不复制。我们补的是“做到哪了、还欠什么”：进度记录随日志一起写，每轮状态写一行索引。账本怎么贯穿系统 →

实时文字不进账本

快的可丢，慢的不丢

流式文字走 Redis 直接显示，半截丢了就按“开始新尝试”重新生成，所以不用写检查点，账本也不用扛这部分压力。完整回答由 DSH 落盘，结局落盘后才发出。

为什么不是每用户一份 SQLite

也不用完整的账本表

SQLite 的 WAL 模式不能放在网络文件系统；放宿主本地盘，宿主宕机后别人接不了。索引放 BE 已有的数据库，一轮只写几行，压力很小。

什么时候才上独立流服务

出现任一情况再评估 Durable Streams、NATS JetStream、S2 等
  • Redis 成为瓶颈：压测或线上证明容量、连接数不够。
  • BE 负担过重：按会话消费流已经影响其他业务。
  • 多方读同一条流：除前端外，钉钉等渠道也要按序号读取。

现在先不做按序号续读：DSH 自己的序号在崩溃后可能被复用，不能直接当游标，它的客户端也是重连后重取快照。我们保持快照 + 水位，真到这一步再由流服务提供序号。

有两种走法不考虑

看起来更简单，实际代价更大
  • BE 直接轮询账本取文字：流式文字频率高，延迟也差。索引只用于看结局和对账。
  • 前端或 BE 直连 DSH 的客户端协议：宿主要直接面对外网，多宿主时要知道用户在哪台，BE 还要用 Java 重写它的多路复用逻辑；下行缓冲也没有上限，一个慢客户端可能拖累同宿主的其他用户。

一人多沙箱是另一条线，不依赖账本，可以按业务需要并行推进。

05一轮对话的新数据流

按一轮对话的先后顺序，逐步对照今天和以后。

  1. 发出消息入口

    今天：BE 生成 trace id，把命令放进 Redis；宿主重启后这条命令卡住。

    以后：不新增编号。宿主用 rpcId = messageId 把消息交给 DSH，并写一条进度记录绑定这一轮；重投时 DSH 认得这个编号，不多开一轮。

    详解结合 ByClaw 看这一步怎么走 →
  2. 忙时又来一条排队 · 插话

    今天：排队靠宿主内存里的队列。

    以后：继续用 DSH 的 followup / steer。它的排队区是持久的，进程崩溃后还在；但优雅停机可能清空它，这点要先解决。

  3. 调用模型生成

    今天：重试时，新文字可能接在半截旧文字后面。

    以后：DSH 已有重试和尝试事件：失败的尝试落盘后发新一次。宿主把这个信号传下去，前端替换这一步未完成的文字。崩溃时半截文字不保留，由续跑重新生成。

    详解重试时前端怎么不重复 →
  4. 执行工具先记意图

    今天：进程内失败和重启后的处理没有串起来。

    以后：DSH 工具调用落盘后才经 SSH 执行。宿主重启后，未完成的调用会变成“结果未知”或“未开始”交给模型，模型先检查再决定。我们把 callId 作为幂等键传给自己的工具，并给工具加统一超时。

  5. 等用户回答持久等待

    今天：重复提交可能提前结束本轮。

    以后：继续用现有的 Redis 状态。重复或已消费的回答当作重复处理，不发结束事件。这里不换 DSH 的提问机制，因为它不支持委派出去的子 Agent 提问。

  6. 委派与团队归属与失败出口

    今天：闸门只提醒，不失败；父子关系只在进程内。

    以后：模板委派改用 DSH 的 waitForChildren，团队闸门保留并加时限。用户停止时取消向下传播；超时以失败结束并带回已完成部分。宿主重启后，由续跑器按日志判断子任务状态（父子关系不持久，这里最难）。

  7. 回到前端出口

    今天：BE 收到结束事件就收尾；事件写失败被静默吞掉。

    以后：实时文字经 Redis 推送。最终答案要等日志落盘成功才发出。断线重连继续用快照 + 水位；Redis 丢了，BE 向宿主要已落盘的内容重建。阶段 3 起 BE 看轮次索引的结局收尾。

  8. 宿主重启启动续跑

    今天：没人接手，一直转圈。

    以后：续跑器启动时扫描自己名下未确认的命令，打开对应会话对照日志：已完成就补发结果；在等用户就继续等；被中断就按策略续跑或明确失败；反复崩溃到上限直接失败。

06路线与进入条件

每一阶段都能单独上线、单独验收。做完一步，看进入条件，再决定下一步。

阶段 0止血约 2–3 周 · 不改架构
  • 宿主启动时扫描上一代留下的未确认命令，这一轮明确报失败并确认，不再一直转圈
  • BE 给每轮设兜底超时
  • 重复或已消费的提问回答不再发结束事件
  • rpcId = messageId 入口去重
  • 模型重试时前端不重复
  • 委派、团队闸门加时限；事件写失败不再静默吞掉
  • 核实两个推断：优雅停机清队列、共享存储挂住；确认存储的挂载方式
解决问题 1、2、3、8、9 的用户可见部分下一步：阶段 0 的故障场景全部通过
阶段 1升级 DSH 到最新版约 2–3 周 · 含验证
  • Node 升到 24.9 以上
  • 迁移模型选择到新接口（确定不兼容，影响每轮选模型）
  • 修复其他接口差异，核对多用户宿主的配置覆盖
  • 跑能力对齐探针，确认存量会话能打开
代码基线一步到位，还能用上新的定时任务恢复等能力下一步：能力对齐探针全部相同
阶段 2进度记录与启动续跑约 3–4 周
  • 每轮开始写绑定记录（命令、trace id、沙箱），不加新存储
  • 启动续跑器：已完成补发、被中断按策略处理、等待继续等待
  • 自建重启计数，到上限明确失败；续跑前再确认凭证、审批和外部动作
  • callId 传给自有工具作幂等键
  • 模板委派改用 waitForChildren
  • 运维可查：按用户和会话看每轮进度
解决问题 1、5；“不丢、不卡”从兜底变成机制下一步：宿主重启场景通过
阶段 3轮次索引，BE 以账本为准约 2–3 周
  • BE 数据库加一张轮次表，宿主写、BE 读
  • 结局落盘后才更新；BE 按索引收尾，取代“收到结束事件就关闭”
  • 进入索引后就确认 Redis 命令，命令只负责送达
  • Redis 丢失时 BE 向宿主对账并重建快照
  • 入口按 clientRequestId 去重（前端加自动重发时做）
解决问题 4、6；Redis 退回通道下一步：单宿主的容量或故障影响面成为实际限制
阶段 4多宿主有条件 · 与宿主池方案合并
  • 用户 → 宿主的租约放进索引，带纪元号
  • 新宿主拿到租约后按阶段 2 的规则续跑
  • 会话写入前校验纪元（需要实现 DSH 的存储接口，文件锁不够）
容量能横向扩；单个宿主故障只影响片刻下一步：出现独立流服务的任一触发条件
阶段 5独立流服务有条件 · 没有触发就不做
  • 选型：Durable Streams、NATS JetStream、S2 等，先用真实流量比较
  • 新旧通道并行一段时间，再下线 Redis 上的实时流
解决问题 7；实时流可独立扩容，多方读取同一条流

工期为粗估，以 1–2 人投入计，需在阶段 0 结束后复核。阶段 4、5 的工期等触发后再估。阶段 1 确定的不兼容只来自抽查，没有做完整的类型检查，实际工作量可能更大。

08需要定的事

  • 宿主重启后，被中断的一轮要不要自动续跑：DSH 会要求模型先核实“结果未知”的工具，但外部副作用仍可能重复，而且研究也指出正确恢复不等于安全恢复。建议先做成“只读类任务自动续跑、其他明确提示用户”，续跑前确认外部动作是否发生过，这需要你定。
  • 宿主彻底挂了谁来标失败：建议保持宿主是唯一写者，BE 只在展示层用兜底超时标失败，宿主恢复后再对账。
  • 先止血还是先升级：建议先止血，2–3 周内消掉最常见的“一直转圈”；这些修复基本与 DSH 版本无关。
  • 升级跟 alpha 还是等正式版：最新是 0.2.2-alpha.2，要求 Node 24.9 以上。建议在验证环境先跟，线上等 rc。
  • 阶段 0 的范围：“模型重试时前端不重复”要同时改宿主、BE 和前端，放在阶段 0 还是单独排。
  • 失败的产品表现：一轮多久没进展算失败；失败时用户看到什么。
  • 上游协作：优雅停机清队列、输入被取走但还没写日志的窗口，这两处要改 DSH core，是否提 PR。
