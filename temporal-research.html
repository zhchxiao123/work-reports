02

四个关键组件

Server 存历史、维护状态并分派任务；真正的业务代码运行在 SDK Worker。

Frontend

对 SDK 的 gRPC 入口。接收启动、交互与 Worker 请求，连接内部服务。它不是执行你的 Agent 代码的进程。

History

每个 Workflow Execution 有追加事件历史与持久 Mutable State；History shards 管执行状态、计时器与后续任务。

Matching + Worker

Matching 管 Task Queues，Worker 轮询并回传命令或结果；多个 Worker 可消费队列，恢复不依赖固定进程活着。

官方依据：History 职责

静态源码证据

service/matching/service.go 注册 Matching gRPC 服务、健康状态与 membership；停止时先退出成员环、标不健康、等待流量收敛，再停止 handler 与 gRPC。这说明服务生命周期需要 drain，不能只 kill 一个进程就视为平滑负载均衡。

03

如何恢复：重放不是重跑所有副作用

Workflow 是确定性控制逻辑；Activity 承担网络、模型、文件与业务副作用。记录已完成 Activity 的结果供重放使用。

Activity 在“外部动作成功、完成结果尚未回报”之间崩溃，可能被重试。必须有幂等键、外部结果查询或明确非重试策略；Temporal 不能自动令任意外部副作用 exactly-once。

官方依据：Event sourcing、确定性与副作用要求

04

Agent 怎样接入

推荐把一次可恢复任务建为 Workflow，把模型与工具阶段建为 Activity；不能直接在 Workflow 内运行非确定性的模型 SDK。

模型循环

一次推理返回结构化计划，Workflow 决定调度哪些工具。不要把模型生成结果或时钟、随机数当可随意重放的 Workflow 逻辑。

交互与取消

应用通过 SDK 提交交互与取消；Activity 必须配合 SDK 心跳和取消机制，停止 Workflow 不保证远程 shell 自动停止。

数据与版本

大文件与视频放外部存储，历史记录引用和摘要；长期 Agent 需要控制历史增长及 Workflow 代码兼容，不能无限堆上下文。

05

对 DSH 多实例有什么帮助

Temporal 提供执行调度与恢复底座，但不是通用 HTTP sticky-session 代理，也不是沙箱管理平台。

能帮助

异步任务接入、任务队列、步骤重试、等待与事件历史，使任务不必绑死在一个 API 进程。

仍需 owner

现有 DSH ctx、运行 Agent 和取消句柄在进程内。若整个 DSH turn 放一个 Activity，turn 内崩溃仍需 DSH checkpoint 或标记 unknown。

仍需 Cube

工具执行隔离、文件持久化、B 生命周期由 Cube 或其他执行平台负责；Workflow 不能替代 PVM。

Workflow 状态恢复、DSH 对话上下文恢复、工具沙箱恢复是三种不同能力。第一阶段不要把“上了 Temporal”当成三种恢复都已完成。
06

第一轮实验与部署取舍

先验证小工作流，再评估引入 Server 与数据库的运维成本。

闭环

用受控模型 + 测试工具分成 Activity；任务完成后检查历史和产物，不仅看 Worker 日志。

故障注入

在模型完成后、工具副作用成功后但提交前、等待用户输入期间杀 Worker；验证重复执行、恢复与取消。

边界
