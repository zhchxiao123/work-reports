NATS 与 Durable Streams
相似的是持久流，边界不同

从消息路径、消费确认、重放、复制和租户隔离，判断它能否成为 DSH 的事件与任务交付底座。

调研：2026-10-13Server v2.15.1固定源码核对未运行验收
结论先行

NATS 是消息系统，JetStream 是其中的持久化与消费状态层。它与 Durable Streams 都能保存并重读事件；JetStream 更直接承担服务间消息、worker 消费与重投，Durable Streams 的普通读取路径更直接面向 HTTP 客户端和断线补读。

两者都不替代 Agent 运行时、业务授权、外部副作用幂等或沙箱生命周期。DS 的 subscription 扩展必须与普通 GET/SSE 分开比较。

01 / 比较对象

先拆开 NATS 的三层能力

Core NATS

按 subject 发布订阅、request/reply、queue group。实时交付为 at-most-once；没有订阅者接收时，Core 本身不保存历史供以后重放。

JetStream

启用后的存储与交付层：消息进入 stream，consumer 管读取与确认。正常 ACK/重投模型为 at-least-once，需要应用接受重复尝试。

KV / Object Store

在 JetStream 上提供不同数据访问模型。它们扩展消息底座的用法，不代表关系型事务、用户文件权限或业务数据库都已解决。

Durable Streams

本页指 durable-streams/durable-streams 的 HTTP 流协议；不是 JetStream 的 durable consumer，也不是 S2 的另一种叫法。

依据：NATS 概念 · JetStream · DS 概念

02 / 消息路径

消息被保存，与工作被完成是两回事

Publisher → subject→Stream leader / store→PubAck：stream + sequence
Consumer 选择记录→Client / worker 处理→Consumer ACK

发布到匹配 subject 后，JetStream 为消息分配 stream sequence。使用 JetStream 发布 API 才能等待 PubAck；仅使用普通 Core publish，即使消息被某个 stream 捕获，也不能把发送返回当成存储确认。

PubAck 不等待消费者完成工作。处理结束后，消费者另发 ACK。若请求超时或回执丢失，结果可能已经生效，应以稳定身份重试或核对，而不是直接判定失败。

Publishing / PubAck

03 / 状态模型

Subject、Stream、Consumer、Client 各管什么

对象职责必须区分
Subject消息寻址与过滤；支持层级和通配匹配命名不是业务授权，需 account 与权限配合
Stream保存选定 subjects，配置存储、保留与副本一个 stream 的序号与另一个 stream 不共用顺序
Consumer过滤、交付、未 ACK 状态与重投durable 是固定身份与可恢复状态，不是“永久不删数据”
Client拉取或订阅、处理、确认多个 client 共用一个 consumer 可分工，不是每个都收到全量

多个 consumer 可独立读同一 stream。stream sequence 指向存储记录，consumer sequence 记录交付进度，重投不能当成新增业务事件。起读策略与重放速度也是两个选择：从全量、新消息、指定时间/序号起读，和即时/原速重放分别配置。

对象模型 · 历史读取 · Ordered consumer

Ordered consumer 适合有序查看与重放，不应不加区分地替代有 ACK 和工作分配需求的 worker consumer。消息序号有序，也不保证多个并行 worker 的副作用按序完成。
04 / 消费协议

ACK、重投与背压：确认的是哪一层

信号 / 配置含义业务设计注意
ACK该次消息处理被确认应在业务要求的结果提交后发送
NAK请求重投，可指定延迟重投可能换一个 worker
InProgress延长 ACK 等待表示还在工作，不是完成
TERM停止重投这条记录不表示业务成功
AckWait / BackOff未确认消息的重投时机过短可能在旧 worker 尚未结束时再次派发
MaxAckPendingconsumer 全局未确认上限多个 worker 共用此限制；不等于整个系统准入已完成
MaxDeliver限制投递尝试并产生 advisory并不会自动把业务结果写入你自定义的死信 stream

Pull consumer 的 fetch / consume 让 worker 按可处理容量取消息。命名 durable 可以恢复消费状态，但仍要正确处理 pending 与 ACK floor，不能用一个简单“最新已读序号”代替并发确认逻辑。

05 / 去重与副作用

Exactly-once 必须说明范围

常规 JetStream publish 以 Nats-Msg-Id 在配置的去重窗口内识别重试；窗口不是无限。expected-last-sequence 一类头部提供乐观并发条件，不能自动成为 DSH owner 的权限或任期证明。

同步确认 ACK（客户端 API 常称 double ACK / AckSync / ackAck）让 worker 等待服务器记录确认。写侧去重与读侧 ACK 确认，可以减少消息层重复窗口；它们无法和任意邮件、shell、HTTP 服务或数据库一起原子提交。

关键失败窗口：工具成功，ACK 尚未发出

worker 已完成外部发布，但在 ACK 前退出，消息会再次到达。消息系统不知道外部发布已经成功。此时需要稳定 operationId、外部结果查询、业务幂等或人工协调；不能仅靠一次 NATS 去重 ID 避免消费侧副作用。

较新版本还有原子 batch publish，能让同一批消息 all-or-nothing；这仍不意味着跨 PostgreSQL 与消息系统的事务。本页固定 v2.15.1 的源码包含该路径，不把旧安装版本视为已经支持。

06 / 历史与清理

选择日志，还是选择工作队列

保留策略删除条件对 DSH 的推断
Limits年龄、条数、字节等限制；ACK 不决定删除适合保留窗口内会话事件回放
Interest相关消费者均确认；没有兴趣的消息可立即移除消费者拓扑会影响历史存续
WorkQueue某次成功 ACK 后移除；未确认仍可重投适合工作交付；不能同时当完整历史库

所有策略仍受流限制影响。WorkQueue 中消费者过滤范围不能随意重叠，可让多个 worker 共用同一 consumer 分工。限制截断、删除或 TTL 会造成历史缺口，应用需要明确补档、快照或不可恢复的响应。

07 / 集群与持久性

副本、多数派和落盘不是同一个保证

在复制场景中，JetStream 有元数据协调与各 stream / consumer 的协调状态；不是整个集群只用一条全局消息日志。stream 由 leader 排序，并在多数副本确认后回应。R=3 可在剩余多数可达时容忍一台不可用；R=2 失去一台就没有多数。

File / Memory 决定消息的存储介质。File store 仍涉及同步策略：固定版本源码默认后台同步间隔为 2 分钟，并有 SyncAlways 等路径。因此 PubAck、quorum 与所有机器突然掉电后的物理落盘保证必须分开核对。

当前 220 / 118 是两台 Cube 计算主机，不是已部署的 JetStream 集群。也不能把在两机上启动三个进程当成三个独立主机故障域。本次没有做 Raft 故障或掉电试验。

多 stream 可分散 leader 和副本，单个 stream 仍有自身排序与资源瓶颈。生产运维还需规划磁盘、资源限额、备份、升级与慢消费者监测，不能只引用供应商吞吐数字。

08 / 接入与隔离

能连浏览器，不等于成为 HTTP 流协议

NATS WebSocket 承载 NATS 协议，客户端继续使用 subject 与 JetStream API。它不是 Durable Streams 的 HTTP GET / SSE / ETag 语义，不能直接沿用同样的 CDN 历史缓存机制。

NATS account 隔离 subject 空间，用户权限限制其中的发布与订阅，跨 account 通过明确 import / export 连通。它提供消息层租户边界；应用仍需把用户、团队、工作区和会话 ACL 映射到相应权限，限制管理 API 与通配订阅。

对目前的 DSH，我们更倾向先让后端消费 NATS、通过已鉴权的产品 API 给浏览器输出。直接浏览器连消息系统也能设计，但不能把宽权限服务器凭据交给浏览器。监控端口、系统 account 和消息管理权限应与业务接入分别配置。

09 / DURABLE STREAMS 对照

共同点是持久事件，差别在消费契约

维度JetStreamDurable Streams
寻址Subject → Stream → ConsumerURL 指向流资源
位置Stream sequence + Consumer 状态普通读取保存 opaque next offset
确认原生消费 ACK 与重投普通 GET 不 ACK；另有 subscription ACK 模型
写入重试Msg-Id 去重窗口，expected 状态检查Producer-Id / Epoch / Seq；epoch fencing
浏览器NATS client over WebSocketHTTP catch-up、long-poll、SSE
权限Account + Subject 权限HTTP 实现／鉴权入口负责
运维边界明确的 stream 与 consumer 复制配置由具体实现决定存储与 HA，不能只看协议
本次重要核实：DS subscription 规范与 Caddy 实现差距

固定 DS 协议已定义 reserved subscription API、pull-wake、claim / ack / release 与 lease generation。不能再概括成“DS 完全没有 ACK”。

同一固定 SHA 的 Caddy webhook 已有 callback ACK 代码，但使用旧的 query / callback 路由；订阅及 cursor 保存在内存 maps。没有静态证据支持它已完整实现当前 pull-wake 控制路由和跨重启持久消费状态。协议、代码路径与运行验收需要分别判断。

DS 的 Stream-Cursor 用于 live 缓存协调，不能当消费 offset。重读进度、通知和业务完成是不同状态。两者若组合使用，应明确哪个记录是权威，以及如何映射稳定 eventId，而不是假定 sequence 与 opaque offset 可互换。

10 / 项目集成判断

把事件历史与任务交付分别设计

以下是设计建议，不是本项目已经接入 NATS 的说明。一个可验证的起点，是保留当前业务状态的事务权威，通过 outbox 发布事件，用 JetStream 承担可靠交付；浏览器输出可经产品 HTTP 接口或另一条明确的回放流暴露。

业务事务 + Outbox→JetStream：日志 / 工作交付→DSH owner / worker→结果提交 + ACK

会话输出

使用稳定 eventId、sessionId、turnId 和顺序信息。历史流选择保留策略与容量上限；前端断线后从已处理位置补读。

工作队列

任务按容量拉取，副作用完成后确认；先解决 owner lease、业务去重、unknown 协调与取消，再讨论重投次数。

执行顺序

同一会话只允许一个推进者。共享 consumer 的负载分配不会自动维护 DSH 进程内上下文；需要路由与会话所有权。

控制范围

NATS 可传递消息，Cube 仍管 PVM；工作进程仍运行 Agent。收到消息、启动 B 与提交最终结果是不同的可见阶段。

选择提示：先解决 HTTP 回放时，DS 更贴近现有接入；扩展到跨服务消息与 worker 交付时，JetStream 更值得实验。也可以二者分层组合，但要承担同步、鉴权、保留与故障协调成本。
