DSH 如何接入多租户

从可信身份到独立上下文，再到工具沙箱与持久数据：解释实际代码如何把多租户装配到原生 DSH。

官方源码未修改共享进程 · 多上下文binding = 空间 × 用户 × 工作区
01

多租户接入在 DSH 外层完成

没有修改官方 DSH 源码，也没有让所有用户共用一个全局会话服务。共享的是宿主 Node 进程，平台按绑定装配多个官方 DSH 上下文。

平台新增

鉴权与 ACL、绑定映射、原生 Web 代理、工具按需生命周期。

DSH 复用

boot / Cordis 上下文、原生 profile 与配置编辑器、会话持久化、凭据服务、Agent 和 SSH 文件工具。

运行行为调整

通过配置 patch 选择远程工具提供器、重定向存储并限制宿主操作；官方源码未改，插件组合与默认配置发生变化。

02

binding：贯穿各层的归属索引

空间决定组织与访问边界；用户决定私有身份；工作区决定执行与数据作用域。当前绑定粒度是三元组，不是单纯 tenant，也不是 conversation。

const bindingKey = (tenant, user, workspace) =>
  "mt-" + createHash("sha256")
    .update(JSON.stringify([tenant, user, workspace]))
    .digest("hex").slice(0, 48);

稳定性

同一三元组重启后生成同一 key。B 重建的 sandbox ID 改变，binding key 不变。使用稳定 ID；修改绑定公式需要迁移存储与资源映射。

会话复用

同一绑定多个会话共用一个上下文和 B；不同用户即使进入同一共享工作区也产生不同绑定。

不是认证凭据

48 位十六进制摘要是资源索引，不是加密或授权。知道 key 不能绕过网关权限；控制器接口另有私有认证。

数据库绑定与运行时 binding key 有什么区别？

user_bindings 存储 tenant_id / user_id / workspace_id 与界面使用的状态、代次等字段；DSH Host 根据同一三元组计算哈希 key。它们是相关的两种表示，并非所有数据库表都改成用哈希主键。

控制器 epoch、平台 generation 和连接代次用于各层生命周期；不应当把它们当成同一计数器。实际 B 状态还要查询控制器与 Cube。

03

请求路由：先确定用户，再选择 DSH

客户端提供工作区 URL，不能自己指定可信 userId。网关从平台 session Cookie 解析用户，校验权限后把请求导向该用户的上下文。

鉴权没有下放给 key

校验工作区成员、角色、ready 状态与同源请求。await 初始化后再次校验 ACL，避免等待期间已撤权却继续代理。

两层登录态

平台 Cookie 用于对外认证；原生 DSH 内部 Cookie 由后端持有并注入代理。内部服务绑定 A 的 loopback 随机端口。

前端状态也分区

native-client.js 给 localStorage / sessionStorage 加绑定命名空间，调整 fetch、资源与 WebSocket 路径。X-DSH-Binding 与 WS binding 防止账号切换后继续使用旧页面。

撤权与退出不仅影响新请求，也会关闭已有连接。浏览器绑定标识用于一致性检查，不能替代服务端身份校验。
04

上下文装配：把原生单用户能力组合起来

instance() 按 key 缓存上下文；pending Promise 合并并发启动。配置 revision 改变时释放旧上下文并重新装配，持久化目录保持稳定。

home = BASE + "/state/runtimes/" + key

// 通过原生配置接入，不给 DSH 核心增加 tenant 参数
session-persistence-jsonl.root = home + "/sessions"
credentials.dshHome = home
profileContext = { dir: home + "/profile", home, cwd: "/workspace", ... }
ctx.dshHomePath = (...parts) => join(home, ...parts)

// 原生 profile 编辑写入独立 patch；部署默认值由生成 bundle 提供
ctx = await boot(...readProfilePatches("dsh", profileContext)...)

配置持久化

生成 bundle 提供部署默认值，profile/cordis.patch.yml 保存原生界面的配置修改；重建上下文不覆盖已有用户 patch。

凭据与 Skill

凭据文件按绑定 home 保存。当前适配器把 profile Skill 注入该 ctx；禁用了默认 skill-filesystem 扫描，不能据此声称全部原生 Skill 管理路径都已实现。

实际隔离强度

对象、注册表、目录和内部 Web 服务分别装配；Node 进程、依赖、CPU / 内存与故障域仍共享。恶意插件不具备进程级隔离。

05

工具路由与恢复也必须使用同一绑定

host 字段在适配层充当逻辑别名，不是直接把哈希当成普通 DNS 地址。ensure 返回实际连接信息，适配器生成该绑定的 SSH 配置，经 Cube Proxy 进入 B。

控制器串行化

binding_lock(key) 串行化同一绑定的创建、检查点和回收；不同绑定有各自锁。租约避免活动工具被误暂停。

恢复路由

key 对应保存的 volume_id、归档哈希、epoch 和 restore_pending。恢复失败拒绝创建空目录替代，保留明确的失败状态。

启动一致性校验

Host 检查 ctx.fs 为 SshFileSystem，并检查 ctx.ssh.config.host 与 FS 的 SSH host 都等于 key；不匹配立即报错。

共享工作区元数据不代表共享工具文件。当前每用户独立 B 与 /workspace；如果要做协作共享文件，需要另设计共享卷、锁和权限，不能直接复用一个用户的 key。

本次证据边界

深化时优先检查

同绑定并发会话共享文件的竞争；配置 revision 变更与活跃 Agent；解绑 / 删除的数据清理；tenant 跨界授权；A 中插件与共享依赖的隔离。

如果未来要让 DSH 核心原生支持多租户

需要明确传递可信 Principal / TenantScope，审计所有注册表和持久化服务的作用域，并让会话、凭据、Skill、工具路由与资源配额统一按作用域访问。当前实现通过多个 ctx 与独立 home 达成组合，不应把一个共享 ctx 简单加 tenantId 就视为完成隔离。
