01

结论：AX 在上，Substrate 在下

两者不是两个互相替代的 Agent SDK。AX 已建立对 Substrate 的依赖；与我们研究关联最强的是任务资源模型和沙箱生命周期。

google/ax

上层 Agent 工作负载编排：声明任务与环境，准备工作区，控制执行和观察状态。

agent-substrate/substrate

下层执行底座：让大量逻辑 Actor 复用较少的物理 worker，管理隔离、路由和快照。

我们的研究

DSH 提供对话与 Agent 循环，CubeSandbox 提供工具 PVM，平台适配器提供身份绑定和按需生命周期。

02

AX：把 Agent 执行声明为资源

AX 用独立控制面存储与 reconcile 避免把每个高频任务都变成 Kubernetes CRD；它不是只写一个 Helm chart。

Task

隔离执行单元：镜像、命令、CPU / 内存与工作区引用。一个任务可承载整个工作，也可成为委派任务树中的一个节点。

Workspace

可复用的准备定义：Git、MCP、Skill 与 bootstrap goal。绑定到 Task 后在沙箱里物化；不是天然的跨任务共享目录。

Model

模型提供者、模型标识和参数配置，引用 Kubernetes Secret。AX 自身准备工作区等组件也可使用它。

03

Runner 契约：谁真正运行 Agent？

默认架构中，Task 的 Agent 命令在 Actor 沙箱内部执行。AX 控制面在外面，不等于模型循环本身必定像我们的 A 一样位于工具沙箱之外。

启动

固定入口 /usr/local/bin/ax-task-runner，读取 Task / Workspace YAML，准备数据与依赖，再以子进程启动 spec.command。可替换镜像和自定义 runner。

就绪与调试

runner 提供 healthz / readyz 与元数据端点；debug 开启时提供 guest 服务，支持 ax ssh。命令退出后 runner 继续服务。

暂停与恢复

runner 文档明确：/workspace 通过快照保留；恢复进入新容器和新进程树。因此不能仅凭 suspend / resume 就承诺原 Agent 进程无缝续跑。

依据：Runner 接口与恢复语义

这与 Substrate 底层能保存进程内存的设计不是同一层承诺。若让 DSH 作为 Task 命令运行，必须先验证实际快照类型、退出流程和 DSH 会话恢复，而不是把底层快照能力直接套到上层。
04

Substrate：逻辑 Actor 与物理 worker 分开

空闲逻辑实例可以多，运行中的物理容量可以少。Kubernetes 管基础设施和 worker，Substrate 管更高频的 Actor 激活与状态。

Actor

一次逻辑工作负载实例，保存状态、快照引用和当前位置；不是自动等同于用户、会话或 AI Agent。映射粒度由上层选择。

WorkerPool / Worker

WorkerPool 管预热容量；worker 接受 Actor 分配，释放后可承载其他 Actor。要防止跨 Actor 残留状态。

节点与存储

ate-api-server / PostgreSQL 管状态，atelet 协调节点，ateom 调用后端 checkpoint / restore；快照插件负责对象存储搬运。

依据：资源与组件设计

架构文件开头明确标注部分设计仍是设想；README 的百万级、密度和延迟数字属于项目声明，本报告没有测量，也不作为当前系统的容量保证。
05

按需激活与恢复：网络请求就是唤醒入口

Substrate 的设计将请求路由与 Actor 激活关联；暂停则是明确生命周期操作，不能把文档中的空闲设想直接理解为默认自动计时回收。

Golden snapshot

首次启动从模板快照恢复，后续使用 Actor 自己的状态；减少重复初始化。实际启动延迟仍需测量。

Suspend 与 Pause

架构文档区分持久外部快照与节点本地 pause；后者恢复可能绑定节点。节点故障、版本升级与迁移要另外验证。

恢复边界

gVisor 和 micro-VM 使用不同后端。文件、内存、连接和外部副作用不能笼统视作一个“全部恢复”保证。

Substrate 与 CubeSandbox 在执行底座层有重叠；AX 与我们的平台生命周期编排有部分重叠，DSH 的原生问答与上下文能力仍是另一个层面。

可借鉴：资源定义

把 template、workspace preparation、资源规格与运行实例分开，让声明与状态明确；避免用一个 binding 字符串承担所有产品语义。

可借鉴：预热与观测

将逻辑实例和计算容量分开；统一 Ready、暂停、恢复失败与运行位置，跨生命周期追踪日志和指标。

不能直接套用

AX 默认连接 Substrate API，不是 Cube API。把 Cube 替换进去或保留共享 A 都需要适配协议、存储与就绪契约。

07

可行的研究路线与当前边界

保留现有已验证环境，另做隔离实验。先学习契约和恢复语义，再判断是否值得换执行底座。

实验 1 · Substrate 单 Actor

部署独立测试集群，运行有内存计数和文件写入的小程序；验证 suspend / resume、worker 迁移和故障恢复。

实验 2 · DSH 自定义 runner

按 AX runner 契约打包 DSH，验证原生会话与文件恢复。明确这会产生按 Task 运行 DSH 的模式，与现有共享 A 不同。

实验 3 · 保留 A 替换 B

作为另一条路线，仅用 Substrate 承载工具 helper，平台增加 lifecycle backend；验证 SSH / guest API、租约、资源与绑定映射。

安全与成熟度：文档和代码需要一起看

Substrate authentication.md 写“授权/RBAC 尚未实现”；本次读取的 cmd/ateapi/main.go 已出现实验性 OpenFGA 开关（默认 false）与 AccessPolicy 检查。因此应判断为文档存在滞后、功能需核对启用状态，不能说完全没有授权，也不能认为默认有完整多租户授权。

认证文档 · API 入口代码

AX 标记重度开发，Substrate 为 pre-1.0；API 和行为可能改变。本页做了文档与入口静态核对，没有验证调度、快照或授权的运行时完整性。

调研结论：最有价值的是“任务声明 → 逻辑实例 → 物理容量 → 持久状态”的分层。是否采用整套系统，要由部署成本、恢复语义和实际容量实验决定。

08

Substrate、CubeSandbox 与 Firecracker：目标相近，层次不同

Substrate 与 CubeSandbox 都管理沙箱执行与生命周期；Firecracker 是构建 microVM 的底层 VMM，不能直接当成完整沙箱服务平台。

比较项Agent SubstrateCubeSandboxFirecracker
核心对象Actor、worker、模板、快照Sandbox、模板、计算节点、持久卷microVM、vCPU、内存、虚拟设备
平台职责执行容量分配、激活、路由、暂停恢复服务 API、生命周期、网络与存储管理虚拟机运行与快照等底层能力
集群与用户能力基于 Kubernetes 的执行控制面；用户治理需核对配置沙箱服务控制面；业务用户治理仍需上层需要自行增加调度、鉴权、路由和持久化系统
与当前项目关联工具 B 执行底座的另一个候选目前 A / B 的执行平台自建沙箱底座时可研究的 VMM；并非直接替代完整 Cube 服务
不能说“它们都是 Firecracker 的封装”。 当前核对的 Substrate 后端和 CubeSandbox 组件各有自己的实现路径。共同具有隔离与快照相关能力，不代表内部使用同一个 VMM，也不代表恢复语义、部署约束和安全边界完全相同。

平台对平台比较

比较 Substrate 与 CubeSandbox，应看 API、生命周期、网络策略、存储、容量调度、部署成本和可观测性。

VMM 对 VMM 比较

比较 Firecracker 与具体 microVM 后端，应看虚拟设备、宿主要求、快照恢复、隔离与运行开销。gVisor 不是同类 VMM。

上层仍需 DSH

无论选择哪个底座，会话、模型循环、业务鉴权、Skill 和工具路由仍是上层职责。直接使用 Firecracker 需要补齐更多平台功能。
