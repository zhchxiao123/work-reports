新数据流 · 第 3 步详解

调用模型：重试时前端怎么不重复

重试时模型会生成一段新文字，和上次不会完全一样，所以没法靠给文字去重。正确的做法是告诉前端：上一次尝试作废了，用新的一次替换它。

结论：宿主在 DSH 的一次尝试失败时，发出“开始新尝试”事件。前端和 BE 快照收到后清掉这一步未完成的文字，已完成的步骤不动。DSH 自己的客户端也是这样做的，这段逻辑从 rc.2 到最新版没有变化，不用等升级，也不依赖账本。

01现在为什么可能重复

宿主防得住同一次尝试内的重复，但下游并不知道“尝试”这回事。

环节现在后果
宿主DSH 每次尝试有 attemptId，宿主按“尝试 + 序号”去重只管同一次尝试；新尝试的序号重新开始，文字照常发出
BE 快照收到增量就往回答后面追加断线重连时拿到的快照也可能带着半截旧文字
前端按 streamId 丢弃重投的帧，其余往后追加新尝试的文字是新帧，会接在半截旧文字后面
结束时BE 保存明确的最终答案入库内容大概率正确，问题主要出现在生成过程中
以上来自读代码的推断，还没有实测。需要先模拟一次模型中途断流来确认。

Pi Durable 和 DSH 怎么做

界面显示状态，不拼增量

Pi Durable 存的是“这次生成到目前为止的全文”，界面只显示最新值。崩溃后，半截内容转成一条标记为“已中断”的记录，不再进入模型上下文，然后重新请求。

DSH 的做法更接近我们的方案：失败的尝试落盘后，它的客户端用这条持久事件替换这次尝试的临时文字，然后开始下一次尝试。ByClaw 只需把这个信号传到 BE 和前端。

03四条规则

  1. 事件带上尝试信息

    每个文字事件带 turn、step、attempt_id、index，子 Agent 按各自的会话分开算。attempt_id 只在进程内有效，日志里没有，所以只用于实时显示，不要存下来；需要持久引用时用“会话 + turn + step + 序号”。

  2. 新增“开始新尝试”事件

    assistant.attempt.start 和文字走同一条 Redis 流，顺序有保证。触发时机是 DSH 的 assistant/attempt 事件（一次尝试失败落盘），不是 llm/retry，因为其他重试路径可能不写后者。BE 快照和前端收到后，清掉这个 step 未完成的文字和思考内容。

  3. 丢弃旧帧

    attempt_id 不是当前这次的，直接丢弃；attempt_id + index 相同的重投也丢弃。

  4. 只有完整提交的回答才算数

    失败的半截不入库，宿主累积的回答文本也要一起重置。例外：用户主动停止时，回答带 interrupted 标记，这段文字要保留，不能清掉。工具调用由 DSH 保证落盘后才执行，不受影响。

04各种情况怎么走

情况处理
模型接口报错，宿主进程内重试发出“开始新尝试”，前端替换这一步。这种情况不需要账本
宿主崩溃后重启（需要阶段 2 的续跑器）DSH 恢复时把这一轮标记为中断，进行中的尝试不留记录。续跑时重新生成并发“开始新尝试”，半截文字在前端被替换；已完成的步骤不重做
重试时前端正好断线快照已按新尝试清过，重连后整体替换，再接收新帧
旧尝试的帧迟到或重投按规则 3 丢弃
子 Agent 的模型调用重试只替换这个子 Agent 这一步的内容，主对话和其他成员不受影响
重试次数用完明确显示这一轮失败，提示用户重试，不再一直转圈

05要改什么

宿主

阶段 0

在事件里带上尝试信息，发出“开始新尝试”，新尝试时重置累积的回答文本。

BE

阶段 0

快照记下每个 step 的起点，收到新尝试就截回去；把事件字段原样转给前端。

前端

阶段 0

按 step 管理正在生成的文字，处理新尝试事件，丢弃旧帧，显示重试提示。

还没确认的

  • 现在是否真的会重复显示：代码显示 ByClaw 会跨尝试追加，失败的轮次入库也可能带上半截（推断）；需要在验证环境模拟模型中途断流确认。
  • 重试时半截文字怎么显示：当前按“直接清掉并提示”设计，实现最简单，但文字会闪一下；另一种是变灰保留、新文字到了再替换，前端要多一种显示状态。
