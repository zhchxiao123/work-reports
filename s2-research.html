定位：流式数据存储 API

S2 服务与仓库中的 s2-lite 要分开理解：仓库包含 CLI、Rust SDK 与可自托管的 API 服务实现。

S2 云服务

s2.dev 定位为 serverless streaming datastore；云端的容量、部署与可用性契约不能从 lite 推断。

s2-lite

单节点二进制，使用 SlateDB；可以 S3 兼容对象存储、本地磁盘或仅内存运行。

数据模型

Basin 管理流资源，Stream 保存有序 Records。每条 record 有序号、时间戳、headers 和 body；不是原生 conversation 对象。

仓库 README · Records 文档

读写与持久化链路

生产者追加 records，服务赋予序号；读者从保存的序号补读并继续追踪。

DSH 事件生产者 → append records → S2 Stream → seq_num 续读 → 网页 / 手机 / 桌面
会话事件格式、身份权限和任务完成条件仍由应用定义。

API

支持 append、read 和 check tail。HTTP API 可用 JSON / Protobuf，SDK 的 S2S streaming sessions 基于 HTTP/2；读也可使用 SSE。

确认边界

README 说明 bucket 模式在对象存储 durable 后才确认写入或返回给读者；仅内存模式是测试模拟。分离本地 WAL 与对象主存储会改变故障持久性边界，需单独验收。

Lite 静态实现

streamer 拥有 stream tail，串行化 append 并向 followers 广播已确认 records；代码含 in-flight append、durability notifier 和 fencing token。

和 Durable Streams 哪些相似，哪些不同

二者都能承载 Agent 会话事件并支持重连；不能把位置标识或协议直接互换。

Durable Streams 分析与协议出处

写入重试、条件追加与 fencing 要按各自 API 设计，不把 Durable Streams 的 Producer-Id / Epoch / Seq 当成 S2 请求格式。二者也都不能保证外部工具副作用 exactly-once。

接入 DSH：事件层候选

可按会话或任务组织 Stream，让客户端读取与 Worker 执行解耦。当前只是集成方案，没有实现 adapter。

事件 envelope

记录 tenant / binding / conversation / turn / eventId / type；record seq_num 用于传输位置，业务 ID 用于业务去重与关联。

状态权威

若任务数据库是权威，使用 outbox 协调状态提交与流发布；S2 append 不自动和 PostgreSQL / SQLite 构成同一事务。

租户授权

云 API 的 token 与 lite 覆盖面不同。README 中 lite 示例 token 可 ignored，access-tokens API 不支持；不能直接把服务公开给终端用户，需上层鉴权与隔离。

“能重读事件”与“能恢复 DSH 在途任务”是两层。S2 不分配 DSH Worker，不管理 B PVM，也不负责取消远程进程。

部署与性能验证

先做同负载对照，区分内存、本地持久化与对象存储。

部署

Lite 可单机或通过 Helm 部署，但 Helm 不会自动赋予分布式服务语义；WAL、主存储、缓存与恢复需核对。

压测入口

README 提供 s2 bench：写入目标 MiB/s、持续时间与 catchup delay。再补 Agent 小事件、多流、扇出、断线与正确性核对。

验收指标

吞吐、确认 P95/P99、写入到客户端可见延迟、补读速度；同时检查丢失、重复、序号与故障后持久性。

s2 bench <basin> --target-mibps 10 --duration 5s --catchup-delay 0s
