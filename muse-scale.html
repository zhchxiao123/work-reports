几亿人连同一个地址：海量长连接是怎么扛住的

这一篇不分析 Muse 的代码，而是回答一个基础问题：几亿个客户端都连 wss://hatch.metaaivm.com/v1/noise，并且都保持长连接，这在技术上为什么成立，靠的是什么。最后再把这些概念对照回 Muse 的入口。文中数字分两类：实测（本次分析中查到的 DNS、TTL、响应头）与公开资料的量级（各大厂博客、论文里的数字，用来建立直觉，不是精确值）。

01先说结论

三句话
一个域名不是一台机器；长连接的成本是内存，不是 CPU；入口只要无状态，就可以无限加机器。

域名只是路牌。从"几亿人输入同一个名字"到"字节落到某台机器的某个进程"，中间有 DNS、VIP、L4、L7 四层分流，每一层都把流量切成更小的份。到最后一层时，每台机器只看到自己那几十万条连接。

空闲长连接几乎不耗 CPU。一条建好的 TCP/TLS/WebSocket 连接，不收发数据时只是内核里的一组状态加用户态的一个对象，大约几十 KB 内存。事件驱动的网络库（epoll / kqueue / io_uring）让一个线程可以同时"盯着"几十万条这样的连接，只在有数据到达时才被唤醒。

有状态的东西被推到了后面。入口机只做 TLS 终止、鉴权、按 vm_id 查表转发，不记住任何会话内容，所以任何一台都可以接任何一条连接，坏了换一台就行。真正有状态的是每个用户自己的 VM，而它按用户切分，天然水平扩展。

结论是"分流 + 便宜 + 无状态"。↓　先看分流：一个名字怎么变成几千台机器。

02四层分流漏斗

每一层解决一个不同的问题：DNS 解决"去哪个机房"，VIP 解决"一个地址多台机器"，L4 解决"同一连接的包始终到同一台"，L7 解决"解密、鉴权、按业务路由"。

层代表技术关键性质
DNSGeoDNS（按地理 / 延迟返回不同答案）、Anycast 权威 DNS、短 TTL决定去哪个机房；客户端缓存 TTL 到期后可能被调到别处。Muse 的 AAAA 记录 TTL 24 秒，说明在做主动调度。
VIP / BGP / ECMP一个 IP 由多台机器通过 BGP 共同宣告；路由器用 ECMP 把包按五元组哈希分给它们；Anycast 让全球多个机房宣告同一 IP把"一个 IP"变成"一组机器"的第一步；完全在网络设备里完成，没有软件瓶颈。
L4Google Maglev（2016 论文）、Meta Katran（XDP/eBPF，开源）、Cloudflare Unimog、Linux IPVS一致性哈希保证同一条 TCP 连接的所有包落到同一台 L7；L4 节点增减时尽量不打断已有连接；通常用 DSR 或 IPIP/GUE 封装，回包不经过 L4。
L7Meta Proxygen、Envoy、nginx、HAProxy、Cloudflare Pingora终止 TLS、解析 HTTP/WebSocket、鉴权、限流、选后端。连接的内存成本在这里。Muse 的 401 响应头里的 proxy-status: e_fb_vipaddr / e_fb_zone 就是这一层的签名。
后端路由一致性哈希 / 目录服务 / 服务发现Muse 用 vm_id 查"这个 VM 在哪台宿主机"，再把 Noise 密文搬过去；查表服务是入口唯一的"有状态"依赖。
小结：前三层几乎不花软件成本，第四层是花钱的地方，第五层是花大钱但可分片的地方。
漏斗里出现了 L4 和 L7 两个词。↓　它们到底指什么，为什么一个不够、要两层都用？

03L4 与 L7：同一个包，两双眼睛

"L4 / L7" 来自 OSI 七层模型：第 4 层是传输层（TCP / UDP），第 7 层是应用层（HTTP、WebSocket、TLS 之上的内容）。一个负载均衡器被称为 L4 还是 L7，取决于它读到包的哪一层就做决定。读得越浅，越快、越便宜、越无状态；读得越深，越聪明、越贵、越需要维护连接。

维度L4（传输层）L7（应用层）
读到哪一层IP + TCP/UDP 头；握手期可见 TLS SNI解密后的 HTTP 请求行、头、路径、查询参数、WebSocket 帧
决策依据五元组哈希Host、路径、头、Cookie、查询参数、鉴权结果
连接归属不持有连接；客户端的 TCP 另一端是 L7 机器持有连接；是客户端 TCP/TLS 的真正对端，再向后端另开连接
状态可做到无状态（一致性哈希 + 连接表仅作加速）每连接必有状态（TCP、TLS、WS、路由上下文）
回包路径DSR：后端直接回客户端，L4 只处理上行双向都经过它
单机吞吐每秒千万级包，线速每秒几万到几十万请求；连接数几十万到百万
扩容方式加机器即可，ECMP 自动分摊；增减时一致性哈希保连接加机器即可，但新机器要从 L4 拿到流量；连接迁移需优雅排空
故障影响一台 L4 挂：ECMP 重新哈希，部分连接可能重置（一致性哈希尽量减少）一台 L7 挂：它持有的所有连接断开，客户端重连到别的机器
能做的事分流、DDoS 粗过滤、SNI 路由TLS 终止、鉴权、限流、重试、灰度、WAF、协议转换、按业务路由
典型实现Google Maglev · Meta Katran · Cloudflare Unimog · Linux IPVS · AWS NLBMeta Proxygen · Envoy · nginx · HAProxy · Cloudflare Pingora · AWS ALB
为什么两层都要：只有 L4 没法终止 TLS、没法按业务路由；只有 L7 则每台机器都要独自面对公网流量的分配问题，而且 L7 机器一多，前面总得有东西把一个 IP 分给它们。于是 L4 负责"把连接均匀、稳定地分到 L7 机器"，L7 负责"理解请求"。

一次 WebSocket 建链穿过两层

以 Muse 的 /v1/noise 为例
  • 1. TCP 三次握手：SYN 到达 VIP，L4 按五元组哈希选中边缘机 X，封装（IPIP/GUE）转给 X；X 回 SYN-ACK 直接给客户端（DSR）。此后这条连接的每个上行包都被哈希到 X。
  • 2. TLS 握手：ClientHello 里的 SNI 是 hatch.metaaivm.com；L4 不处理，X 上的 Proxygen 终止 TLS。此时 L7 第一次"看见"内容。
  • 3. HTTP 升级：X 解析 GET /v1/noise?vm_id=…&auth_token=… 与 Upgrade: websocket，校验 token，按 vm_id 查到 VM 宿主机，向它建立后端连接，回 101 Switching Protocols。
  • 4. 之后的每一帧：X 解 WebSocket 帧头，取出二进制负载（NoiseTransportFrame），原样转给 VM；反向亦然。L7 不再理解内容，只做帧搬运。
  • 5. 断开：X 收到任一端关闭就关另一端；若 X 自己要下线，用关闭码 1012 / 1013 通知客户端稍后重连，流量由 L4 重新哈希到别的机器。

几个容易混淆的点

边界与变体

"L4 看不到 SNI"不完全对。TLS 握手的 ClientHello 是明文，SNI 字段可读；一些 L4 产品据此做"按域名分流"（SNI 路由），但仍不解密。Muse 入口只有一个主机名，不需要。

L7 不一定终止 TLS。也有 TLS 直通（passthrough）模式，但那样它就退化成 L4 了，无法按路径路由。Muse 的 401 响应头证明边缘终止了 TLS。

WebSocket 对 L7 是"长寿请求"。升级成功后它仍是一条 HTTP 连接的延续，L7 必须一直持有；这就是为什么长连接的成本落在 L7 而不是 L4。

HTTP/3（QUIC）改变了分工。QUIC 跑在 UDP 上，连接由 Connection ID 标识而非五元组，L4 要按 CID 哈希（Katran 支持）；Muse 当前走的是 TCP 上的 WSS。

分流把"几亿"切成了"几十万"。↓　那一台机器扛几十万条长连接，凭什么？

04一台机器能扛多少长连接

这个问题在业界有二十多年的演进史，名字叫 C10K 到 C10M。核心转变只有一个：从"每条连接一个线程"变成"每条连接一个状态对象，一个线程服务几十万个对象"。

模型：一连接一线程

C10K 之前

每条连接占一个线程或进程，栈 1–8 MB，上下文切换随连接数线性增长。1 万条连接就是 10 GB 栈内存加满负荷的调度器。这是"长连接很贵"这个直觉的来源，但它描述的是 25 年前的服务器。

模型：事件循环

epoll · kqueue · IOCP · io_uring

内核维护一个"哪些 fd 有事件"的就绪列表，应用一个线程循环取事件处理。连接本身只是一个状态对象，空闲时不占调度。nginx、Node.js、Netty、Go 的 netpoller、Erlang 的 BEAM 都是这个模型。

模型：内核旁路与硬件卸载

XDP · DPDK · TLS offload

L4 这一层把包处理挪到网卡驱动层（XDP）或完全绕过内核（DPDK），单机每秒处理上千万包；TLS 握手可以卸载到专用硬件或集中到边缘。这些让"几十万连接 + 心跳"的包处理不成为瓶颈。

单机几十万条是常规。↓　那几亿条到底要多少台，心跳要花多少？

成本项量级结论
内存9 TB 总量，分摊到几百台机器对一家拥有数十万台服务器的公司是零头；这是长连接"便宜"的根本原因。
心跳 CPU/带宽每台 5 万包/s，每包几十字节单机几 MB/s，微不足道；但心跳间隔每缩短一倍，全局成本翻倍，所以移动端会把间隔拉到分钟级并随网络自适应。Muse 的 10 s 心跳只在前台 web 层。
建链 CPUTLS 握手约 1 ms，Noise 握手更轻稳态可忽略；危险在于故障恢复时几千万客户端同时重连（惊群）。退避 + 抖动 + 服务端 1012/1013 分批驱逐就是为此设计。
NAT / 防火墙超时家用路由器 UDP 30–60 s、TCP 几分钟到几小时心跳不只是为了探活，也是为了让中间设备不要把映射表项回收掉；这是心跳间隔不能无限拉长的原因。
vm_id 查表每次新连接一次查询Muse 入口唯一的有状态依赖，需要一个低延迟的分布式目录；连接建立后不再查。
后端（VM）每用户一台 VM真正的大头，但与入口无关；入口再多连接也不会让 VM 变贵。
小结：把"几亿长连接"拆开看，内存是几百台机器的事，心跳是每台几万包的事，握手是故障时的事。没有一项落在"一个地址"上。
账算清楚了。↓　顺便把几个常见的直觉误区纠正一下。

06四个常见误解

这些直觉在小系统里是对的，到了这个规模就不成立了。

误解一：一个地址 = 一台服务器

实际：一个名字 → 几千台机器

域名经 GeoDNS 返回不同 VIP，VIP 经 BGP/ECMP 对应一组机器，L4 再分给几百台 L7。"地址"只是客户端看到的最外层路牌。Muse 的 hatch.metaaivm.com 是一个 CNAME，指向 Facebook 边缘的 c10r.facebook.com 命名空间，与 www.facebook.com 用的是同一套。

误解二：端口只有 65535 个，所以最多 6 万连接

实际：限制在客户端那一侧，而且是每个目标

一条 TCP 连接由四元组（源 IP、源端口、目标 IP、目标端口）唯一标识。服务端监听一个端口，可以同时接受来自不同"源 IP + 源端口"组合的无限多条连接。65535 的限制是说：同一个客户端 IP 到同一个服务端 IP:端口最多约 6 万条。几亿个不同的客户端完全不受此限。

误解三：长连接比短连接贵

实际：对高频交互，长连接更便宜

短连接每次请求都要 TCP 三次握手 + TLS 握手（1–2 ms CPU，1–2 个 RTT 延迟），还要在服务端留 TIME_WAIT。长连接把这些摊销到整个会话，空闲时只占几十 KB 内存。真正贵的是"每条连接一个线程"的旧模型，而不是连接本身。对需要服务端主动推送的 agent 场景，长连接是唯一合理的选择。

误解四：入口必须记住每个用户

实际：入口无状态，状态在后端

入口机只需要在建链时校验 token、查一次 vm_id → 宿主机，之后就是搬运字节。它不缓存会话、不理解业务、甚至看不到 Noise 明文。任何一台入口机坏掉，客户端重连到另一台即可，后端 VM 毫无感知。这正是"可以无限加机器"的前提。

一句话记住：规模问题的解法从来不是"一台更大的机器"，而是"让每一层都只看自己需要看的那一点点信息"。看得越少，越便宜，越容易复制。
通用原理讲完。↓　对照回 Muse 的入口，每个概念落在哪。

07对照 Muse

把前面的概念映射到本次分析里实测到的东西。

通用概念Muse 里的对应（实测）说明

防惊群重连退避 0.5 / 1 / 2 / 5 / 10 s，上限 15 s；服务端用关闭码 1012 / 1013 通知"稍后再试"故障恢复时把几千万客户端的重连摊开。
连接数 vs 后端数每用户 2–3 条连接，每用户 1 台 VM入口的连接数是 VM 数的两三倍；但入口便宜、VM 贵，所以产品用"VM 空闲挂起 + 有人看才唤醒"控成本。
小结：Muse 没有在入口上做任何特别的事，它只是把 Meta 已经为 Messenger、WhatsApp 跑了十多年的那套边缘拿来用，然后把真正特别的部分（Noise 隧道、SEV-SNP 证明、每用户 VM）放在入口之后。
