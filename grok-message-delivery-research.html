Agent 如何“把话送出来”
与持久消息交付有什么不同？

追踪 prompt 接受、用户回应、Agent inbox、SSE 与 checkpoint，比较 Durable Streams、JetStream、LiteTopic 和 S2。

调研：2026-10-13固定提交 a9f633e非官方重建 / 扩展6 项隔离源码探针
核心判断

Grok 的投递逻辑属于 Agent 应用层：它管理谁该回应、怎样排队、何时唤醒。Streams 管持久记录与读取 / 消费位置。两层可以组合，不能把名字相似的 ACK、cursor 或 epoch 当成相同保证。

先分两条路径：默认 Host 有接受账本与回应义务；仓库新增的非 Cursor router 使用另一套内存排队与 JSON 存储。下文分别说明。

01 / 结论与范围

先区分 Agent 投递策略与持久流底座

这套代码与 Streams 共享去重、排序、重试和恢复问题，但它们管理的状态不同。Grok 的重点是接受用户输入、生成会话投影、安排 Agent 工作，以及让模型真正把回应送出来。持久流管理记录与读取位置；消息 Broker 还可以管理未确认交付和重投。

Grok 应用策略

用户输入抢占、Agent inbox、后台完成唤醒、可见答复义务、模型 nudge、用户输出投影。

Stream / Broker 能力

写入确认、持久记录、历史续读、消费者进度、消费 ACK 与重投。不同产品的契约仍需分别核对。

固定提交 a9f633e09d49…（2026-08-23）是非官方重建与扩展，不是原厂服务端源码。仓库保留协议与 artifact anchors，但本次没有逐项重演原始 0.18.0 应用。下文的“代码行为”限定于这个提交。

Renderer → Coordinator：sendPrompt↓ 先交给 inference router 判断

Cursor / 默认 Host 路径

Gateway HTTP → Host send-pipeline → 本地 transcript / nonce ledger → 答复义务 → scheduler → runner。

非 Cursor router 实验

协调器先调用 router，只有未处理才转发 Gateway。新增 router 不只是替换模型 URL，它改变了接受时机、去重、排队、取消与持久化边界。不能把 Host 的保证自动套到所有 provider。

03 / 用户输入

接受、入库、回显和执行是四个不同状态

clientNonce / digest→追加用户条目→pending + 答复义务→发出 echo→入 user lane / accepted

默认 Host 合并同一进程的 in-flight nonce，ledger 以 accountSlot + nonce 检查摘要与重复；之后固定目标会话、追加文本和附件，再排入运行。awaitTurn=false 时，后续执行是 detached，接受回执不等待最终任务完成。

状态源码能确认什么不能推出什么
accepted发送管线已接受 / 排入本地执行模型已经回应、任务成功、队列可跨进程恢复
echo用户条目向客户端投影所有路径均已强持久提交
活跃会话 append先更新内存；DB false 可警告后继续 echo / 执行看到回显就等于 DB 保存成功
离屏用户 appendDB false 会抛出未持久错误与活跃会话具有完全相同的降级语义

04 / 去重与未知

nonce ledger 是受限的接受账本，不是事务 Outbox

send-acceptance.json 记录输入摘要、目标 Agent、echoEntryId 和 pending / accepted / rejected。默认最多 256 条；淘汰、损坏或写失败会留下 history gap / degraded 信息。它与 transcript DB 和内存队列分别写入，没有联合事务。

条件行为
相同 nonce + 相同 digest，记录尚在返回 duplicate；pending 也不会自动重新 dispatch
相同 nonce + 不同 digest拒绝摘要冲突
记录已淘汰或历史有 gaplookup 可返回 unknown-durability；admitSend 仍可 dispatch
文件写失败当前实例保留内存记录；新实例未必能恢复同一记录
本次源码探针验证了后两项：unknown 标记不等于严格禁止重发；完全无法写入 ledger / marker 时，旧实例能判 duplicate，新实例可能判 not-found。它不是无限期的 exactly-once 接受保证。

持久化采用临时文件 + rename；该模块未调用 fsync。原子替换与掉电落盘不是同一个保证。即使 ledger 记录 accepted，若运行队列只在内存中，进程退出后仍需协调“接受了但未执行”的任务。

lookup / admitSend · 容量与 gap · 文件写入

05 / ACK 的语义

欠用户一个回应，和欠 Broker 一次确认不同

ACK obligation 按 Agent 合并用户发送，记录 lastSend、coalescedCount、redriveAttempts，并保存本地文件。它不为每条输入保存独立消费序号。运行中生成 ackToken；有效 token 兑现后清掉这个 Agent 的整个 obligation。

Grok obligation

“这个 Agent 仍需要做出可见回应。”合并多次输入，空闲或重启后可以启动 hidden run，提醒模型调用 SendMessage。

Broker consumer ACK

“这个消费者确认了相应交付。”用于未确认集合和重投；业务决定在哪个提交点确认。

Grok 默认空闲约 5 秒可 redrive，最多 3 次，之后报告 lost。重试动作是让模型重新组织回应，不是重发原始流记录。恢复提示还允许承认上下文缺失，请用户重发；不会据此伪称原任务完成。

fulfill 时点没有等待 Renderer receipt、人类已读或外部 connector 成功。离屏 SendMessage 路径甚至未检查 DB append 的 boolean；与离屏用户输入的严格处理要区分。

token / fulfill · 重挂与 redrive · obligation 状态 · 发送时的 fulfill

06 / 输出与渠道

SendMessage success 不是收件人已收到

模型产生 SendMessage→onSendMessage / transcript 投影→工具 success≠Renderer receipt / connector 成功

默认工具调用同步的 onSendMessage 后返回 messageId / timestamp。runner 的 sentMessageCount 在 transport 回调前增加，因此它是输出事件记账；不是网络消费凭证。

外部渠道投递是 detached Promise。失败会报 tray 错误并排入内存 follow-up，让 Agent 获得补救提示。工具 success 不等待这个 Promise，也没有在该路径看到事务 outbox 的逐消息待投递状态。

代码同时有“没有说话就提醒”和“已有开场答复，但工具结束后仍欠收尾”的 nudges。这比单纯 broker 重投更贴近 Agent 产品需求；业务仍要用显式任务状态确认真实结果。

工具回执 · count 时点 · 渠道投递 · 回复与收尾 nudge

07 / 调度与打断

用户优先的调度策略，不等于流内 FIFO

调度层固定代码行为与流的差别
按 Agent 管队列user / agent / background 三个内存 lane不是 Broker 的持久 consumer
优先级user 优先，然后 agent，再 background执行顺序可以不同于事件追加顺序
用户抢占中断旧 run；可恢复的旧纯文本输入可并入新 turn不保证每条输入都启动独立任务
Watchdoguser 等待超过约 120 秒，另有约 30 秒 grace；可逃逸旧 slot新队列推进不证明旧执行已消失

逃逸后，未结束的旧 Promise 可进入 zombies。generation 避免迟到旧任务清理新 active slot；退休 ackToken 避免旧 run 兑现新义务。它们是局部回调隔离，不能自动阻止旧工具写外部系统。

迁移到 JetStream 或 LiteTopic 后，仍需要独立保留抢占 / supersede / 背景唤醒策略；同时用业务 ownerEpoch 与提交条件防止旧执行越过接管边界。消息序号不能直接替代这些状态。

08 / Agent 到 Agent

发件历史、收件队列和父任务唤醒有不同持久性

Agent inbox

sendToAgent 写发件投影，将 inbound 放入 pendingAgentInbound Map，异步 revive 后返回 Sent。接收端 transcript 与 agent lane 稍后处理；Sent 不等于接收端已落库。

父子 completion

pending-wake 文件保存 workId 等元数据；真正的 completion payload 排在内存 Map。恢复时可重挂 watcher，或明确说明进程内 subagent 已中断、最终状态未知。

收件 revive 先从 Map 取出并删除，再解析会话；解析失败并不在这一层普遍回队。completion 也可先清 marker 再启动父任务 follow-up。两者都有持久历史与运行待办之间的失败窗口。

所以，看到发件条目、pending marker 或 telemetry 的 delivered，不能一概解释成“完整 payload 已由目标消费并展示”。不同动作可复用 stream 作可靠收件箱，但运行恢复仍需应用状态机。

发件 / inbox · take / delete · completion Map · subagent 重启恢复提示

09 / 客户端续接

SSE 负责实时转发，历史另走 transcript API

Gateway /events 发送 data、retry 和 heartbeat，来源是进程内订阅。固定函数没有持久 event ID / offset；Coordinator 每次重新 GET /events，也没有传 Last-Event-ID。1～10 秒退避与 35 秒 stall watchdog 恢复连接，不是把离线记录从某个位置重新播放。

Host 另外提供 getTranscript、分页 / window / tail 和 snapshot 投影。读取当前状态能够修复部分 UI 状态，但与逐事件日志重放有不同粒度。完整 Renderer 的断线补洞没有在本次运行验收。

状态用途不能互换
Replica epoch + sequence按进程 / surface 排序投影不是持久流中稳定的记录位置
Tool relay replay内存中保留 tool call / result，重发给 Renderer不跨 Coordinator 重启保存所有事件
Transcript snapshot / page查询会话当前投影与历史条目不自动保留每个 token delta
DS offset / S2 sequence指向流内位置，按保留范围续读不直接代表“Agent 已答复”或任务完成

Tool relay 接受更大的序号并拒绝旧 epoch，但不要求序号必须连续，不能将其描述为主动完整补洞。Gateway sink.write 返回的背压信号也未在该函数变成 Broker 级未确认上限；慢客户端需要单独验收。

10 / 会话持久化

Journal 是本地 checkpoint 镜像，不是消息消费 ACK

FileTranscriptMirror 确实实现了 JSONL、pending WAL、checkpoint hash、inode / 尾部一致性检查，以及文件和目录 sync。它根据 agent checkpoint 判断补写 pending 内容、丢弃未提交内容，或报告冲突。

checkpoint 变化→prepare pending WAL→state checkpoint / commit 协调→JSONL + cursor / sync

新会话选择 journal 受 sand_new_transcript_journal gate 控制；已有 journal marker 的会话继续走 journal。legacy mirror 失败不会回滚 agent-store checkpoint。不能因为类存在，就宣称当前应用已启用这条路径。

这里的 journal cursor 指本地推导/延迟 step，nonce ledger 指 prompt 接受记录，Replica sequence 指投影顺序，stream offset 指运输位置。四种状态都可以有“进度”的含义，但管理对象不同。

本次确认的是源码路径；没有做 journal crash、掉电或完整 Agent checkpoint 恢复试验。也没有用它推出分布式多副本保证。

11 / 新增 Router 实验

提前 accepted、文本自动投影，是另一套语义

维度默认 Host 路径非 Cursor router
accepted 时点追加 / obligation / 排队流程中排入内存 Promise chain 后立即返回，execute 尚未完成校验与持久写入
nonceledger + digest + duplicate 检查保存到条目；未做同样的去重
调度user / agent / background，抢占按 Agent 内存 chain 串行；未复用这些 lane
输出SendMessage 工具、obligation / nudgesprovider 文本自动转成 send-message 事件
存储transcript DB 与 checkpoint 等共享 JSON 文件；每 Agent 最后 200 条
取消默认 Host 的 run 生命周期入口 signal 未传给 router 执行；不能默认继承 Gateway 取消

routed token / 部分文本先发给 UI，最终 assistant 文本在 provider 完成后才写 JSON。因此中断前曾经显示内容，不代表全部 delta 已持久。每 Agent 串行也不构成共享整份 JSON 的全局写锁，跨 Agent 的 read-modify-rename 存在覆盖窗口；这是静态并发推论，未重现实验。

这条路径是仓库新增实验。用它说明本 fork 的行为很有价值，但不应据此评价原厂 Grok Bot 所有 provider 的投递保证。

12 / 与 Streams 对照

共同需求是恢复，主要差别在管理的责任

对象 / 技术主要管理状态确认或进度对 Grok 的补充
Grok 默认 Hostprompt 接受、调度、可见答复、唤醒nonce 接受记录、per-agent obligation、run token是应用行为层；内存 inbox / scheduler 仍需恢复设计
Durable StreamsHTTP 流资源、写入与历史续读普通读取保存 opaque offset；subscription 扩展另看实现为会话输出提供历史 + live 读取；业务答复义务仍在应用层
JetStreamstream 记录、consumer pending / ACK / 重投stream sequence 与消费确认分别管理可承担任务 / inbox 交付；不能判断模型是否真正答复用户
RocketMQ LiteTopic动态子通道、消费组与订阅交付组位点、Shared / Exclusive、ACK / visibility按会话定向传输；TTL、起点与子级授权仍要明确定义
S2持久追加记录与按位置读记录 sequence、append 确认与 read 位置可作事件历史；不等于模型执行调度或回复策略

三处名称相似，行为差异最大

  1. ACK：Grok 清除“欠回应”的 Agent 义务；Broker 确认相应交付。DS 普通读 / S2 read 的位置又是另一种状态。
  2. 重试：Grok hidden run 可能重新生成文本；Broker 重新交付原记录。二者不能直接共用副作用幂等假设。
  3. 顺序：流内事件有位置；Agent 调度允许抢占、合并和 supersede。输入排序不保证外部工具按序完成。

这些机制互补。即使把所有 inbox 记录写进持久流，也仍要设计取消、结果未知、业务去重、owner 接管与上下文恢复；反之，仅有回复 nudges 不能替代可重读的持久消息。

13 / 故障窗口推演

确认停在哪一层，恢复就应从哪一层协调

选择一个窗口

交互是基于代码顺序的解释，不连接 Grok / Broker。

accepted 保存，执行队列仍在内存

同 nonce 可以被判 duplicate，但还未开始的任务可能已随进程消失。应查询持久任务状态并协调重派，而非只看回执。

源码窗口可能缺什么应用应记录什么
transcript 追加后，nonce ledger 前重复请求的接受身份输入身份与任务在同一权威中登记
inbox Map 取出后，收件存储前未确认的 inbound payload持久 inbox 领取与完成状态
completion marker 清除后，父 run 前可恢复的 completion 结果稳定 completionId、结果记录与消费 ACK
Router token 可见，最终 JSON 前delta 历史明确完整 / 部分 / 丢失范围，或持久事件输出

以上均是实现顺序推论。文件重载探针只验证特定 ledger 行为；没有把这些推论包装成真实应用故障复现。

14 / 对 DSH 的建议与验证

借鉴回应策略，在独立持久交付层上落地

持久输入 / Task + Outbox→Stream / Broker→DSH 调度与 owner→Cube 工具 / 结果提交→可回放输出 / 用户界面

值得借鉴

用户优先、开场与收尾分开、显式答复义务、后台完成唤醒、无法恢复时坦诚显示 unknown。

落地时增强

持久 inbox / outbox、稳定业务 ID、task 状态、结果去重、ownerEpoch 条件提交；消费者 ACK 与用户回执分开。

建议建立 accepted、started、result_committed、output_published、client_received 等阶段。reply_obligation 独立记录该 turn 是否仍欠回应，而非清掉一整个 Agent 的所有消息。状态方案为本项目建议，不是仓库已有协议。
